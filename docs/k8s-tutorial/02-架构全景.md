# 02 架构全景：K8s 组件与通讯

## 本章目标

- 掌握 K8s 的两大分区：控制面（Control Plane）与工作节点（Worker）
- 认识每组件的职责
- 理解组件间的通讯方式（谁和谁说话、走什么协议）
- 在本集群中找到每个组件对应的进程/容器

## 2. 控制面组件（Control Plane）

| 组件 | 角色 | 一句话职责 |
|------|------|-----------|
| **kube-apiserver** | 集群的"总入口" | 唯一能读写 etcd 的组件；所有 kubectl/组件请求都经过它；负责认证、授权、准入 |
| **etcd** | 数据存储 | 持久化保存集群全部状态（期望+实际），分布式强一致 KV 数据库 |
| **kube-scheduler** | 调度器 | 为新 Pod 挑选最合适的节点（过滤→打分） |
| **kube-controller-manager** | 控制器集合 | 常驻控制循环，维持期望状态（Node/Pod/Deployment/... 各控制器） |
| **cloud-controller-manager** | 云控制器 | 对接云厂商（本环境无云，不存在） |

> k3s 要点：以上全部组件 **打包进单个 `k3s-server` 进程**（嵌入式 etcd 也在其中，除非配置外部 etcd）。这就是 k3s "单二进制" 的含义 —— 一条 `k3s` 命令跑起整个控制面。

## 3. 工作节点组件（Worker）

| 组件 | 角色 | 一句话职责 |
|------|------|-----------|
| **kubelet** | 节点上的"管家" | 接收 API Server 下发的 Pod 定义，调用容器运行时创建/管理容器，并上报节点/Pod 状态 |
| **kube-proxy** | 网络代理 | 监听 API Server 的 Service 变化，维护节点上的 iptables/IPVS 规则实现流量转发与负载均衡 |
| **容器运行时** | 运行容器 | 真正拉镜像、起进程（本环境：containerd） |
| **CNI 插件** | 网络插件 | 为每个 Pod 分配 IP、配置网络（本环境：flannel + VXLAN） |
| **kubelet 内部** | — | 还内置了静态 Pod、探针、cAdvisor（指标采集）等能力 |

> 本集群 server 节点未设污点（`taint_server: false`），所以 server 也运行 kubelet/kube-proxy 且可调度业务负载 —— 即 control plane + worker 合体。agent 是纯 worker。

## 4. 组件间如何通讯

### 4.1 通讯总原则

```
   所有组件          只有 apiserver          只跟 apiserver 交互
 ┌──────────┐       ┌─────────────┐       ┌────────────────────┐
 │ kubectl  │──────▶│             │◀──────│ scheduler          │
 │ 用户工具  │ HTTPS │             │       │ controller-manager │
 └──────────┘       │ kube-       │◀──────│ kubelet            │
   其余组件          │ apiserver   │       │ kube-proxy         │
                ┌───▶│             │◀──────│ (watch 监听)       │
                │    └──────┬──────┘       └────────────────────┘
                │           │ 读写
                │           ▼
                │     ┌─────────┐
                └─────│  etcd   │
                      └─────────┘
```

**核心规则**：
1. **只有 apiserver 能访问 etcd**，其他组件一律不许直接碰数据库
2. **所有组件只与 apiserver 通信**（HTTPS/TLS），谁也不直接连别人（除探针/业务流量）
3. kubelet 等组件通过 **watch 长连接**监听 apiserver，状态一变立即感知（事件驱动，非轮询）
4. etcd 与其他组件通过 apiserver 走 **gRPC over TLS**

### 4.2 一次 Pod 创建的完整旅程（经典面试题）

```
1. 用户   kubectl apply -f deployment.yaml
        ────────────────────────────────▶
2. apiserver 认证+授权+校验，写入 etcd
3. controller-manager (Deployment控制器) watch 到期望3副本 → 创建 ReplicaSet → RS控制器创建 Pod 对象
4. scheduler 观察到"未调度Pod" → 选节点 → 把 Pod 绑定到 k3s-demo-agent-1
5. 该节点 kubelet watch 到"分配给本节点的 Pod" → 通过 containerd 拉镜像、创建容器
6. kubelet 持续上报 Pod/容器状态 → apiserver 写回 etcd
7. 用户  kubectl get pods 看到 Running
```

## 5. 本集群实站对照

### 5.1 控制面组件在这里

k3s 单进程整合控制面。SSH 到 server-1 看进程：

```bash
vagrant ssh k3s-demo-server-1 -- "sudo ps -eo pid,comm --no-headers | grep -E 'k3s|containerd' | head"
```

预期输出（节选）：

```
  681 k3s-server         ← 整个控制面 + 嵌入式 etcd
 1563 containerd        ← 容器运行时
 2174 containerd-shim   ← 每个容器的 shim 进程
 ...
```

对应服务：

```bash
vagrant ssh k3s-demo-server-1 -- "sudo systemctl list-units --type=service --state=running | grep k3s"
```

预期输出：`k3s.service  loaded active running  Lightweight Kubernetes`

### 5.2 控制面组件以 Pod 形式出现（kube-system）

k3s 把部分控制面组件也以容器运行（coredns、metrics-server、local-path-provisioner、traefik/nginx-ingress 等）：

```bash
kubectl get pods -n kube-system -o wide
```

预期输出（本环境真实）：

```
NAME                                      READY   STATUS    IP            NODE
coredns-576bfc4dc7-c5j4q                  1/1     Running   10.42.0.234   k3s-demo-server-1
local-path-provisioner-86f46b7bf7-mdnxz   1/1     Running   10.42.0.230   k3s-demo-server-1
metrics-server-557ff575fb-khjrx           1/1     Running   10.42.0.233   k3s-demo-server-1
```

- **coredns**：集群 DNS，第 04 章细讲
- **metrics-server**：资源指标采集（HPA 依赖它）
- **local-path-provisioner**：本地存储动态供应（第 05 章细讲）

> 为什么标准 K8s 的 kube-scheduler/kube-controller-manager 在这里看不到 Pod？
> 因为 k3s 把它们编译进了 `k3s-server` 进程（静态内嵌），不单独以容器运行。

### 5.3 网络组件

```bash
vagrant ssh k3s-demo-server-1 -- "sudo ip -br link show flannel.1"
```

预期输出：`flannel.1  UNKNOWN  52:83:90:f3:12:17  <BROADCAST,MULTICAST,UP,LOWER_UP>` — flannel 的 VXLAN 隧道接口。

CNI 配置：

```bash
vagrant ssh k3s-demo-server-1 -- "ls /var/lib/rancher/k3s/agent/etc/cni/net.d/"
```

预期输出：`10-flannel.conflist` — 告诉 containerd 用 flannel 作为 CNI。

### 5.4 Rancher 界面对照

Rancher → 集群 → **Nodes** 页：
- 能看到 server-1（control-plane,etcd,master）与 agent-1（worker）的角色图标
- 点进节点 → **Allocation** 标签页可看该节点上的 Pod（= kubectl 描述节点的 Pod 列表）

## 6. 常见误区

| 误区 | 纠正 |
|------|------|
| "etcd 是隐藏的，看不到" | k3s 中查看：`k3s etcd-snapshot list` 可用即证明 etcd 在跑（第 08 章） |
| "kubectl 直接连 etcd" | ❌ kubectl 只连 apiserver（6443），etcd 只认 apiserver |
| "controller-manager 在 k3s 里不存在" | 存在，只是编译进 `k3s-server` 进程，不是独立容器 |

## 动手练习

1. 用一条命令查看所有控制面组件的 API 是否健康：`kubectl get --raw='/healthz'` 与 `kubectl get componentstatuses`（后者在新版可能不再返回信息，观察差异）。
2. 查看 `kube-system` 命名空间下 Pod 的镜像，找到 coredns 用的镜像名：`kubectl get pod -n kube-system -l k8s-app=kube-dns -o jsonpath='{.items[0].spec.containers[0].image}'`。
3. 在 server-1 节点上确认 containerd 在运行：`sudo systemctl is-active containerd`。
4. 思考：为什么 etcd 不能直接暴露给用户访问？

<details>
<summary>参考答案</summary>

1. `kubectl get --raw=/healthz` → `ok`；`kubectl get componentstatuses` 在 k8s v1.19+ 已弃用（不再通过 API 暴露），这是刻意为之 —— 组件健康由检查器直接探测。
2. 应输出 `rancher/mirrored-coredns-coredns:1.11.1` 之类的 rancher 镜像仓库地址（离线环境镜像加速所致）。
3. 输出 `active`。
4. 直接暴露 etcd 等于把集群全部状态（含所有 secret）公之于众且绕过 apiserver 的认证/授权/准入控制 —— 所以只有 apiserver 有 etcd 访问权。
</details>
