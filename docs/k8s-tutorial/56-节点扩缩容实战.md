# 56 节点扩缩容实战：从 nodes.yml 到集群验收

## 章节信息

| 项目 | 内容 |
|------|------|
| 适用平台 | Linux / macOS（标准路径）；Windows（ops VM 路径，Vagrant 生命周期在宿主机，k3s-ops.sh 在 ops VM 内执行） |
| 前置章节 | 00/06/08/38/45/46 |
| 预计耗时 | 60-120 分钟（含一次临时 agent 扩缩容演练） |
| 破坏性操作 | **中-高**：会创建/销毁 VM、向集群加入/移除节点；误操作可能影响调度、Pod、etcd 成员。必须先备份、确认节点名、确认工作负载可迁移。 |
| 实测环境 | k3s v1.30.2+k3s2，双节点基线（server-1 192.168.56.10，agent-1 192.168.56.20）；2026-11-26 临时扩容 `agent-2`（192.168.56.21）后清理恢复。 |

## 本章目标

- 掌握节点扩缩容的**通用标准流程**：准备节点 → 加入/移除 → 验收 → 清理。
- 掌握本仓库 **`vagrant/nodes.yml` + Vagrant + k3s-ops.sh** 的实践路径，并理解其边界。
- 能在扩容前做容量/命名/IP/角色检查，在缩容前做 drain/迁移/备份检查。
- 能区分“从 Kubernetes 删除 Node 对象”“卸载 k3s”“销毁 VM”三个不同动作。

> **边界声明**：本章以实验集群为例。生产扩缩容还要考虑机架/可用区、负载均衡、存储亲和、PodDisruptionBudget、变更窗口和回滚方案。`k3s-ops.sh` 是本仓库封装，不是 k3s 标准接口。

## 1. 扩缩容全景

```text
                 扩容（Add Node）
nodes.yml -> vagrant up -> 安装/加入 k3s -> kubectl get nodes -> 观测调度
                                          |
                                          v
                                 kubeconfig/labels/taints/PDB

                 缩容（Remove Node）
备份/检查 -> cordon -> drain -> kubectl delete node -> 卸载 k3s -> vagrant destroy
                  \_________________ Kubernetes ________________/ \__ VM/OS __/
```

| 动作 | Kubernetes 层 | VM/OS 层 | 本仓库层 | 验收 |
|---|---|---|---|---|
| 扩容 agent | 新节点注册为 Node，Pod 可调度 | VM 启动、网络通、k3s-agent 运行 | `nodes.yml` + `up` + `add-node` | `kubectl get nodes` Ready |
| 扩容 server | 加入控制面/etcd（高风险） | VM 启动、6443/2379/2380 等通 | 需谨慎，至少 3 server | etcd 成员健康、API 正常 |
| 缩容 agent | drain/delete node | 停 k3s-agent、清数据、销毁 VM | `remove-node` + `destroy` | 节点消失、Pod 重建 |
| 缩容 server | 先摘 etcd 成员再清理 | 停 k3s、清数据、销毁 VM | 需按 etcd 成员流程 | quorum 不丢、API 正常 |

## 2. 变更前检查清单

**扩容前**：

```bash
# 基线
kubectl --kubeconfig ./kubeconfig get nodes -o wide
kubectl --kubeconfig ./kubeconfig get pods -A -o wide
kubectl --kubeconfig ./kubeconfig top nodes   # 需 metrics-server

# 资源与 IP 规划
cd vagrant && vagrant status
cat vagrant/nodes.yml
```

检查项：

- 新节点名、IP、角色、CPU/内存是否与现有拓扑冲突。
- 宿主机是否有足够 CPU/内存/磁盘。
- 镜像架构与节点架构一致（arm64/amd64）。
- 若要承载有状态工作负载，确认存储方案不是 local-path 绑定旧节点的假设。

**缩容前**：

```bash
# 确认待删节点上的工作负载
kubectl --kubeconfig ./kubeconfig get pods -A -o wide --field-selector spec.nodeName=<node>

# 确认 PDB/副本数
kubectl --kubeconfig ./kubeconfig get pdb -A

# 建议先打快照（etcd）
vagrant ssh k3s-demo-server-1 -c "sudo k3s etcd-snapshot save --name before-scale-down"
```

检查项：

- 关键 Deployment 是否有足够副本和 PDB。
- 是否有 `nodeSelector`/`nodeAffinity`/local PV 绑定该节点。
- 该节点是否为 server/etcd 成员；server 缩容不能当 agent 处理。

## 3. 扩容：通用标准流程（agent）

### 3.1 准备节点

通用标准要求：

- OS 满足 k3s 前置（见 45 章：swap、内核模块、sysctl、时间、防火墙）。
- 节点能访问 server 的 `6443`，能拉取或导入所需镜像。
- 有唯一 hostname、IP、机器 ID。

### 3.2 加入 k3s 集群

**标准方式**（在新节点执行）：

```bash
# 从 server 获取 token（在 server 节点）
sudo cat /var/lib/rancher/k3s/server/node-token

# 在新 agent 节点安装并加入
curl -sfL https://get.k3s.io | \
  K3S_URL="https://<server-ip>:6443" \
  K3S_TOKEN="<node-token>" \
  INSTALL_K3S_VERSION="v1.30.2+k3s2" \
  sh -s - agent --node-name <node-name> --node-ip <node-ip>
```

### 3.3 验收

```bash
kubectl get nodes -o wide
kubectl get pods -A -o wide
kubectl describe node <node-name>
```

验收点：

- Node `Ready`。
- `k3s-agent` systemd active。
- 能调度新 Pod（可用一个简单 Deployment 验证）。
- 节点 labels/taints 符合预期。

## 4. 扩容：本仓库实践（agent）

### 4.1 修改 nodes.yml

编辑 `vagrant/nodes.yml`，新增节点。**这是唯一需要手动编辑的配置文件**：

```yaml
  - name: agent-2
    role: agent
    ip: 192.168.56.21
    cpus: 1
    memory: 2048
```

注意：

- `name` 使用短名，集群内主机名会是 `<cluster_name>-<name>`，如 `k3s-demo-agent-2`。
- IP 不能与现有节点冲突。
- 内存/CPU 要评估宿主机余量；本次实测给临时 agent-2 分配 1c/2GB。

### 4.2 创建 VM

```bash
./k3s-ops.sh up agent-2
# 等价标准命令：cd vagrant && vagrant up k3s-demo-agent-2
```

### 4.3 加入集群

```bash
./k3s-ops.sh add-node agent-2
# agent 会走 ansible/playbooks/k3s-add-agent.yml -> k3s-agent role
```

**本仓库边界**：

- `k3s-ops.sh add-node` 适合**新起空节点**；对已加入集群的节点重复执行可能重启 k3s 服务。
- 节点名接受短名/完整名，由 `lib/nodes.sh` 统一解析；不要手写前缀拼接。
- `k3s-ops.sh install/add-node/remove-node` 现已生成运行时 `ansible/inventory.generated.yml`（gitignored）并显式设置 `ANSIBLE_CONFIG`。Linux/macOS 宿主机默认读取 `.vagrant/machines/<host>/virtualbox/private_key`；Windows ops VM/预分发 key 使用 `~/.ssh/k3s-ops/<host>`。若封装行为异常，仍可退回标准 kubectl + vagrant 生命周期命令，并记录边界。
- `add-node/remove-node` 需要能匹配目标主机。若在非 Vagrant provisioner 环境执行且 inventory 未生成，可能出现“匹配不到主机”或空跑。

### 4.4 2026-11-26 实测证据（临时 agent-2）

```bash
# 1) 扩容前快照
vagrant ssh k3s-demo-server-1 -c "sudo k3s etcd-snapshot save --name before-agent2-drill"
# 实测：Snapshot before-agent2-drill-1795663300-k3s-demo-server-1-1795664937 saved.

# 2) 修改 nodes.yml 后创建 VM
cd vagrant && vagrant up k3s-demo-agent-2

# 3) 加入后验收
kubectl --kubeconfig ./kubeconfig get nodes -o wide
# 实测关键行：
# k3s-demo-agent-2   Ready   <none>   ...   v1.30.2+k3s2   192.168.56.21
```

验收通过后，临时节点已删除并恢复 `vagrant/nodes.yml`，快照已清理（见本文后续记录）。

## 5. 缩容：通用标准流程

缩容顺序很重要，核心原则：**先迁走业务，再删 Kubernetes 对象，再卸载节点，再销毁 VM**。

### 5.1 cordon + drain

```bash
kubectl cordon <node>
kubectl drain <node> --ignore-daemonsets --delete-emptydir-data --timeout=15m
kubectl get pods -A -o wide --field-selector spec.nodeName=<node>
```

说明：

- `cordon` 只禁止新调度，不驱逐已有 Pod。
- `drain` 走 Eviction API，会受 PDB 保护；卡住时先查 PDB/裸 Pod/local data。
- DaemonSet Pod 默认不会被 drain 删除，`--ignore-daemonsets` 常用但要确认后果。

### 5.2 从 Kubernetes 删除节点

```bash
kubectl delete node <node>
```

这一步只删除 API 中的 Node 对象，不会自动销毁 VM，也不保证节点上的 k3s 已卸载干净。

### 5.3 卸载 k3s（在被删节点上）

```bash
# agent
sudo /usr/local/bin/k3s-agent-uninstall.sh

# server
sudo /usr/local/bin/k3s-uninstall.sh
```

如果节点已经销毁或无法访问，这一步无法执行；需要至少确保 Node 对象和 etcd 成员状态已清理，并记录残留风险。

### 5.4 销毁 VM

```bash
# Vagrant/VirtualBox
vagrant destroy -f <vm-name>
```

### 5.5 验收

```bash
kubectl get nodes -o wide
kubectl get pods -A
vagrant status
```

## 6. 缩容：本仓库实践与实测边界

### 6.1 推荐顺序（本仓库）

```bash
# 1) Kubernetes 层：先排空
kubectl --kubeconfig ./kubeconfig cordon k3s-demo-agent-2
kubectl --kubeconfig ./kubeconfig drain k3s-demo-agent-2 --ignore-daemonsets --delete-emptydir-data --timeout=15m

# 2) 删除 Node 对象（可由 remove-node playbook 做，也可手动确认）
kubectl --kubeconfig ./kubeconfig delete node k3s-demo-agent-2

# 3) 仓库封装尝试清理（观察输出，不盲信）
./k3s-ops.sh remove-node -n agent-2

# 4) 销毁 VM
cd vagrant && vagrant destroy -f k3s-demo-agent-2

# 5) 恢复 nodes.yml
# 删除临时 agent-2 条目，避免后续 up/provision 误建
```

### 6.2 2026-11-26 实测观察

临时 `agent-2` 扩容验收后，缩容实测如下：

```bash
# drain/delete node：标准命令成功，agent-2 从 API 消失
kubectl drain k3s-demo-agent-2 --ignore-daemonsets --delete-emptydir-data
kubectl delete node k3s-demo-agent-2

# k3s-ops.sh remove-node：实测失败
./k3s-ops.sh remove-node -n agent-2
# 现象：playbook 报告 "No hosts matched" / 空 inventory / k3s-manage 角色执行上下文不满足预期

# agent 节点卸载脚本：本次环境未找到 agent uninstall 脚本路径可直接复用（以实际节点为准）
# VM 清理：成功
cd vagrant && vagrant destroy -f k3s-demo-agent-2

# nodes.yml 恢复后验收：集群回到 2 个 Ready 节点
kubectl --kubeconfig ./kubeconfig get nodes -o wide
```

**结论**：

- **标准命令是可靠兜底**：`cordon/drain/delete node` + `vagrant destroy` 可以完成本次临时 agent 清理。
- **`k3s-ops.sh remove-node` 在当前仓库/执行上下文下存在边界**：它依赖 inventory/role 上下文；不要把它当成唯一正确路径。
- 删除 Node 对象 ≠ 卸载 k3s ≠ 销毁 VM；文档和脚本都要明确三层。

## 7. Server 节点扩缩容特别说明

> ⚠️ server 扩缩容比 agent 风险高得多，尤其是嵌入式 etcd。

| 场景 | 风险 | 要点 |
|---|---|---|
| 新增 server | 中高 | 需要正确的 join 参数、证书/token、etcd 成员加入；建议奇数 server（3/5） |
| 移除 server | 极高 | 必须先确认 etcd quorum、移除 etcd 成员，再 drain/delete/uninstall；不能直接 destroy |
| 单 server 集群 | 高 | 无控制面冗余；升级/重启即控制面中断，必须先备份 |

标准思路：

```bash
# 查看 etcd 成员（server 上）
sudo k3s etcd-snapshot save --name before-server-change
sudo etcdctl member list   # 需设置 ETCDCTL_* 证书参数，见 12 章

# 新 server 加入（示例思路）
curl -sfL https://get.k3s.io | K3S_TOKEN=<token> sh -s - server \
  --server https://<existing-server>:6443 \
  --node-name <name> --node-ip <ip>
```

本仓库有 `k3s-add-server.yml`，但生产使用前必须在隔离环境验证 etcd 成员变化、证书、负载均衡和回滚。

## 8. 常见坑与排障

| 现象 | 原因 | 排查 | 处理 |
|---|---|---|---|
| 新节点 `NotReady` | k3s-agent 未启动、网络不通、镜像/运行时问题 | `systemctl status k3s-agent`；`journalctl -u k3s-agent -n 200`；`kubectl describe node` | 修复网络/配置/镜像后重启服务；确认 6443 可达 |
| `add-node` 对已有节点执行后服务重启 | 设计上只用于新空节点 | 检查命令历史、节点状态 | 避免重复执行；已有节点变更走 upgrade/config 流程 |
| `remove-node` 报 No hosts matched | inventory 非 Vagrant 动态上下文，或节点名未匹配 | 检查 `ansible/inventory.yml`、`nodes.yml`、`lib/nodes.sh` 解析结果 | 退回标准命令：drain/delete/uninstall/destroy；必要时修 inventory 生成 |
| drain 卡住 | PDB 不允许驱逐、裸 Pod、local data、Finalizer | `kubectl get pdb -A`；`kubectl describe pod`；`kubectl get pods -A -o wide --field-selector spec.nodeName=<node>` | 调整副本/PDB；处理裸 Pod/emptyDir；必要时设超时并人工评估 |
| 缩容后 Pod Pending | 剩余容量不足、nodeAffinity/nodeSelector/local PV 绑定 | `kubectl describe pod`；`kubectl get pv,pvc -A`；`kubectl get nodes -o wide` | 扩容回补、调整调度约束、迁移数据 |
| 删除了 VM 但 Node 仍残留 | 只做了 VM 层操作 | `kubectl get nodes` | `kubectl delete node <name>`；必要时清理失联 server/etcd 成员 |

## 9. 动手练习

1. **设计扩容**：为当前双节点集群设计一个 `agent-2` 扩容方案，写出 IP、CPU/内存、前置检查、验收命令和回滚点。
2. **标准命令演练**：在测试环境用标准 k3s install script 加入一个 agent，再用 `cordon/drain/delete node/uninstall` 完成缩容。
3. **边界识别**：解释 `k3s-ops.sh add-node`、`remove-node`、`vagrant destroy`、`kubectl delete node` 各自影响哪一层。
4. **PDB 联动**：给一个 2 副本 Deployment 设置 PDB，再尝试 drain 承载它的节点，观察阻塞与放行条件。

## 10. 清理

本章若做了临时扩容，必须清理：

```bash
# Kubernetes 层
kubectl --kubeconfig ./kubeconfig drain <temp-node> --ignore-daemonsets --delete-emptydir-data --timeout=15m
kubectl --kubeconfig ./kubeconfig delete node <temp-node> --ignore-not-found

# VM 层
cd vagrant && vagrant destroy -f <temp-vm>

# 配置层：移除 vagrant/nodes.yml 中临时节点条目

# 验收
kubectl --kubeconfig ./kubeconfig get nodes -o wide
cd vagrant && vagrant status
```

同时清理实验快照/备份（确认不再需要）：

```bash
vagrant ssh k3s-demo-server-1 -c "sudo k3s etcd-snapshot ls"
# 确认后删除
vagrant ssh k3s-demo-server-1 -c "sudo k3s etcd-snapshot delete <snapshot-name>"
```

## 11. 小结

- 扩缩容要分三层看：**Kubernetes 对象、节点上的 k3s/OS、VM/基础设施**。
- 扩容核心是“准备好节点再加入，加入后用 kubectl 验收”；缩容核心是“先 drain，再 delete node，再卸载/销毁”。
- 本仓库可用 `nodes.yml + k3s-ops.sh up/add-node` 做实验扩容，但 `remove-node` 存在执行上下文边界，标准命令必须掌握。
- server/etcd 成员扩缩容属于高风险变更，不能套用 agent 流程。
