## 1. k3s 为什么会“多出来”这些东西

上游 Kubernetes 通常只给你控制面和基础 API，CNI、CoreDNS、Ingress、监控、LB 等组件由你自行安装。k3s 面向边缘和快速交付，把一些常用组件**打包进发行版**，并在 server 启动时自动部署。

这带来两个直接结果：

1. **开箱即用更快**：单机/小集群拉起后就有 DNS、metrics-server、本地存储等基础能力。
2. **运维要理解“自动部署层”**：你看到的某些资源不是手工 `kubectl apply` 的，而是 k3s server 从 manifests 目录持续同步出来的。

本项目当前策略（`ansible/group_vars/all.yml`）：

```yaml
k3s_config:
  disable_traefik: "{{ disable_traefik | default(true) }}"
  disable_servicelb: "{{ disable_servicelb | default(true) }}"
  taint_server: "{{ taint_server | default(false) }}"
```

对应到 server 节点 `/etc/rancher/k3s/config.yaml`，实测可见：

```yaml
disable:
  - traefik
  - servicelb
```

这也是本教程前面章节的前提：Ingress 用 nginx-ingress（第 31 章），ServiceLB 保持关闭（第 44 章）。

### 2.1 AddOn 对象：k3s 的“静态 manifest 同步记录”

k3s 会把 manifests 目录中的文件注册为 `AddOn`（`k3s.cattle.io/v1`）：

```bash
kubectl --kubeconfig ./kubeconfig get addon -A
```

实测输出：

```text

kube-system   auth-delegator              /var/lib/rancher/k3s/server/manifests/metrics-server/auth-delegator.yaml              f55fee...
kube-system   auth-reader                 /var/lib/rancher/k3s/server/manifests/metrics-server/auth-reader.yaml                 97a74f...

kube-system   metrics-apiservice          /var/lib/rancher/k3s/server/manifests/metrics-server/metrics-apiservice.yaml          03266d...

kube-system   runtimes                    /var/lib/rancher/k3s/server/manifests/runtimes.yaml                                   4ea3be...
```

可以把 AddOn 理解为：**k3s 对“这个文件已被管理”的内部记录**。它带有 source 文件路径和 checksum，便于 k3s 判断文件是否变化。

### 2.2 关键行为边界（很重要）

| 行为 | 结论 | 运维含义 |
|------|------|----------|
| 放入 manifests 目录的文件 | k3s 会自动部署/更新 | 适合受控的自动化交付，但要明确谁是“源” |
| 修改 manifests 文件 | k3s 会按文件变化同步 | 直接手改节点文件可能在重启/升级时被覆盖或造成漂移 |
| 删除 manifests 文件 | k3s 通常会删除对应 AddOn 管理的资源 | **危险**：误删内置 manifest 可能删掉 CoreDNS/metrics-server 等组件 |
| 用 `kubectl edit` 改 AddOn 部署出来的资源 | 可能被 k3s 再次同步覆盖 | 想持久化，改源文件/HelmChartConfig/上游交付方式，不要只改运行时对象 |

> 项目实践：不要把 `/var/lib/rancher/k3s/server/manifests` 当普通 GitOps 目录随手改。它是 k3s server 本地管理目录，变更应经过明确的运维流程。

## 3. 内置组件长什么样

### 3.1 CoreDNS manifest

`coredns.yaml` 是普通 Kubernetes YAML，包含 ServiceAccount、ClusterRole、ClusterRoleBinding、ConfigMap、Deployment、Service 等对象。实测片段：

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: coredns
  namespace: kube-system
data:
  Corefile: |
    .:53 {
        errors
        health
        ready
        kubernetes cluster.local in-addr.arpa ip6.arpa {
          pods insecure
          fallthrough in-addr.arpa ip6.arpa
        }
        hosts /etc/coredns/NodeHosts {
          ttl 60
          reload 15s
          fallthrough
        }
        prometheus :9153
        forward . /etc/resolv.conf
        cache 30
        loop
        reload
        loadbalance
        import /etc/coredns/custom/*.override
    }
    import /etc/coredns/custom/*.server
```

这说明 k3s 的“内置组件”并不神秘，本质还是标准 K8s 资源，只是由 k3s 自动投递。

### 3.2 metrics-server manifest

实测 `metrics-server-deployment.yaml` 关键字段：

## 4. HelmChart / HelmChartConfig：k3s 的 Helm 控制器

k3s 内置 Helm Controller，会识别 `HelmChart` 和 `HelmChartConfig` CRD，并在集群内创建 Helm job 执行安装/升级。

### 4.1 CRD 存在，但当前集群没有 HelmChart 实例

```bash
kubectl --kubeconfig ./kubeconfig get crd | grep -i helm
kubectl --kubeconfig ./kubeconfig get helmcharts,helmchartconfigs -A
```

实测：

```text
helmchartconfigs.helm.cattle.io    2026-05-25T09:12:53Z
helmcharts.helm.cattle.io          2026-05-25T09:12:53Z

No resources found   # HelmChart
No resources found   # HelmChartConfig
```

这很正常：本项目把 traefik/servicelb 关闭了，而且 ingress/monitoring 等组件是我们用 Helm CLI 或手工方式安装的，不是通过 k3s manifests 里的 HelmChart CR 自动安装。

### 4.2 HelmChart.spec 关键字段

`kubectl explain helmchart.spec` 实测可见字段（节选）：

```text
authSecret, backOffLimit, bootstrap, chart, chartContent, createNamespace,
dockerRegistrySecret, failurePolicy, helmVersion, jobImage, repo, repoCA,
repoCAConfigMap, set, targetNamespace, timeout, valuesContent, version
```

理解方式：

| 字段 | 作用 |
|------|------|
| `chart` / `repo` / `version` | 指定 Helm chart 来源与版本 |
| `chartContent` | 直接内嵌 chart（base64/gzip），离线或内置场景常见 |
| `targetNamespace` / `createNamespace` | 安装目标命名空间 |
| `valuesContent` | 内联 values.yaml 内容 |
| `set` | 类似 `helm install --set` 的键值覆盖 |
| `bootstrap` | 标记为引导组件，适合系统关键组件 |
| `failurePolicy` | 失败策略（如 abort/reinstall，具体以版本行为为准） |

### 4.3 HelmChartConfig：给已存在的 HelmChart 打补丁

`HelmChartConfig` 只有很小的 spec（实测）：

```text
failurePolicy <string>
valuesContent <string>
```

它的典型用途是：**不改原 HelmChart，只追加/覆盖 values**。例如 k3s 自带 Traefik 时，常用 HelmChartConfig 修改 Traefik Service 类型或端口；本项目禁用了 Traefik，因此没有这个对象。

### 4.4 HelmChart 与 `helm install` 的区别

| 维度 | `helm install/upgrade`（CLI） | `HelmChart`（k3s CRD） |
|------|-------------------------------|------------------------|
| 执行位置 | 你运行 helm 的机器/ops VM | k3s 集群内 Helm Controller 创建 Job |
| 真源 | 命令、values 文件、CI/GitOps | Kubernetes CR（可放 manifests 目录或 GitOps） |
| 适合场景 | 人工运维、CI/CD、一次性安装 | 集群引导、自动部署、声明式托管 |
| 可见性 | `helm ls` | `kubectl get helmchart -A` + helm job/pod + `helm ls` |

两者不是互斥关系。k3s 内置组件常用 HelmChart/manifest；本教程里的 Rancher、nginx-ingress、监控等更多用 Helm CLI，便于教学时显式控制版本和 values。

## 5. `disable` 与组件生命周期

### 5.1 k3s server 的 disable 选项

`k3s server --help` 实测与组件相关的关键项：

```text
--disable value                 Do not deploy packaged components and delete any deployed components
                                (valid items: coredns, servicelb, traefik, local-storage, metrics-server, runtimes)
--disable-helm-controller       Disable Helm controller
--disable-cloud-controller      Disable k3s default cloud controller manager
--disable-network-policy        Disable k3s default network policy controller
--disable-kube-proxy            Disable running kube-proxy
```

`disable` 的行为不是“隐藏”，而是**不部署打包组件，并删除已部署的对应组件**。这是运维上非常强的语义。

### 5.2 本项目为什么禁用 traefik / servicelb

| 组件 | 本项目选择 | 原因 | 对应章节 |
|------|-----------|------|----------|
| `traefik` | 禁用 | 使用 nginx-ingress，避免双 Ingress Controller 冲突 | 31,44 |
| `servicelb` | 禁用 | 使用 NodePort + nginx-ingress；避免 Klipper LB 抢占 30080/30444 | 44 |
| `local-storage` | 保留 | 教学环境默认 StorageClass，48/49/50 等章节依赖它 | 05,20,48 |
| `metrics-server` | 保留 | `kubectl top`、HPA、监控基线依赖 | 08,47 |
| `coredns` | 保留 | 集群 DNS 基础设施 | 04,19 |

### 5.3 配置从哪里来

本仓库的配置链路：

```text
vagrant/nodes.yml
  -> Vagrant/Ansible provision
  -> ansible/group_vars/all.yml（默认值/映射）
  -> ansible/roles/k3s-server/templates/config.yaml.j2
  -> /etc/rancher/k3s/config.yaml（节点实际生效）
  -> /etc/systemd/system/k3s.service（ExecStart --config ...）
```

实测 systemd 单元：

```text
ExecStart=/usr/local/bin/k3s server \
    --config /etc/rancher/k3s/config.yaml
```

因此排查“为什么组件没装/被删了/参数没生效”，要按这个链路从上游到下游看，不要只看某一个文件。

## 6. k3s 与上游 K8s 运维差异

| 主题 | 上游 K8s（常见发行版） | k3s |
|------|------------------------|-----|
| 安装形态 | 多组件二进制/容器，kubeadm/kubespray 等编排 | 单二进制，server/agent 模式 |
| 内置组件 | 通常较少，CNI/Ingress/LB 自选 | 打包 coredns、metrics-server、local-storage、traefik、servicelb 等 |
| 自动部署 | 一般无 manifests 自动投递机制 | server 监控 `/var/lib/rancher/k3s/server/manifests` |
| Helm 集成 | 外部 Helm CLI/ArgoCD/Flux | 内置 Helm Controller + HelmChart/HelmChartConfig CRD |
| 组件禁用 | 组件各自安装/卸载 | `disable` 可声明式关闭打包组件 |
| 容器运行时 | containerd/containerd+CRI-O 等外部管理 | 内置 containerd（`k3s ctr`, `k3s crictl`） |
| 数据库 | 外部 etcd 或托管 | 默认 sqlite（单节点）或嵌入式 etcd（HA） |
| 升级/运维 | kubeadm/发行版工具 | 可用 k3s 安装脚本、systemd、或本仓库 `k3s-ops.sh` 封装 |

这不代表 k3s “不是 K8s”。它是 CNCF 认证的 Kubernetes 发行版；差异主要在**打包、默认组件和运维入口**。

## 7. 安全与运维注意事项

1. **不要手改内置 manifest 当长期方案**。节点重建、k3s 升级或配置变更可能覆盖。
2. **`disable` 会删除组件**。在生产环境禁用 `coredns`/`local-storage`/`metrics-server` 前，要确认依赖。
3. **HelmChart 是集群内执行**。chart 来源、valuesContent、Secret 引用都要纳入审计。
4. **AddOn/HelmChart 不等于 GitOps 全部**。它们适合引导和简单自动化；复杂多环境交付仍建议 Fleet/ArgoCD/Helm CI。
5. **排障先看三层**：`config.yaml`（意图）→ `manifests/AddOn/HelmChart`（声明）→ Pod/Job/Event（实际执行）。

## 8. 常见坑与排障

| 现象 | 原因 | 处理 |
|------|------|------|
| 修改 `/var/lib/rancher/k3s/server/manifests/*.yaml` 后被还原 | AddOn controller 以 manifests 目录为真源持续 reconcile | 不直接改文件；改 nodes.yml/k3s config、HelmChartConfig 或 GitOps 源 |
| 禁用组件后资源还在/又出现 | disable 配置未真正下发到 config.yaml，或改错位置 | 检查 `nodes.yml -> group_vars -> config.yaml.j2 -> /etc/rancher/k3s/config.yaml` 链路；确认 k3s 重启 |
| HelmChart 已创建但组件没装起来 | `helm-install-*` Job 失败（镜像拉取、chart、values 问题） | `kubectl -n kube-system get jobs,pods | grep helm-install`；查看 Job Pod 日志 |
| HelmChartConfig 不生效 | 名称/namespace 不匹配目标 HelmChart，或 controller 未运行 | `kubectl -n kube-system get helmchart,helmchartconfig`；确认 `helm-controller` 正常、spec 内容正确 |

## 11. 小结

- k3s 把常用组件打包，并通过 `server/manifests` + AddOn 控制器自动部署。
- `HelmChart/HelmChartConfig` 是 k3s 内置 Helm Controller 的声明式接口，不是 Helm CLI 替代品。
- `disable` 是强语义：不部署并删除对应打包组件；本项目据此关闭 traefik/servicelb。
- k3s 与上游 K8s 的核心差异在运维和打包层，API/资源模型仍是 Kubernetes。
