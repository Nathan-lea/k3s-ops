# 19 服务发现详解：名字如何变成地址

## 1. 服务发现：它到底解决什么问题

### 1.1 Pod IP 是"易变的"，这是所有问题的起点

本集群两天内的两次采集对比（**同一个 coredns Pod**）：

```text
10-05: coredns-576bfc4dc7-c5j4q   10.42.0.29   (RESTARTS 13)
10-06: coredns-576bfc4dc7-c5j4q   10.42.0.62   (RESTARTS 14)   ← 重启过一次，IP 变了
```

再看它的 Service（被所有 Pod 当 DNS 服务器用的那个）：

```text
kube-dns   ClusterIP   10.43.0.10   53/UDP,53/TCP,9153/TCP
```

**核心矛盾**：Pod 重建/漂移 → IP 变化（Pod IP 不在集群外可达，也不承诺稳定）；但所有客户端需要**一个不变的入口**。如果让应用"记住 Pod IP"直接调用，Pod 一重启就全挂。

### 1.2 服务发现 = 两件事的自动化解

| 方向 | 谁发起 | 机制 | 答的问题 |
|------|--------|------|---------|
| **找服务**（正向） | 客户端（任意 Pod/节点） | DNS + Service ClusterIP | "我想掉的 `nginx-svc` 在哪？" |
| **感知后端**（反向） | 控制面 | Endpoints/EndpointSlices watch | "当前有哪些 Pod 配得上这个服务？" |

两条链汇合在 kube-proxy：一边拿到"名字→VIP"（DNS），一边拿到"VIP→Pod 列表"（Endpoints），最终织成每个节点上的转发规则。

> **一句话**：服务发现把"易变的 Pod IP + 不变的访问需求"之间的空隙，用一套自动更新的中间层（名字 + 虚拟 IP + 端点清单 + 转发规则）填平。

## 2. 原理总览：四大件各司其职

### 2.1 一张图看清全套数据流（本集群实测数值）

```text
┌────────────┐  DNS查询       ┌──────────────────────────┐
│   应用     │ ──────────▶   │ CoreDNS (Pod 10.42.0.62) │
│ (nginx-demo│               │ kube-dns Service 10.43.0.10│
│  Pod 里)   │ ◀──────────   └──────────────────────────┘
└────┬───────┘  返回记录      返回: nginx-svc.lab.svc.cluster.local = 10.43.23.169
     │
     │ HTTP http://nginx-svc.lab.svc.cluster.local/  ──▶ 10.43.23.169:80 (ClusterIP)
     ▼
┌─────────────────────────────────────────────────────────────┐
│ kube-proxy 在各节点写的 iptables (第 11 章)                    │
│ 10.43.23.169:80 ──负载均衡──▶ 10.42.0.57:80 / .58 / .66 / .67 / .68
└─────────────────────────────────────────────────────────────┘
```

### 2.2 四大件角色表

| 组件 | 类型 | 干什么 | 由谁维护 | 本集群实例 |
|------|------|--------|---------|-----------|
| **Service** | API 对象 | 提供稳定的虚拟 IP（ClusterIP）+ 端口抽象 + 选择器 | 用户创建；控制面分配 IP | `nginx-svc` 10.43.23.169 |
| **CoreDNS** | 集群 DNS | 把 `svc.ns.svc.cluster.local` 解析成 ClusterIP | Deployment（k3s 内建） | `kube-dns` 10.43.0.10 |
| **Endpoints/EndpointSlices** | API 对象 | 记录"当前后端 Pod 的 IP:Port 清单" | **控制面自动维护**（watch Pod） | `nginx-svc` → 5 个 10.42.0.x |
| **kube-proxy** | 节点进程 | 把 VIP 规则写到每个节点的 iptables/ipvs | k3s 内嵌于各节点 | server-1 / agent-1 各一份 |

> 注意：Service 和 Endpoints 都"躺"在 etcd（第 17 章定义世界），**真正干活的是每节点的 kube-proxy 规则**。这也是为什么"服务通了"要逐节点验证规则（第 11 章）。

## 3. DNS 命名体系：名字到地址的完整规则

### 3.1 全名三段式（必须背）

```text
<service>.<namespace>.svc.cluster.local
   nginx-svc .  lab      .svc  .cluster.local
      │           │         │        │
    服务名      命名空间   固定段   集群域(可配置)
```

- `svc.cluster.local` 是固定后缀；`cluster.local` 是集群域（k3s 可通过 `--cluster-domain` 改）
- 同一命名空间内，这四种写法都能访问（**实测全部返回 200**）：

```bash
kubectl -n lab exec deploy/nginx-demo -- curl -s -o /dev/null -w "%{http_code}\n" http://nginx-svc.lab.svc.cluster.local/   # 全名: 200
kubectl -n lab exec deploy/nginx-demo -- curl -s -o /dev/null -w "%{http_code}\n" http://nginx-svc.lab/                     # 带 ns 短名: 200
kubectl -n lab exec deploy/nginx-demo -- curl -s -o /dev/null -w "%{http_code}\n" http://nginx-svc/                         # 纯短名(同 ns): 200
```

### 3.2 为什么短名能用？—— Pod 的 resolv.conf（实测全文）

```bash
kubectl -n lab exec deploy/nginx-demo -- cat /etc/resolv.conf
```

真实输出：

```text
search lab.svc.cluster.local svc.cluster.local cluster.local
nameserver 10.43.0.10
options ndots:5
```

三个字段就是短名魔法的全部秘密：

| 字段 | 值（实测） | 含义 |
|------|-----------|------|
| `nameserver` | `10.43.0.10` | 所有 Pod 的 DNS 服务器 = kube-dns Service（CoreDNS） |
| `search` | `lab.svc.cluster.local svc.cluster.local cluster.local` | 名字补全候选：先试同命名空间，再试 svc，再试集群域 |
| `ndots` | `5` | 名字里"点"数 ≤5 时，**先依次套 search 域试**，全失败才直接查原名字 |

> `nginx-svc`（0 个点）→ 依次试 `nginx-svc.lab.svc.cluster.local` ✅ 命中，解析成功。
> **排障启示**：哪天纯短名突然解析不了，先看是不是跨了命名空间（跨 ns 必须用 `svc.ns` 或全名）；再查 search 域有没有配进去（dnsPolicy 问题）。

### 3.3 跨命名空间调用：必须带命名空间

```text
http://cert-manager-webhook.cert-manager.svc.cluster.local/    ← 全名（任何地方）
http://cert-manager-webhook.cert-manager/                      ← 带 ns 短名（任何地方）
http://cert-manager-webhook/                                   ← ✗ 只有 cert-manager ns 内可用
```

> 本集群里 kube-apiserver 调用 cert-manager 的 webhook 时就靠 `cert-manager-webhook.cert-manager.svc` 这样的服务名（`cert-manager-webhook` Service：10.43.10.230，实测）。这就是"服务发现被管理面自己用着"的例子。

### 3.4 特殊形态

**① Headless Service（`clusterIP: None`）——解析直接给 Pod IP**
不分配 ClusterIP、不生 kube-proxy 规则；DNS 返回**所有后端 Pod IP 的 A 记录**：

```text
普通 Service  : nginx-svc.lab.svc.cluster.local → 10.43.23.169（虚拟 IP，一条）
Headless      : my-svc.lab.svc.cluster.local    → 10.42.0.57, 10.42.0.58, ...（真实 Pod IP，多条）
<pod>.<svc>.<ns>.svc.cluster.local              → 单个 Pod 的真实 IP（须 Pod 名含在 service 端点内）
```

典型用途：StatefulSet 有状态主从直连（`pod-0.redis-headless` 直打到 0 号实例）、客户端要做自定义负载均衡。本集群未部署 Headless（概念如上，可用 `kubectl explain svc.spec.clusterIP` 探索）。

**② ExternalName——外部域名的 CNAME 别名**
`svc.spec.externalName: db.example.com`：DNS 返回的是 CNAME，把集群内服务名"别"到集群外真实域名。适用于"内网应用先接外部 SaaS，以后迁回集群"的过渡。

**③ 控制面自己的服务：`default/kubernetes`**
永远存在（本集群实测）：

```text
default   kubernetes   ClusterIP   10.43.0.1   443/TCP
default   kubernetes   ENDPOINTS   192.168.56.10:6443   ← kube-apiserver 真实地址
```

kubelet、kubectl、所有 SDK 默认都连 `https://kubernetes.default.svc.cluster.local:443`——这是集群里**第一个、也是最重要的服务发现**。

## 4. 后端发现：Endpoints / EndpointSlices（控制面如何"感知"）

### 4.1 生命周期五步（服务发现的"反向链"）

```text
① 创建 Service(selector: app=nginx-demo)   ──用户/apply──▶ etcd
② Endpoints 控制器 watch Service+Pod        ──控制面──▶ 算出匹配的 Pod IP 列表
③ 写入 Endpoints / EndpointSlices           ──控制面──▶ etcd（第 17 章"定义世界"）
④ kube-proxy watch 到变化                   ──每节点──▶ 重写本机 iptables（第 11 章）
⑤ 新 Pod 上线/下线 → 重复 ②③④              ──自动──▶ 永远新鲜
```

**关键**：整条链是**事件驱动、自动对账**的——你不用手动通知任何人"我加了 3 个副本"。

### 4.2 老一代：Endpoints（同名对象）

```bash
kubectl -n lab get endpoints nginx-svc
```

真实输出：

```text
NAME        ENDPOINTS                                                    AGE
nginx-svc   10.42.0.57:80,10.42.0.58:80,10.42.0.66:80,10.42.0.67:80,10.42.0.68:80   3d2h
```

5 个副本 5 条记录，与 `kubectl get pods -l app=nginx-demo` 一一对应。**Endpoints 出错（为空/不对）＝服务发现的后端链断了**。

### 4.3 新一代：EndpointSlices（K8s 1.21+ 默认，本集群在用）

```bash
kubectl -n lab get endpointslices -l kubernetes.io/service-name=nginx-svc -o yaml
```

真实输出节选（5 个端点之一）：

```yaml
apiVersion: discovery.k8s.io/v1
kind: EndpointSlice
metadata:
  labels:
    kubernetes.io/service-name: nginx-svc     # ← 归哪个 Service（关键标签）
addressType: IPv4
ports:
- port: 80
  protocol: TCP
endpoints:
- addresses: [10.42.0.67]
  conditions:
    ready: true
    serving: true
    terminating: false                          # ← 状态细分比以前丰富
  nodeName: k3s-demo-server-1
  targetRef:                                     # ← ★ 指回具体 Pod（含 uid）
    kind: Pod
    name: nginx-demo-7fb649d588-v8wl5
    namespace: lab
    uid: 0cf512d4-9530-44ab-842c-7836b41ca51d
```

**为什么升级到 EndpointSlices**（对排障有实际意义）：

| 优点 | 说明 |
|------|------|
| 切片化 | 一个大 Service 拆成多个 slice，单个对象小，**watch 负载低** |
| 状态细分 | `ready/serving/terminating` 三维，可精细控制"不 ready 就不转发" |
| 扩展性好 | 5000 端点级别的服务不把 etcd 压垮（Endpoints 单对象会巨大） |

> 排障注意：老教程讲 `kubectl get endpoints`，新版本看 `kubectl get endpointslices`——两者是"同一个事实的两种视图"。`get endpoints` 依然可用、内容一致（上面实测两者都有）。

### 4.4 selector 不匹配 → Endpoints 为空（核心排障点）

```text
kubectl -n lab get svc nginx-svc -o jsonpath='{.spec.selector}'   → map[app:nginx-demo]
kubectl -n lab get svc nginx-svc -o jsonpath='{.spec.ports}'      → [{port:80 ...}]
kubectl -n lab get endpoints nginx-svc                            → 若为空 = 没有任何 Pod 有 app=nginx-demo
```

**最常见故障**：手误把 Pod 标签写成 `app: nginx` 或加了 `version` 标签——selector 严格相等匹配，一个不满足就少一个端点。**排查顺序永远是：svc selector → pod labels → endpoints 是否同步**。

### 4.5 无 selector 的 Service：手工指定端点

`default/kubernetes` 就是典型（selector 空，端点手工写 apiserver 地址）：

```bash
kubectl get svc kubernetes -o jsonpath='{.spec.selector}'   # 输出 <nil>（无 selector）
kubectl get endpoints kubernetes                           # 192.168.56.10:6443（手工维护）
```

用途：把**集群外的服务**（外部数据库、旧系统）也挂进集群 DNS，让 Pod 用服务名访问。此时 Endpoints 控制器不自动管，需要你自己维护（或 externalName 替代）。

### 4.6 后端变化的自动对账（本集群活案例）

coredns 重启，Pod IP 从 `10.42.0.29` 变成 `10.42.0.62`：

```text
10-05: Endpoints kube-dns → 10.42.0.29:53      Pod IP = 10.42.0.29
10-06: Endpoints kube-dns → 10.42.0.62:53      Pod IP = 10.42.0.62   （自动更新 ✅）
       kube-dns Service ClusterIP 10.43.0.10   （纹丝不动 ✅）
```

**全集群无感知**：没有任何 Pod 需要改配置——这就是服务发现的意义。

## 5. 客户端发现方式对比：DNS vs 环境变量

### 5.1 环境变量方式（实测）

每个 Pod 创建时，kubelet 把**当时存在的** Service 注入环境变量（`NS` 前缀转大写、`-` 转 `_`）：

```bash
kubectl -n lab exec deploy/nginx-demo -- env | grep -iE "NGINX_SVC|KUBERNETES" | head
```

真实输出：

```text
KUBERNETES_PORT=tcp://10.43.0.1:443
NGINX_SVC_PORT_80_TCP_PROTO=tcp
NGINX_SVC_PORT_80_TCP=tcp://10.43.23.169:80        ← 服务名+端口 → ClusterIP
NGINX_SVC_PORT_80_TCP_PORT=80
NGINX_SVC_SERVICE_HOST=10.43.23.169
KUBERNETES_SERVICE_HOST=10.43.0.1
KUBERNETES_SERVICE_PORT=443
KUBERNETES_PORT_443_TCP_ADDR=10.43.0.1
```

> 注意：`KUBERNETES_*` 恒在（`default/kubernetes` 比任何 Pod 都早存在）；`NGINX_SVC_*` 之所以在，是因为 nginx-demo 在 nginx-svc 创建**之后**重启过（rollout restart），否则新 Pod 会没有这些变量。

### 5.2 对比表（选型依据）

| 维度 | DNS（推荐） | 环境变量 |
|------|------------|---------|
| 发现时机 | 运行时解析，**服务后建也能用** | **创建时快照**：Pod 启动时不存在的 Service 永远拿不到 |
| 信息量 | 名字/多个端口/Headless 多 IP | 完整但**每多一个 Service 就多占一份内存**（几百个服务时是负担） |
| 延迟/失败 | 解析失败可控（可重试） | 无此问题，但拿不到就是拿不到 |
| 典型场景 | 一切生产环境、跨 ns | 同命名空间小规模、死板但简单的场景 |
| 端口多时 | 不受影响 | 变量数量爆炸（每端口每协议一组） |

**结论**：生产一律用 DNS；环境变量是"能工作但不优雅"的旧方便法。

## 7. 排障：服务发现四层链路

### 7.1 四层模型（从外向里排查）

```text
第1层 Service   : 定义在不在？ClusterIP 对不对？       → get svc <名> -o yaml
第2层 Endpoints : 后端有没有？Selector 对不对？        → get ep <名> / get endpointslices
第3层 DNS       : 名字解析得出吗？解析到谁？           → exec Pod 里 curl 全名/短名；检查 resolv.conf
第4层 数据面    : 规则在每节点一致吗？包到了吗？       → 第 11 章 iptables；各节点分别验证
```

### 7.2 现象 → 定位表

| 现象 | 最可能原因 | 第一命令（实测可用） |
|------|-----------|---------------------|
| `connection refused` | Pod 没起/端口不对 | `kubectl get ep <svc>` + `kubectl get pods -l <selector> -o wide` |
| Endpoints 为空 | **Selector 与 Pod 标签不匹配** | `kubectl get svc <名> -o jsonpath='{.spec.selector}'` → 对比 `kubectl get pods --show-labels` |
| 全名能通、短名不通 | 跨命名空间了 | 改用 `svc.ns`；检查 resolv.conf search 域 |
| 纯短名突然不通 | dnsPolicy/ndots 被改 | `exec cat /etc/resolv.conf` 看有没有 `<ns>.svc.cluster.local` 第一个 |
| 解析超时/无响应 | CoreDNS 挂了或重启风暴 | `kubectl -n kube-system get pods -l k8s-app=kube-dns`；看 RESTARTS |
| 有的节点通有的不通 | 该节点 kube-proxy 规则缺失/损坏 | 逐节点 `iptables -t nat -L KUBE-SERVICES -n`（第 11 章） |
| 用环境变量拿不到某服务 | **服务比 Pod 晚创建** | 改用 DNS；或重启 Pod |
| 解析到旧 IP | Endpoints 未刷新（极少） | `kubectl get endpointslices -l kubernetes.io/service-name=<svc>` 看 targetRef 新旧 |

### 7.3 完整排查案例（本集群真实链路走一遍）

```bash
# 症状：Pod 里 curl http://nginx-svc/ 不通
# ① Service 在吗？Selector 对吗？
kubectl -n lab get svc nginx-svc -o jsonpath='{.spec.selector}'
#    → map[app:nginx-demo]
# ② 后端端点有吗？
kubectl -n lab get endpoints nginx-svc
#    → 10.42.0.57:80,10.42.0.58:80,...  ← 有 5 个，Selector 命中
# ③ Pod 标签对得上吗？
kubectl -n lab get pods -l app=nginx-demo --show-labels | head
#    → 5/5 Running（第 13 章 selector 匹配）
# ④ DNS 解析呢？
kubectl -n lab exec deploy/nginx-demo -- curl -s -o /dev/null -w "%{http_code}\n" http://nginx-svc.lab.svc.cluster.local/
#    → 200  ← 第 3 层通过
# ⑤ 那问题在数据面：逐节点看规则一致性（第 11 章完整展开）
vagrant ssh k3s-demo-server-1 -- "sudo iptables -t nat -L KUBE-SERVICES -n | grep 10.43.23.169"
vagrant ssh k3s-demo-agent-1  -- "sudo iptables -t nat -L KUBE-SERVICES -n | grep 10.43.23.169"
```

> 排障心法：**从"接口定义"查到"实际执行"**——1→2→3 层是"声明该有的"，4 层是"实际杀人的"。多数"服务不通"死在 2（selector 笔误）和 4（规则不一致）。

### 7.4 常见坑速查

1. **跨 ns 想用纯短名** → 必失败，要用 `svc.ns` 或全名
2. **环境变量拿不到后建服务** → 特性不是 bug，换 DNS
3. **Headless Service 没有 kube-proxy 规则** → 别去 iptables 里找它
4. **rdns 时外部域名被 ndots:5 拖慢** → 每跳一个 search 域都试一次，超时后才是直查；`ndots:1` 可缓解（改 dnsConfig）
5. **Pod 用 `dnsPolicy: Default`** → 直接用节点 resolv.conf，**不走集群 DNS**，服务名解析必失败（除非显式指定）
6. **`options ndots:5` 下写全名仍会先试 search** → 用尾点 `nginx-svc.lab.svc.cluster.local.`(FQDN) 可要求跳过 search（非必须，了解即可）

## 8. Rancher 界面对照

- **服务发现入口**：`Service Discovery` 页签列出所有 Service（含 ClusterIP/DNS 名/Selector）
- **工作负载 → 某服务 → 查看**：能看到关联端点（Pod IP 列表）——即 Endpoints 的 UI 视图
- **命名空间 → 服务**：跨命名空间时从"工作负载"里能直接看到每个服务的完整 DNS 名
- **Ingress**：按域名路由到 Service 名（name-based 转发，就是 DNS + 服务发现的上一层封装）
- **Launch kubectl**：跑"四层排障"整条链路

## 9. 小结

- **问题根源**：Pod IP 易变（coredns 10.42.0.29→0.62 实证）；**方案**：稳定名字 + 实时端点
- **四大件**：Service（VIP）/ CoreDNS（名字→VIP）/ Endpoints-Slices（VIP→Pod 列表）/ kube-proxy（写规则）——全自动对账
- **DNS 命名**：全名 `svc.ns.svc.cluster.local`；短名靠 resolv.conf 的 `search` + `ndots:5`；跨 ns 必须带命名空间
- **后端发现**：Endpoints 控制器 watch selector → 写 Endpoints/EndpointSlices → kube-proxy 重写规则；Selector 笔误 = 端点为空是头号故障
- **两种客户端方式**：DNS（推荐，运行时解析）/ 环境变量（创建时快照，后建服务拿不到）
- **排障四层**：SVC → EP → DNS → 数据面，从上往下逐层验证；多数问题死在 selector 和数据面一致性
- 服务发现被管理面自用（`kubernetes.default.svc` → apiserver），是 K8s 一切互调的地基

1. 在任意 nginx-demo Pod 里 `cat /etc/resolv.conf`，解释三行字段各自作用；再用 `curl` 分别验证全名/带 ns 短名/纯短名三种写法的 HTTP 码。
2. `kubectl get endpoints nginx-svc` 与 `kubectl get endpointslices -l kubernetes.io/service-name=nginx-svc -o wide` 对比，数出端点数量是否一致（应为 5 个），再 `-o yaml` 看一个端点的 `targetRef.uid` 与 Pod 的 `metadata.uid` 是否同值。
3. 排障演练（不破坏集群，只读）：把 `kubectl get svc nginx-svc -o jsonpath='{.spec.selector}'` 的输出和 `kubectl get pods -l app=nginx-demo --show-labels` 对比，说出"如果 Pod 标签多了个 `version:v1` 会怎样"。
4. 用环境变量方式找 nginx-svc：`exec` 进 Pod 跑 `env | grep NGINX_SVC`，对照第 5.1 节输出；再解释"为什么新加一个 Service 后，现存 Pod 里永远找不到它的变量"。
5. 深度题：为什么 `default/kubernetes` Service 的 Endpoints 是 `192.168.56.10:6443` 而不是某个 10.42.0.x 的 Pod IP？它属于哪种 Service（§4.5）？

<details>
<summary>参考答案</summary>

1. `nameserver` = DNS 服务器（kube-dns 10.43.0.10）；`search` = 短名补全候选（同 ns → svc → 集群域）；`ndots:5` = 点数少时先套 search 试。三种写法都应返回 200。
2. 5 个端点两边一致；`targetRef.uid` 与对应 Pod 的 `metadata.uid` 相同（EndpointSlice 就是通过 uid 精确指向 Pod 的）。
3. selector 是严格相等匹配，多一个 `version:v1` 不满足任何 selector 表达式缺失——但若 selector 本身是 `app: nginx-demo` 则**不受影响**（selector 只要包含 Pod 的全部标签就能选中；多了的标签不影响）。若 selector 写了 `version: v1` 而 Pod 没这个标签，端点才会消失。
4. 环境变量是 **Pod 创建时**由 kubelet 注入的"当时存在的 Service 快照"；后建的 Service 不会回溯注入到已运行 Pod——所以拿不到，改用 DNS。
5. 无 selector Service：`default/kubernetes` 不选择任何 Pod，端点是手工/控制器维护的 apiserver 真实地址（节点 IP:6443）。它把"访问集群 API"也变成一次服务发现（§4.5）。
</details>
