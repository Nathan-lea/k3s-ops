# 47 监控告警实战：Prometheus + Grafana + Alertmanager

## 章节信息

| 项目 | 内容 |
|------|------|
| 适用平台 | Linux / macOS（标准路径）；Windows（ops VM 路径，在 ops VM 内执行 kubectl/helm） |
| 前置章节 | 08/10/34/36/46 |
| 预计耗时 | 60-90 分钟 |
| 破坏性操作 | 中：Helm 安装会创建大量 CRD/Workload；资源不足时可能影响现有业务。建议在独立 namespace 并使用实验裁剪值。 |
| 实测环境 | k3s v1.30.2+k3s2，双节点（server-1 2c/4GB + agent-1 2c/4GB），见 [00-README](00-README.md) |

## 本章目标

- 理解 Kubernetes 监控告警的最小闭环：指标采集 → 存储查询 → 可视化 → 告警
- 认识本仓库 `addons/monitoring/values.yaml` 的基线配置与资源风险
- 能为小型实验集群裁剪 kube-prometheus-stack 的安装参数
- 会验证 Prometheus/Grafana/Alertmanager 的关键链路，并知道何时不应强行部署

---

## 1. 监控告警最小闭环

```text
应用/节点/kube-state-metrics/metrics-server
          │
          ▼
     Prometheus 抓取指标（ServiceMonitor/PodMonitor）
          │
          ├──> Grafana 查询展示
          └──> Alertmanager 告警路由（邮件/飞书/Slack/Webhook）
```

与第 08 章的区别：

- **08 章**：单机/单对象视角（probe、events、logs、kubectl top、etcd snapshot）。
- **47 章**：集群级可观测性（时序指标、Dashboard、告警规则、通知）。

## 3. 仓库基线：`addons/monitoring/values.yaml`

仓库现有值文件：

```yaml
grafana:
  adminPassword: admin
  service:
    type: NodePort
    nodePort: 30300
prometheus:
  prometheusSpec:
    retention: 7d
    resources:
      requests:
        memory: 2Gi
    serviceMonitorSelectorNilUsesHelmValues: false
alertmanager:
  enabled: false
```

### 3.1 这份基线的含义

| 字段 | 含义 | 实验环境评价 |
|------|------|-------------|
| `grafana.service.type=NodePort` | Grafana 通过 NodePort 暴露 | 适合实验环境，便于浏览器访问 |
| `grafana.adminPassword=admin` | 固定初始密码 | **仅实验用途**，生产必须改为 Secret/随机密码 |
| `prometheus.prometheusSpec.retention=7d` | 指标保留 7 天 | 小集群可接受，但要看磁盘 |
| `resources.requests.memory=2Gi` | Prometheus 至少申请 2Gi 内存 | 对 4GB 节点偏重，可能调度失败或挤压业务 |
| `serviceMonitorSelectorNilUsesHelmValues=false` | 采集所有 ServiceMonitor（不只 Helm release 自带） | 灵活，但会增加抓取对象，需注意规模 |
| `alertmanager.enabled=false` | 未启用 Alertmanager | 只能看指标，不能发告警 |

### 3.2 ⚠️ 资源风险

当前 server-1 已有 72% 内存占用、94% CPU 占用。若直接按 `requests.memory=2Gi` 部署 Prometheus，常见结果是：

- Pod Pending（节点可分配内存不足）；
- 或勉强调度后导致现有 Rancher/系统组件变慢；
- 抓取/查询时 CPU 再次飙高。

**结论**：教学演示可以部署“裁剪版”；完整 kube-prometheus-stack 应在资源更充足的集群进行。

## 4. 实验裁剪建议（lab profile）

在仓库基线之上，为实验环境创建一个更小的 values（示例：`/tmp/opencode/monitoring-lab-values.yaml` 或你自己的工作目录，不必提交）：

```yaml
grafana:
  adminPassword: admin
  service:
    type: NodePort
    nodePort: 30300
  resources:
    requests:
      cpu: 50m
      memory: 128Mi
    limits:
      cpu: 200m
      memory: 256Mi

prometheus:
  prometheusSpec:
    retention: 2d
    scrapeInterval: 60s
    evaluationInterval: 60s
    resources:
      requests:
        cpu: 200m
        memory: 512Mi
      limits:
        cpu: 1
        memory: 1Gi
    serviceMonitorSelectorNilUsesHelmValues: false
    podMonitorSelectorNilUsesHelmValues: false

alertmanager:
  enabled: true
  alertmanagerSpec:
    resources:
      requests:
        cpu: 20m
        memory: 64Mi
      limits:
        cpu: 100m
        memory: 128Mi

# 小实验集群可关闭部分重组件，按需开启
prometheusOperator:
  resources:
    requests:
      cpu: 50m
      memory: 128Mi
    limits:
      cpu: 200m
      memory: 256Mi

kube-state-metrics:
  resources:
    requests:
      cpu: 20m
      memory: 64Mi

prometheus-node-exporter:
  resources:
    requests:
      cpu: 20m
      memory: 32Mi
```

> 这是**教学裁剪示例**，不是生产推荐。生产应结合节点规模、指标量、保留期、磁盘 IOPS 单独评估。

## 5. 部署步骤（建议在资源充足时执行）

### 5.1 安装前检查

```bash
helm version --short
kubectl get nodes
kubectl top nodes
kubectl get storageclass
kubectl get apiservices | grep metrics
```

实测事实（2026-11-24）：

```text
v3.21.0+ge0878d4
local-path (default)   rancher.io/local-path   Delete   WaitForFirstConsumer   false
v1beta1.metrics.k8s.io  kube-system/metrics-server  True
```

### 5.2 添加仓库并安装

```bash
helm repo add prometheus-community https://prometheus-community.github.io/helm-charts
helm repo update

kubectl create namespace monitoring --dry-run=client -o yaml | kubectl apply -f -

# 实验裁剪版（推荐先用 lab values）
helm upgrade --install kube-prometheus-stack prometheus-community/kube-prometheus-stack \
  -n monitoring \
  -f addons/monitoring/values.yaml
```

如果使用实验裁剪版，把 `-f` 换成你的 lab values 文件。

### 5.3 验收

```bash
kubectl get pods -n monitoring -o wide
kubectl get svc -n monitoring
kubectl get prometheus,alertmanager -n monitoring
kubectl get servicemonitor -n monitoring | head
```

Grafana（仓库基线）：

```text

User: admin
Password: admin   # 仅实验环境；生产不要明文写死
```


## 6. 告警实战：最小可用 Alertmanager

仓库基线中 `alertmanager.enabled=false`。若要演示告警闭环，至少要：

1. 启用 Alertmanager；
2. 保留/配置 PrometheusRule；
3. 给 Alertmanager 配置 receiver（实验可用 webhook/null receiver）。

### 6.1 最小 Alertmanager 配置示例

```yaml
alertmanager:
  enabled: true
  config:
    global:
      resolve_timeout: 5m
    route:
      receiver: "dev-null"
      group_wait: 30s
      group_interval: 5m
      repeat_interval: 2h
    receivers:
      - name: "dev-null"
```

> `dev-null` 适合教学：验证告警产生和路由，不实际发通知。接入飞书/钉钉/Slack/Webhook 时，把 receiver 改成真实配置，并把密钥放 Secret。

### 6.2 验证告警

```bash
kubectl get prometheusrules -n monitoring | head
kubectl -n monitoring port-forward svc/kube-prometheus-stack-alertmanager 9093:9093
# 浏览器访问 http://127.0.0.1:9093
```

在 Prometheus UI 的 **Alerts** 页面查看规则状态：`Inactive` / `Pending` / `Firing`。

## 7. 常见坑与排障

| 现象 | 原因 | 排查 |
|------|------|------|
| Prometheus Pod Pending | `requests.memory` 过大、节点资源不足 | `kubectl describe pod -n monitoring <pod>` 看 Events |
| Grafana 能开但无数据 | Prometheus 未就绪或 datasource 未配置 | 检查 Grafana Data Sources、Prometheus Service |
| NodePort 30300 访问不了 | Service 未创建/节点防火墙/端口冲突 | `kubectl get svc -n monitoring`、节点安全组/iptables |
| 指标缺失 | ServiceMonitor 标签不匹配、target down | Prometheus UI → Status → Targets |
| 告警不触发 | 规则未加载/阈值不满足/Alertmanager 未启用 | Prometheus Rules/Alerts + Alertmanager UI |
| 集群变慢 | 监控栈过重 | `kubectl top nodes/pods -A`，降低 scrape 频率、retention、资源 |

排障命令：

```bash
kubectl get pods -n monitoring
kubectl describe pod -n monitoring <pod-name>
kubectl logs -n monitoring <pod-name> --tail=200
kubectl get events -n monitoring --sort-by=.lastTimestamp | tail -n 30
```

## 8. 与本仓库的关系

- **基线值文件**：`addons/monitoring/values.yaml`。本章建议在其基础上派生实验裁剪值，不要直接把生产密码/大资源请求提交为默认实验配置。
- **运维入口**：安装前后可用 `./k3s-ops.sh status` 看集群健康；资源紧张时先扩容或调整负载（见 46 章）。
- **后续扩展**：日志可接 Loki，追踪可接 Tempo，告警可接 Alertmanager webhook/OnCall。

---

## 9. 小结

- 监控不是“装一个 Prometheus”就结束，要看采集、存储、展示、告警四段闭环。
- 本仓库 `addons/monitoring/values.yaml` 提供了基线，但其中 `memory: 2Gi` 请求对当前小实验集群偏重。
- 部署前先看 `kubectl top nodes` 和节点可分配资源；资源不足时宁可用裁剪版或扩容后再装。
- Alertmanager 是告警闭环的关键；仓库基线默认关闭，教学时可先用 `dev-null` receiver 验证链路。

## 清理

> 若本章创建了监控实验资源，请按以下顺序清理：

```bash
# 卸载 Helm release
helm uninstall kube-prometheus-stack -n monitoring || true

# 删除实验 namespace（确认其中无其他重要资源）
kubectl delete ns monitoring --ignore-not-found

# 若创建了 lab namespace
kubectl delete ns lab --ignore-not-found
```

> 注意：kube-prometheus-stack 会创建 CRD。`helm uninstall` 默认不会删除所有 CRD；如需彻底清理，请先确认这些 CRD 不被其他组件使用，再按官方文档手动删除。
