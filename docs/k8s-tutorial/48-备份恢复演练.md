## 1. 两类备份，别搞混

| 类别 | 内容 | 备份方式 | 恢复粒度 |
|------|------|----------|----------|
| **etcd / 集群状态** | Deployment/Service/ConfigMap/Secret/PV 对象定义、RBAC、节点对象等 | k3s 内置 `k3s etcd-snapshot save` | 整个集群状态回滚到快照时点 |
| **PV / 应用数据** | PVC 里真实写入的文件（数据库、上传文件等） | 拷贝 PV 目录 / Velero / restic | 单个应用的数据卷 |

> ⚠️ 关键事实：**etcd 快照不包含 PV 里的业务数据**。第 05 章讲过 local-path 的 PV 是节点本地目录，etcd 里只存 PVC/PV 的"定义"，不存文件内容。恢复 etcd 不能恢复业务文件。

本章按这个边界分两条线：

- 第 3-4 节：etcd 快照（标准命令 + 项目封装对照），真实执行。
- 第 5 节：PV 数据备份恢复演练，真实执行。
- 第 6 节：etcd 恢复流程与演练策略（**只讲流程和检查清单，不在本集群实跑**）。
- 第 7 节：生产化方案选型（Velero、异地备份）。

## 3. etcd 快照：标准命令（k3s 上游）

### 3.1 创建快照

在 server 节点执行：

```bash
vagrant ssh k3s-demo-server-1 -- \
  "sudo k3s etcd-snapshot save --name ch48-demo"
```

## 4. 项目封装对照：`k3s-ops.sh backup/restore`

> 这一节说明"本项目提供了什么便利入口"，**不是标准做法**。换到别的 k3s 集群，用第 3 节的标准命令即可。

| 你的需求 | 标准命令（通用） | 本项目封装 |
|---------|----------------|-----------|
| 创建快照 | `sudo k3s etcd-snapshot save --name <name>`（server 节点） | `./k3s-ops.sh backup`（宿主机，内部走 `k3s-backup.yml`） |
| 列出快照 | `sudo k3s etcd-snapshot list` | `./k3s-ops.sh status` 会顺带检查快照 |
| 恢复快照 | `sudo k3s server --cluster-reset --cluster-reset-restore-path=<path>`（见第 6 节） | `./k3s-ops.sh restore -f <snapshot_file>`（带确认提示） |

封装脚本实际做的事（`ansible/playbooks/k3s-backup.yml`）：

```yaml
- name: Create etcd snapshot
  command: >
    k3s etcd-snapshot save
    --snapshot-dir={{ k3s_etcd_snapshot_dir }}
```

也就是说，`k3s-ops.sh backup` = **标准命令 + Ansible 多节点编排（建目录、列快照）**。在本仓库里用封装脚本更省事（不用手动 SSH 到 server 节点、不用记路径），但**它不是 k3s 标准操作**，不要把它当通用知识讲给别人。

> 本章后续恢复部分以标准命令为主线讲，项目封装只作为"本仓库便利入口"对照。

## 5. PV / 应用数据备份恢复演练（真实实操）

> 场景：一个 Pod 用 local-path PVC 存数据，误删文件后从备份恢复。全程在 `lab` namespace，可清理。

### 5.1 创建测试工作负载

```bash
cat <<'YAML' | kubectl apply -f -
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: ch48-data
  namespace: lab
spec:
  accessModes: [ReadWriteOnce]
  storageClassName: local-path
  resources:
    requests:
      storage: 128Mi
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: ch48-writer
  namespace: lab
spec:
  replicas: 1
  selector:
    matchLabels:
      app: ch48-writer
  template:
    metadata:
      labels:
        app: ch48-writer
    spec:
      containers:
      - name: writer
        image: busybox:1.36
        command: ["sh", "-c", "sleep 365000"]
        volumeMounts:
        - name: data
          mountPath: /data
      volumes:
      - name: data
        persistentVolumeClaim:
          claimName: ch48-data
YAML

kubectl -n lab rollout status deploy/ch48-writer --timeout=180s
kubectl -n lab get pod -l app=ch48-writer -o wide
```

### 5.3 定位 PVC 对应的节点目录

local-path 的 PV 数据在节点本地目录。先查 PV 名和路径：

```bash
kubectl -n lab get pvc ch48-data -o jsonpath='{.spec.volumeName}{"\n"}'
kubectl get pv <PV名> -o jsonpath='{.spec.local.path}{"\n"}{.spec.nodeAffinity.required.nodeSelectorTerms[0].matchExpressions[0].values[0]}{"\n"}'
```

实测输出：


> 要点：local-path PV 绑定在某个节点上（`k3s-demo-agent-1`），备份必须去**该节点**操作。这也是 local-path 的局限：节点故障会导致数据不可达，生产建议用网络存储或 Longhorn（见第 54 章规划）。

### 5.4 备份数据（在 agent-1 节点上）

```bash

  PV=/var/lib/rancher/k3s/storage/pvc-f5f5edf1-6ce1-44a2-acd4-6d900a8b8afc_lab_ch48-data
  sudo mkdir -p /tmp/ch48-backup
  sudo cp -a "$PV"/. /tmp/ch48-backup/
  sudo ls -la /tmp/ch48-backup
'
```

实测输出：


## 6. etcd 恢复流程（本集群不实跑）

> ⚠️ **不在当前 k3s-demo 集群执行本节命令**。它会停止所有 server、用快照重建 etcd，把集群状态回滚到快照时点——当前集群跑着 Rancher/Kyverno，回滚会丢失快照之后的所有变更。

### 6.1 标准恢复命令（k3s 上游）

在 server 节点执行：

```bash
sudo systemctl stop k3s

# 用快照恢复（把 <快照名> 换成实际名称）
sudo k3s server \
  --cluster-reset \
  --cluster-reset-restore-path=/var/lib/rancher/k3s/server/db/snapshots/<快照名>

sudo systemctl start k3s
```

官方文档：https://docs.k3s.io/datastore/backup-restore

### 6.2 恢复前检查清单

1. **确认快照来源可信**：是从当前集群打的、校验过文件完整性的快照，不是来路不明的文件。
2. **先给当前状态再打一个快照**：`k3s etcd-snapshot save --name before-restore`，万一恢复选错快照还能回退。
3. **确认快照时点**：快照之后创建的资源会丢失，评估业务影响。
4. **维护窗口**：恢复期间 API 不可用，通知使用者。
5. **多 server 场景**：所有 server 都要处理，按官方文档逐个成员恢复；单 server（本环境）最简单。
6. **PV 数据另算**：etcd 恢复不恢复 PV 文件，业务数据要靠第 5 节的方式单独恢复。

### 6.3 项目封装对照（不执行）

```bash
# 本仓库封装入口：带交互确认，内部走 k3s-restore.yml
./k3s-ops.sh restore -f <snapshot_file>
```

它会先提示 `This will stop all server nodes and restart the cluster!` 并要求输入 `y/N` 确认。底层 playbook 做的事：停所有 server → 校验快照文件存在 → 在第一台 server 上跑 `--cluster-reset` → 启动第一台 server → 等 API 端口 6443 → 启动其余 server → 重启所有 agent。

### 6.4 恢复后验收

```bash
kubectl get nodes
kubectl get ns
kubectl get pods -A
kubectl get events -A --sort-by=.lastTimestamp | tail -n 30
./k3s-ops.sh status
```

核对：节点 Ready、关键 namespace 和 Pod 回到快照时点、Rancher/Ingress/Gateway 可用、PVC 绑定关系正确。必要时重启相关 Pod（apiserver 证书/token 与快照时点不一致时，kubelet 会逐渐自愈）。

## 7. 生产化方案选型

| 方案 | 覆盖 | 优点 | 局限 / 注意 |
|------|------|------|------------|
| `k3s etcd-snapshot` + cron | etcd | k3s 自带，零依赖；配合 `etcd-snapshot-cron.sh` 易自动化 | 快照留本机，需手动拷走；不含 PV 数据 |
| 拷贝 PV 目录 / rsync | PV 数据 | 简单直接，本章已演示 | 需逐卷处理；local-path 节点绑定；一致性要靠应用配合（停写/快照） |
| **Velero** | etcd + PV | Kubernetes 生态标准备份工具，支持 PVC 快照、命名空间级恢复、对象存储 | 需部署 server + node-agent；本章资源紧张未安装；生产推荐 |
| restic / Kopia | PV 数据 | 去重加密、增量备份、支持对象存储 | 需自行编排调度与恢复流程 |
| 存储层快照（Longhorn / 云盘快照） | PV 数据 | 块级一致性好，恢复快 | 依赖底层存储支持 |

### 7.1 定期备份与异地归档

一个最小可行策略：

1. **etcd**：`etcd-snapshot-cron.sh` 每天定时打快照，保留 7 天；另外用脚本把最新快照 `scp` 到另一台机器或对象存储。
2. **PV**：对关键 PVC 用 Velero 或定时任务备份到对象存储。
3. **演练**：每季度做一次恢复演练（像本章第 5 节那样），验证备份真的可用。

> ⚠️ 备份不等于可恢复。**只有做过恢复演练的备份才算数**。

## 8. 排障清单

| 现象 | 原因 | 排查 |
|------|------|------|
| 快照命令报 `Unknown flag ... skipping` | 无害噪音（子命令不识别 server 参数） | 认准 `Snapshot ... saved.` 即可 |
| 快照列表看不到新快照 | 打在了另一台 server 上 / 目录不对 | `k3s etcd-snapshot list` 在对应 server 执行；检查 `--snapshot-dir` |
| PV 目录找不到 | local-path PV 绑在别的节点 | 用 `kubectl get pv -o jsonpath` 查 `.spec.local.path` 和节点亲和 |
| 恢复后 Pod 起不来 | apiserver 证书/token 与快照时点不一致 | 等待 kubelet 自愈或重启相关 Pod |
| 恢复后业务数据没回来 | 混淆了 etcd 与 PV 备份 | etcd 不含 PV 文件，需单独恢复 PV（第 5 节） |

## 9. Rancher / kubectl 对照

- **etcd 快照**：Rancher 集群管理界面有 etcd 备份/恢复入口（与 `k3s etcd-snapshot` 等价），但命令行更透明、可脚本化。
- **PV / PVC**：Rancher → Cluster → Volumes / PersistentVolumeClaims 可查看绑定关系；真实数据在节点目录，UI 看不到文件内容。
- **恢复验证**：Rancher Workloads 页面看 Pod 状态；CLI 用 `kubectl get pods -A` + `events` 更全面。

---

## 10. 小结

- 备份分两类：**etcd 快照（集群状态）** 和 **PV 数据（业务文件）**，恢复时都要考虑。
- 标准命令是 `k3s etcd-snapshot save/list/prune/delete` 与 `k3s server --cluster-reset`；`k3s-ops.sh backup/restore` 只是本项目的封装入口，不是通用知识。
- etcd 恢复是破坏性操作：先备份当前状态、确认快照时点、维护窗口内执行、恢复后逐项验收。本章不在运行中的集群实跑。
- PV 数据可以用"拷贝节点目录"做轻量备份恢复演练；生产推荐 Velero / 对象存储 / 存储层快照。
- **做过恢复演练的备份才算数**。

<summary>参考答案要点</summary>

5. 例如"先给当前状态再打一个快照"和"确认快照时点"容易被忽略；选错快照或没有回退点会导致恢复后丢失更多数据，且不可逆。
