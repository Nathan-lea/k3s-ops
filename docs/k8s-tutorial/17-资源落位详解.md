# 17 资源落位详解：跨节点、依附关系与存亡规律

## 本章目标

- 建立**三世界模型**：定义世界（etcd）／运行世界（节点）／逻辑世界（命名空间），看透每个对象"到底存在于哪"
- 分清"**跨节点**"的三个层次：逻辑跨节点、物理每节点一份、数据单节点
- 分清"**依附**"的两种机制：ownerReferences（归属，级联删除）vs selector/引用（认领，互不影响）
- 学会用"资源落位"规律派生的排障口诀与操作流程（drain 维护、网络排查、备份恢复）
- 用本集群真实的"负载全堆 server-1"案例验证规律

> 前置：建议先完成 03（工作负载）、04（网络）、06（调度）、13（Label）、15（资源定义文件——本章第 6 节是其速查版）。
> 本章所有输出均为本集群真实采集。

## 1. 三世界模型：每个 K8s 对象到底"存在"在哪里

K8s 里所有东西都是对象（第 15 章），但"存在"有三种完全不同的含义。看一个对象时，先问它属于哪个世界：

```
世界① 定义世界（API / etcd）
  对象 = 一段数据（JSON/YAML），躺在控制面 etcd 里
  └── 几乎一切对象本身都在这里：Deployment、Service、ConfigMap、RBAC、PV、CRD...

世界② 运行世界（节点）
  对象 = 真实进程 / 数据文件，占一台具体节点的 CPU/内存/磁盘
  └── Pod（的容器）、kubelet、containerd、flannel、PV 背后的磁盘数据、etcd 快照文件

世界③ 逻辑世界（命名空间）
  对象 = 逻辑归属/配额约束，只存在于 API 语义，无实体
  └── Namespace 本身、ResourceQuota、LimitRange、PDB（配额类）
```

**唯一"物理存在"的资源形态是 Pod（的容器）**——这条是本章最核心的洞见：

```bash
kubectl get pods -A -o wide        # 只有 Pod 有 IP 和 NODE 列
kubectl get deploy -A -o wide      # Deployment 没有 IP/NODE——它不跑在任何地方
```

真实对比（本集群）：

```text
# pods -A -o wide（真实跑在节点上）
NAMESPACE     NAME                         READY  ...  IP          NODE
kube-system   coredns-576bfc4dc7-c5j4q     1/1       10.42.0.29  k3s-demo-server-1
kube-system   metrics-server-557ff575fb-... 1/1       10.42.0.45  k3s-demo-server-1
ingress-nginx ingress-nginx-controller-...  1/1       10.42.0.36  k3s-demo-server-1

# deploy -A（只存在于 etcd 的声明）
NAMESPACE   NAME      READY   UP-TO-DATE   AVAILABLE   AGE
lab         nginx-demo 5/5    5            5           2d
```

> Deployment 显示 5/5"就绪"，但就绪的是它**派生的 Pod**——声明本身只是 etcd 里的一条数据。这也是"删 Deployment 一切消失、删 Pod 会被重建"的根源：**Pod 是活的（运行世界），Deployment 是死的（定义世界），死的指挥活的。**

### 1.1 每个世界对应的排查工具

| 世界 | 想"看"它用什么 | 本环境例子 |
|------|---------------|-----------|
| 定义世界 | `kubectl get xxx -o yaml/json`、`kubectl explain` | `kubectl get deploy nginx-demo -o yaml` |
| 运行世界 | `kubectl get pods -o wide`、`kubectl top`、`exec`、节点上 `ps`/`ss`/`iptables` | `kubectl top nodes` |
| 逻辑世界 | `kubectl get ns`、`kubectl get resourcequota -n lab` | `kubectl get ns lab` |

## 2. 哪些资源"跨节点"：三个层次必须分清

"跨节点"在 K8s 语境里有三种截然不同的含义，混用是排障最大的坑：

### 2.1 层次一：逻辑上跨节点（所有节点都能用/都可见）

这些资源是**全局的"知识"**：任何节点上的任何 Pod 都能访问它，但它本身不占任何节点：

| 资源 | 为什么"跨节点" | 本环境实测 |
|------|---------------|-----------|
| Service（ClusterIP） | 虚拟 IP 在整个集群网络内可达（第 11 章详解了它怎么变成各节点的规则） | `nginx-svc` ClusterIP `10.43.23.169`，agent-1 上的 Pod 也能访问 |
| PV | 集群级对象（NAMESPACED=false），任何 PVC 都能申请绑定 | `pvc-6172...` 1Gi RWO |
| StorageClass | 全局模板，任何 PVC 可指名 | `local-path`（默认） |
| ClusterRole / ClusterRoleBinding | 全局权限 | `system:basic-user` |
| IngressClass / PriorityClass / RuntimeClass / CRD | 全局定义 | `nginx`（IngressClass） |
| Namespace 本身 | 全局存在（它只是"文件夹"） | `lab` |

### 2.2 层次二：物理上每节点各一份（规则/进程在每个节点都有副本）

这类**在每个节点上都真实存在**，节点之间内容可能一样（副本），但不共享：

| 组件 | 每节点有什么 | 本环境实测 |
|------|-------------|-----------|
| **kubelet / containerd** | 守护进程（k3s 的 agent/server 会各自拉起） | server-1、agent-1 都有 |
| **CNI（flannel）** | 网络插件进程 + vxlan 接口（`flannel.1`）+ 路由规则 | 两节点都有（第 04 章） |
| **kube-proxy 的 iptables 规则** | `KUBE-SVC-*`/`KUBE-SEP-*` 链**每个节点各一份** | 第 11 章实测：两节点都有同样的链 |
| kube-dns（CoreDNS）的解析服务 | 以 Pod 方式部署，通常只在一处，但 Service 让所有节点可用 | coredns Pod 在 server-1，agent-1 的 Pod 也能解析 |

> **排障启发**：Service 不通时，iptables 链只查一个节点可能被误导——**每个节点各有一份**，可能出现"某节点规则损坏/不一致"导致"有的节点通、有的不通"。第 11 章的链是 server-1 的，agent-1 应当同构（可自行验证）。

### 2.3 层次三：数据只存在单一节点（"跨节点可用"是假象）

这是**最容易被误解**的一类：资源在 API 里是集群级，但**数据物理上只在一台节点**：

| 资源 | 数据在哪 | 怎么确认 | 本环境实测 |
|------|---------|---------|-----------|
| **local-path PV** | 绑定节点的磁盘目录（`/var/lib/rancher/k3s/storage/`） | `.spec.nodeAffinity` 的 hostname 表达式 | `pvc-6172...` → `In [k3s-demo-server-1]` |
| **etcd 快照文件** | server 节点的 `/var/lib/rancher/k3s/server/db/snapshots/` | ssh 进节点 find | `chapter12-demo-k3s-demo-server-1-1791077283` |
| **HostPath / emptyDir** | 所在 Pod 的节点（emptyDir 生命周期同 Pod） | 看 Pod NODE 列 | 无（教程未用） |
| **容器文件系统** | 所在 Pod 的节点（容器层） | 看 Pod NODE 列 | nginx-demo 容器数据在 server-1 |
| **k3s 数据目录** | server 节点 `/var/lib/rancher/k3s/`（含 etcd） | 架构（第 02 章） | server-1 |

**实测证据**（local-path 的"跨节点假象"）：

```bash
# PV 的 nodeAffinity 明文写死数据节点
kubectl get pv pvc-61720575-6d78-4437-8d50-553a7b4c8fc8 \
  -o jsonpath='{.spec.nodeAffinity}'

# 输出: {"required":{"nodeSelectorTerms":[{"matchExpressions":[
#   {"key":"kubernetes.io/hostname","operator":"In","values":["k3s-demo-server-1"]}]}]}}

# PVC 侧也有 selected-node 注解
kubectl -n lab get pvc nginx-data -o jsonpath='{.metadata.annotations.volume\.kubernetes\.io/selected-node}'
# 输出: k3s-demo-server-1
```

> **血的教训**：local-path（或任何"节点本地存储"）的 PV 是集群级对象，但**数据绑死一台节点**。如果 server-1 故障：
> - 状态：PV 数据跟着 server-1 走，PVC 无法在其他节点重新绑定
> - 对策：要么用真正跨节点的存储（NFS/Ceph/云盘），要么做备份恢复（第 08/12 章）
> - 更隐蔽的坑：`emptyDir` 也要注意——它在 Pod 所在节点，删 Pod 数据即毁

## 3. 哪些资源"依附"其他资源：两种机制必须分清

"附着/依赖"有两种截然不同的底层机制，决定了删除时的行为天差地别：

### 3.1 ownerReferences（归属）：父生子，级联删除

子资源有 `metadata.ownerReferences` 指向父资源（第 15 章 §6.1）。删除父 → 垃圾回收器（GC）级联删子：

| 链 | 例子（本环境实测） | 删父后果 |
|----|-------------------|---------|
| Deployment → ReplicaSet → Pod | `nginx-demo` → `nginx-demo-7fb649d588` → 5 个 Pod | Pod/RS 全消失 |
| Job → Pod | fleet 的 clean 任务 | Job 删除时 Pod 一起删 |
| Service → Endpoints | `nginx-svc` → `nginx-svc`（同名 Endpoints） | 删 Service，Endpoints 随之消失 |

```bash
# 实测：删掉 Deployment 后 Pod 跟着没
kubectl -n lab get pod nginx-demo-7fb649d588-6m4xl \
  -o jsonpath='{.metadata.ownerReferences[0].kind}:{.metadata.ownerReferences[0].name}'
# 输出: ReplicaSet:nginx-demo-7fb649d588
```

### 3.2 selector / 引用（认领）：指向但不归属，互不影响

资源通过**标签/名字**"指"向另一资源，但**没有所有权**：

| 关系 | 机制 | 删掉"被指"的资源时 |
|------|------|-------------------|
| Service.selector → Pod | label 认领 | 删 Pod → Service 自动摘端点（Endpoints 更新），Service 本身没事 |
| Deployment 引用 ConfigMap/Secret | envFrom/volume 按名字引用 | 删 CM/Secret → **不删 Pod**，运行中的 Pod 继续用旧值；新建/重启的 Pod 才可能失败 |
| PVC → StorageClass | storageClassName 指名 | 删 SC → 不影响已绑定 PVC（已绑定的绑死了） |
| PVC ↔ PV | 绑定（claimRef / volumeName） | 删 PVC → 按 PV 的 **reclaimPolicy** 决定：`Delete`（连带删 PV+数据）/ `Retain`（PV 保留数据） |

```bash
# 实测 Service 与 Pod 只是"认领"：删 Pod 后端点自动摘除
kubectl -n lab get svc nginx-svc -o jsonpath='{.spec.selector}'
# 输出: map[app:nginx-demo]        ← 它只是写"我要 app=nginx-demo 的 Pod"
kubectl -n lab get endpoints nginx-svc -o jsonpath='{.subsets[0].addresses[*].ip}'
# 输出: 10.42.0.28 10.42.0.31 ...   ← 由控制面根据 selector 自动维护
```

### 3.3 一张图画清"归属 vs 引用"

```
Deployment ──owner──▶ ReplicaSet ──owner──▶ Pod        【归属】删父全删（级联）
    └── envFrom 引用 ──▶ ConfigMap                     【引用】删 CM 不影响进行中 Pod
Service ──selector──▶ (app=nginx-demo)──▶ Pod          【认领】删 Pod 自动摘端点
PVC ──volumeName/bind──▶ PV ──nodeAffinity──▶ 单节点磁盘 【绑定】删 PVC 看 reclaimPolicy
```

## 4. 各资源"实际落位"总表（按"跑不跑"归类）

### 4.1 A 类：只在 etcd，从不跑在任何节点（定义型）

| 资源 | 落位 | 备注 |
|------|------|------|
| Deployment/RS/STS/DS/Job/CronJob | etcd（只存声明） | 它们的"手"（Pod）才跑在节点 |
| Service/Ingress/Endpoints | etcd | 但 **kube-proxy 把 Service/Endpoints 翻译成各节点 iptables**（第 11 章） |
| ConfigMap/Secret | etcd | 只在被 Pod 挂载/引用时"进入节点"（成卷/环境变量） |
| PVC/PV/StorageClass | etcd | **PV 数据在节点**，PV 对象在 etcd（§2.3） |
| RBAC（Role/CR/RB/CRB）、ServiceAccount | etcd | 纯逻辑 |
| Namespace/ResourceQuota/LimitRange/PDB | etcd | 纯逻辑 |
| CRD | etcd | 定义扩展 API 类型 |

### 4.2 B 类：真正跑在节点上的（运行型）

| 资源 | 落在哪 | 谁决定 | 本环境实测 |
|------|--------|--------|-----------|
| 用户 Pod | 调度器（nodeSelector/亲和/污点/资源/拓扑） | scheduler | nginx-demo 5 副本全在 server-1（nodeSelector 钉死） |
| 系统 Pod（CoreDNS/metrics-server/ingress-controller） | 调度器 | scheduler | **全在 server-1**（k3s 把控制面组件当 Pod 放 server） |
| 每节点的守护进程（kubelet/containerd/flannel/kube-proxy） | **每个节点必有** | k3s agent/server 进程 | server-1、agent-1 都有 |
| k3s server 进程（api/etcd/scheduler/controller-manager） | 只跑在 server 节点 | 架构设计 | server-1（嵌入式 etcd） |
| PV 物理数据 | nodeAffinity 指定的节点 | 存储插件 + 调度 | local-path PV → server-1 |

### 4.3 本集群真实落位图（强烈建议自己跑一遍）

```bash
kubectl get pods -A -o wide | awk '{print $8}' | sort | uniq -c   # 每节点 Pod 数
```

本集群实测（**负载全堆 server-1 的绝佳案例**）：

```text
k3s-demo-agent-1    1      ← 只有 sched-demo（第 06 章 nodeSelector 指向 agent-1 的实验）
k3s-demo-server-1   15+    ← 几乎全部用户负载 + 全部系统组件
```

为什么？本集群设计是：**server 无污点（taint_server: false）+ 教程实验加 nodeSelector 钉 server-1**。这正好演示：

> **没写 nodeSelector/亲和时**，调度器综合考虑污点、资源余量、亲和/反亲和、拓扑分布，把 Pod 放"最合适"的节点；
> **写了 nodeSelector（如 `kubernetes.io/hostname: k3s-demo-server-1`）**，调度器被钉死，只能放那台；
> **节点有污点（NoSchedule）**，无对应容忍的 Pod 一律调度不过去（第 06 章）。

## 5. 排障与应用：落位规律怎么帮到实际工作

### 5.1 排障"四问"定位法（对应四类现象）

| 现象 | 第一问 | 命令 |
|------|--------|------|
| Pod 卡 Pending（起不来） | **它想落在哪个节点？** | `kubectl get pod -o wide`（NODE 空 = 没调度成功）；`kubectl describe pod` 看 FailedScheduling 事件 |
| 服务偶尔通偶尔不通 | **规则在哪些节点各有一份？** | `kubectl get ep nginx-svc`；逐节点验证 iptables（第 11 章） |
| 数据"消失"或读不到 | **数据在哪个节点磁盘上？** | `kubectl get pv -o jsonpath='{.spec.nodeAffinity}'`；`kubectl get pvc -o jsonpath='{.metadata.annotations.volume\.kubernetes\.io/selected-node}'` |
| 删了资源还报错/还留着 | **归属还是引用？** | `kubectl get <obj> -o jsonpath='{.metadata.ownerReferences}'`；看 finalizer（第 15 章 §6.4） |

### 5.2 节点维护（drain/cordon）——落位规律直接应用

```
kubectl cordon <node>                              # 标记不再接收新 Pod（已有不动）
kubectl drain <node> --ignore-daemonsets \
  --delete-emptydir-data                            # 驱逐该节点所有 Pod（重新调度到别处）
kubectl uncordon <node>                             # 维护完恢复
```

**必须知道的落位真相**：

1. **drain 会驱逐 Pod**：有 ownerReferences 的（Deployment 管的）会在其他节点重建；**无主 Pod（裸 Pod）会被删掉不重建**
2. **本地盘数据不走**：local-path PV/emptyDir 的数据在节点磁盘上，**不会跟着 Pod 迁移**——drain 前先备份（第 08 章快照）
3. **DaemonSet 必须 `--ignore-daemonsets`**：DS 特性就是每节点一个，drain 驱逐不掉
4. **PDB（PodDisruptionBudget）会阻止 drain**：若某应用 PDB 要求 minAvailable，drain 会拒绝执行，先调 PDB 或分批

### 5.3 备份与恢复——"定义"和"数据"分开处理

| 要备份什么 | 在哪备份 | 方式 |
|-----------|---------|------|
| 定义型资源（Deployment/SVC/CM/Secret/...） | etcd / API | `kubectl get xxx -A -o yaml > backup.yaml`；或 etcd 快照（第 12 章） |
| 运行数据（容器内、本地盘 PV） | 节点磁盘 | 进容器 tar、PV 目录快照、应用自带导出 |
| 集群元数据（认证/RBAC/CRD） | etcd | `k3s etcd-snapshot save`（第 12 章全流程） |

> **分工原理**：etcd 里**没有**容器文件系统和本地盘数据——它们在运行世界（节点）；只备份 etcd 不等于全部恢复。

### 5.4 常见误解澄清表

| 误解 | 真相 |
|------|------|
| "PV 是集群级资源，所以数据跨节点" | PV 对象集群级，**数据被 nodeAffinity 绑死单节点**（local-path 尤其明显） |
| "Service 在每个节点都"有"" | Service 是 etcd 数据；是它的 **iptables 规则**在每节点各一份 |
| "删 ConfigMap 会重启引用它的 Pod" | **不会**。运行中的 Pod 继续用旧配置；只有新建/重启才读不到 |
| "节点宕机，数据会漂移" | **不会**。kubelet 会重调度 Pod，但本地盘数据永远留在原节点 |
| "drain 节点等于数据也搬走" | 只搬"可重建的 Pod"，**不搬本地数据** |

## 7. Rancher 界面对照

- **工作负载列表**：每行可展开看 Pod 落在哪个节点（Node 列）——即"运行世界"视图
- **节点页面（Cluster → Nodes）**：看每节点容量/污点/其上工作负载——维护前的第一眼
- **存储 → PVs**：点开 PV 能有 Claims 与节点的绑定关系（local-path 场景显示绑定的节点）
- **存储 → PVCs → 某 PVC → Volume**：能看到绑定的 PV——"绑定关系"的 UI 表现
- **工作负载 → 某应用 → 编辑**：nodeSelector/亲和/污点容忍就在那里改——改完就是"落位规则"变了
- 排障联动：Rancher 的 **Launch kubectl** 可跑本章全部命令

## 8. 小结

- **三世界**：定义（etcd 数据）、运行（节点进程）、逻辑（命名空间语义）；**唯一物理存在是 Pod 的容器**
- **跨节点三层**：逻辑可用（ClusterIP/PV/RBAC）≠ 每节点一份（iptables/CNI/kubelet）≠ 数据单节点（local-path PV/etcd 快照）
- **依附两种**：ownerReferences 归属 = 级联删除；selector/引用 = 互不影响
- **落位决定权**：Pod 落哪个节点由调度器决定（nodeSelector/亲和/污点/资源），没写就是"调度器自由发挥"
- **排障四问**：Pending→NODE 列；时通时断→每节点规则；数据丢→nodeAffinity；删不掉→ownerRef/finalizer
- 本集群案例：负载全堆 server-1 正是"落位规律"的活教材

## 动手练习

1. 跑 `kubectl get pods -A -o wide`，数一下每个节点各有多少 Pod；找出 1~2 个系统组件（如 coredns）所在节点。
2. 用 `kubectl get pv -o wide` 和 `kubectl get pvc -n lab -o wide` 找出 `nginx-data` 绑定的 PV 名，再用 `-o jsonpath='{.spec.nodeAffinity}'` 确认数据在哪台节点。
3. 给 lab 建一个不带 nodeSelector 的测试 Deployment（如 `nginx-test`），观察调度器把它放哪台节点；再加 `nodeSelector: {kubernetes.io/hostname: k3s-demo-agent-1}` 再观察（⚠️ 完成后删除）。
4. 实验"引用不带删"：`kubectl -n lab delete cm app-config`（先备份 YAML），观察 nginx-demo 的 Pod **不受影响继续 Running**；再用备份恢复它（apply）。
5. 深度：解释题——为什么 `kubectl delete deploy nginx-demo` 会把 5 个 Pod 一起删掉，而 `kubectl delete cm app-config` 不会？（提示：看 Pod 的 ownerReferences）

<details>
<summary>参考答案</summary>

1. 本集群当前几乎全部 Pod 在 `k3s-demo-server-1`（coredns/metrics-server/ingress-controller 都在 server-1），agent-1 通常只有教程实验的 sched-demo。原因：server 无污点 + 实验 nodeSelector 钉 server-1。
2. `pvc-61720575-6d78-4437-8d50-553a7b4c8fc8`；nodeAffinity 为 `kubernetes.io/hostname In [k3s-demo-server-1]`——数据在 server-1 磁盘。
3. 不带 nodeSelector 时调度器可能把它放 agent-1（资源更空）；加了 hostname=agent-1 后必然落 agent-1。这直接演示"落位规则由 spec 决定"。
4. 删除 app-config 后，运行中的 nginx-demo Pod 状态不变（配置已在容器内/启动时注入）；新建或重启 Pod 才会因找不到 CM 失败。恢复用 `kubectl apply -f backup.yaml`。
5. Pod 的 `metadata.ownerReferences` 指向 RS（→ Deployment），GC 随父删除级联清理；而 CM 只是被 Pod **按名引用**，Pod 的 ownerReferences 里没有 ConfigMap，所以互不影响。
