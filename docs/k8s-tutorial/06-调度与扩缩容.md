# 06 调度与扩缩容：把 Pod 放到哪、放多少

## 本章目标

- 理解调度器（kube-scheduler）的工作流程：过滤 → 打分 → 绑定
- 掌握调度控制手段：nodeSelector、节点标签、污点/容忍、亲和性
- 理解资源请求/限制（requests/limits）与 QoS
- 掌握手动扩缩容（scale）与自动扩缩容（HPA）

---

## 1. 调度的本质

新 Pod 创建后处于 `Pending`，直到**调度器**为它选定一个节点并写回绑定记录，该节点上的 kubelet 才开始创建容器。

```text
Pod 创建(Pending)
   │
   ▼
kube-scheduler 过滤（Filtering）：
   ├─ 节点健康？资源够不够？（requests）
   ├─ nodeSelector 匹配？
   ├─ 污点是否可容忍（Taints/Tolerations）
   ├─ 亲和性规则？
   │
   ▼ 通过过滤的候选节点
打分（Scoring）：按资源均衡、亲和性等打分
   │
   ▼
选最高分节点 → 绑定（Binding）→ 写回 etcd
   │
   ▼
该节点 kubelet 收到「分给我的 Pod」→ 启动容器
```

**关键认知**：调度只决定「放哪台机器」，真正干活的是 kubelet。

## 2. 调度控制手段

| 手段 | 作用 | 例子 |
|------|------|------|
| **nodeSelector** | 最简单的硬性约束：匹配节点标签 | `disktype: ssd` |
| **节点标签** | 给节点打标（架构、存储类型、环境） | `kubectl label node ...` |
| **污点（Taint）+ 容忍（Toleration）** | 节点主动「拒绝」Pod；Pod 声明「我能忍」才能上去 | 专用节点、隔离 |
| **亲和性（nodeAffinity / podAffinity）** | 更复杂的软/硬规则 | Pod 尽量靠近另一个 Pod |
| **资源 requests/limits** | 调度时的资源门槛 + 运行时的上限 | `cpu: 100m` |

> 本集群设计决策：server 节点 `taint_server: false`（无污点），所以业务 Pod 也能调度到 server 节点 —— 小集群把控制面节点也利用起来。

## 3. 扩缩容手段

| 方式 | 命令/资源 | 适用 |
|------|-----------|------|
| 手动 | `kubectl scale deployment <名字> --replicas=N` | 人工决策 |
| 自动 | **HPA**（HorizontalPodAutoscaler）按 CPU/内存/自定义指标自动调副本数 | 负载波动 |
| 预期副本 | Deployment 中 `spec.replicas` 写死 | 固定规模 |

HPA 工作前提：**metrics-server** 提供指标（本集群已装），Deployment 的容器必须声明 `resources.requests`（HPA 按「实际用量 / request」算百分比）。

## 4. 本集群实站对照

### 4.1 查看节点标签与污点

```bash
kubectl get nodes --show-labels
```

预期输出（节选，注意 server 有 control-plane 角色标签）：

```text
NAME                STATUS   ROLES                       AGE    VERSION   LABELS
k3s-demo-agent-1    Ready    <none>                      123d   v1.30.2  ...kubernetes.io/hostname=k3s-demo-agent-1,...
k3s-demo-server-1   Ready    control-plane,etcd,master   130d   v1.30.2  ...node-role.kubernetes.io/control-plane=true,node-role.kubernetes.io/etcd=true,...
```

```bash
kubectl get nodes -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.spec.taints}{"\n"}{end}'
```

预期输出（本环境两个节点都**没有**污点）：

```text
k3s-demo-agent-1
k3s-demo-server-1
```

空 = 无污点。这就是小集群「server 也能跑业务」的机制。

### 4.2 给节点打自定义标签（磁盘类型示例）

```bash
kubectl label node k3s-demo-server-1 disktype=ssd
kubectl label node k3s-demo-agent-1 disktype=hdd
kubectl get nodes -L disktype
```

预期输出：

```text
NAME                STATUS   ROLES                       AGE    VERSION   DISKTYPE
k3s-demo-agent-1    Ready    <none>                      123d   v1.30.2   hdd
k3s-demo-server-1   Ready    control-plane,etcd,master   130d   v1.30.2   ssd
```

> 这是官方文档最爱用的示例：用标签把节点按存储类型分组，调度时按需选择。做完实验可删标签：`kubectl label node k3s-demo-server-1 disktype-`（`-` 后缀=删除）。

### 4.3 nodeSelector：把 Pod 指定到 hdd 节点

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: sched-demo
  namespace: lab
spec:
  replicas: 2
  selector:
    matchLabels: { app: sched-demo }
  template:
    metadata:
      labels: { app: sched-demo }
    spec:
      nodeSelector:
        disktype: hdd          # 只有带 hdd 标签的节点才会被选中
      containers:
        - name: nginx
          image: nginx:latest
          imagePullPolicy: IfNotPresent
          resources:
            requests: { cpu: 100m, memory: 64Mi }
            limits:   { cpu: 200m, memory: 128Mi }
```

```bash
kubectl apply -f sched-demo.yaml
kubectl -n lab get pods -o wide | grep sched-demo
```

预期输出（Pod 都落在 agent-1 —— 只有它带 `hdd` 标签）：

```text
sched-demo-54bcb66757-42bjv   0/1   ContainerCreating   0   5s   <none>   k3s-demo-agent-1   <none>
sched-demo-54bcb66757-zs9t6   0/1   ContainerCreating   0   5s   <none>   k3s-demo-agent-1   <none>
```

```bash
kubectl -n lab describe pod -l app=sched-demo | grep -E 'Node:'
```

预期输出：

```text
Node:             k3s-demo-agent-1/192.168.56.20
Node:             k3s-demo-agent-1/192.168.56.20
```

> ⚠️ 离线环境注意：`ContainerCreating` 时间较长是镜像拉取慢，不是调度问题 —— 调度已经完成了（NODE 列已填），拉镜像由 kubelet 负责。

### 4.4 手动扩缩容（回顾第 03 章）

```bash
kubectl -n lab scale deploy sched-demo --replicas=4
kubectl -n lab get deploy sched-demo        # 看 READY/AVAILABLE 变化
kubectl -n lab scale deploy sched-demo --replicas=2   # 再缩回
```

### 4.5 自动扩缩容 HPA

前提：容器必须声明 `requests.cpu`（上面 YAML 已声明 `100m`）。

```bash
kubectl -n lab autoscale deployment sched-demo --cpu-percent=50 --min=2 --max=6
```

预期输出：

```text
horizontalpodautoscaler.autoscaling/sched-demo autoscaled
```

```bash
kubectl -n lab get hpa
```

预期输出（**Pod 未就绪时的真实状态** —— TARGETS 显示 `<unknown>`）：

```text
NAME         REFERENCE               TARGETS              MINPODS   MAXPODS   REPLICAS   AGE
sched-demo   Deployment/sched-demo   cpu: <unknown>/50%   2         2         2          5s
```

`<unknown>` 的含义与原因：HPA 拿不到 CPU 指标，常见原因：

1. Pod 还没 Ready（未就绪就没有指标采集）
2. metrics-server 没装/不健康
3. 容器没声明 `resources.requests`

等 Pod Ready 后 `describe hpa` 能看到指标变为数字：

```bash
kubectl -n lab describe hpa sched-demo
```

预期输出（节选）：

```text
Metrics:                                               ( current / target )
  resource cpu on pods  (as a percentage of request):  <unknown> / 50%
Min replicas:                                          2
Max replicas:                                          6
Deployment pods:                                       2 current / 2 desired
Conditions:
  Type            Status  Reason            Message
  AbleToScale     True    SucceededRescale  the HPA controller was able to update...
  ScalingActive   False   FailedGetResourceMetric  the HPA controller was unable to get...
```

`ScalingActive: False + FailedGetResourceMetric` = 拿不到指标。排障顺序：查 metrics-server → 查 Pod Ready → 查 resources 声明。

## 5. Rancher 界面对照

Rancher → 集群 → **Nodes**：点节点可看标签（Labels）、污点（Taints），可直接编辑。
Rancher → 集群 → **Workload → Deployments** → 某应用 → **⋮ → Edit**：可改 replicas（手动扩缩）。
Rancher → 集群 → **Service Discovery → Workloads 页面右侧**：可配置 HorizontalPodAutoscaler（需要先给容器配 resources）。

## 6. 小结

- 调度 = 过滤（硬约束）→ 打分（软偏好）→ 绑定；kubelet 才是干活的
- 常用约束：nodeSelector（标签）、污点/容忍（拒绝/例外）、亲和性（复杂规则）
- 扩缩容：`scale` 手动、HPA 自动；HPA 需要 metrics-server + 容器声明 requests
- `kubectl top` 是查看实际用量的第一工具
- `<unknown>` 指标 = 排障信号：先查 Pod Ready 和 metrics-server

<summary>参考答案</summary>

1. `kubectl -n lab create deployment free-demo --image=nginx:latest --replicas=2`，因两节点都无污点且资源足够，通常会各放一个（调度器尽量均衡）。

4. `kubectl -n lab delete hpa sched-demo`。
5. 生产：控制面节点承载 etcd/apiserver，业务负载挤占资源可能影响集群稳定性，故打污点隔离。本项目小集群、资源有限，把 server 也用于业务是合理的折中（这也是 k3s 轻量化的价值之一）。真实生产建议遵循官方推荐。
