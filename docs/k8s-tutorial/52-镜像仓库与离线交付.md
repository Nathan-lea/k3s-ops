## 1. 为什么“镜像仓库”是生产运维的必修课

在开发机上 `docker pull` 成功，不代表集群里能稳定部署。生产环境常见约束：

- 节点不能直接访问 Docker Hub / ghcr.io / quay.io / registry.k8s.io。
- 安全要求：镜像必须来自受控仓库，经过扫描、签名、审计。
- 离线机房：安装包、镜像、Helm chart 都要提前搬运。
- 多架构：amd64/arm64 镜像不一致会导致“同一清单在另一种节点失败”。

本项目已经踩过相关问题：AGENTS 记录了 Docker Hub/GCR/GitHub raw 访问限制，部署时通过镜像代理或 `docker save/scp/k3s ctr images import` 导入。

## 2. 镜像名、tag、digest：先把对象认清

镜像引用格式：

```text
[registry/][namespace/]repository[:tag][@sha256:digest]
```

示例：

```text
docker.io/grafana/grafana:12.3.1
registry.k8s.io/metrics-server/metrics-server:v0.7.0
quay.io/jetstack/cert-manager-controller:v1.x.y
```

| 维度 | tag | digest |
|------|-----|--------|
| 可读性 | 好，如 `v1.2.3` | 差，是哈希 |
| 可变性 | **可变**，同名 tag 可被覆盖 | **不可变**，内容固定 |
| 适用场景 | 开发、教学、版本跟踪 | 生产发布、供应链审计、强一致部署 |
| 风险 | “昨天的 latest 和今天不一样” | 需要维护 digest 清单 |

生产建议：发布时记录 digest；GitOps/Helm values 中尽量固定版本，不用浮动 `latest`。

## 3. k3s 的 `registries.yaml`

k3s 使用 containerd，镜像仓库镜像/认证配置放在：

```text
/etc/rancher/k3s/registries.yaml
```

修改后通常需要重启 k3s（server/agent 对应节点服务）才能完全生效。

### 3.1 仓库中的模板

本仓库模板：`ansible/roles/k3s-common/templates/registries.yaml.j2`

```yaml
{% if containerd_mirrors is defined %}
mirrors:
{% for registry, mirrors in containerd_mirrors.items() %}
  {{ registry }}:
    endpoint:
{% for mirror in mirrors %}
      - "{{ mirror }}"
{% endfor %}
{% endfor %}
configs:
  "docker.io":
    auth: {}
{% endif %}
```

默认变量在 `ansible/group_vars/all.yml`：

```yaml
containerd_mirrors:
  docker.io:
    - "https://docker.1panel.live"
    - "https://docker-0.unsee.tech"
  registry.k8s.io:
    - "https://k8s.m.daocloud.io"
  registry.k8s.io/ingress-nginx:
    - "https://k8s.m.daocloud.io"
  quay.io:
    - "https://quay.m.daocloud.io"
  gcr.io:
    - "https://gcr.mirrors.ustc.edu.cn"
```

### 3.2 节点实际配置（实测）

在 server-1 查看：

```bash
vagrant ssh k3s-demo-server-1 -c "sudo cat /etc/rancher/k3s/registries.yaml"
```

实测输出（2026-11-26）：

```yaml
mirrors:
  docker.io:
    endpoint:
      - 'https://docker.1panel.live'
  registry.k8s.io:
    endpoint:
      - 'https://registry.aliyuncs.com/k8s'
      - 'https://k8s.m.daocloud.io'
      - 'https://registry.k8s.io'
  quay.io:
    endpoint:
      - 'https://quay.mirrors.ustc.edu.cn'
      - 'https://quay.io'
configs:
  docker.io:
    auth: {}
```

**观察**：节点实际文件与当前仓库模板不完全一致。这是正常的运维信号——说明集群可能经历过手工调整、旧模板或不同环境配置。排障时应同时看：

1. 仓库模板/变量（期望状态）
2. 节点 `/etc/rancher/k3s/registries.yaml`（实际状态）
3. `systemctl status k3s` / containerd 日志（是否生效）

## 4. 私有仓库认证与 TLS

生产私有仓库通常需要认证和自签 CA。`registries.yaml` 支持 `configs`：

```yaml
mirrors:
  registry.example.com:
    endpoint:
      - "https://registry.example.com"

configs:
  "registry.example.com":
    auth:
      username: "<robot-user>"
      password: "${REGISTRY_TOKEN}"
    tls:
      ca_file: "/etc/rancher/k3s/certs/registry.example.com-ca.crt"
      # insecure_skip_verify: true  # 仅临时排障，不建议生产使用
```

注意事项：

- **不要把密码/token 提交到 Git**。本仓库当前模板把 `docker.io.auth` 写成空对象是安全的；真实凭据应来自 Ansible Vault、SOPS 加密变量、或节点外部注入。
- **优先 CA 信任，不要长期 `insecure_skip_verify`**。跳过 TLS 校验会暴露中间人风险。
- **robot account 优先于个人账号**。便于审计、轮换和最小权限。
- **按 namespace/项目隔离权限**。Harbor 项目、云厂商仓库 IAM 都应最小化。

## 5. 离线/半离线交付方案

| 方案 | 适用场景 | 优点 | 缺点 | 本项目关联 |
|------|----------|------|------|-----------|
| 公网镜像 + mirror | 能访问镜像站但不稳 | 简单，改 registries.yaml 即可 | 依赖外部镜像站可用性 | 当前默认方案 |
| 私有 Registry/Harbor | 内网多集群、需要审计/扫描 | 可控、可审计、可复制 | 需部署维护 Harbor | P2 进阶 |
| `docker save` + `scp` + `k3s ctr images import` | 少量镜像、临时救火 | 不需要仓库服务 | 手工、不可规模化 | AGENTS 已记录的应急方案 |
| airgap tarball / 私有制品库 | 完全离线机房 | 可审计、可版本化 | 准备成本高 | 生产/边缘场景 |
| Helm chart + 镜像一起搬运 | 离线 GitOps/Helm 交付 | 版本一致性好 | 需制品清单和校验 | 与 24/28 章结合 |

### 5.1 应急导入（实测过的模式）

当节点拉不到镜像时，可以在有镜像的机器上：

```bash
# 宿主机/可联网机器
docker pull docker.io/grafana/grafana:12.3.1
docker save docker.io/grafana/grafana:12.3.1 -o grafana-12.3.1.tar
scp -i <node-key> grafana-12.3.1.tar vagrant@192.168.56.20:/tmp/

# 目标节点
sudo k3s ctr images import /tmp/grafana-12.3.1.tar
sudo k3s ctr images ls | grep grafana
```

这是第 49 章 Grafana 镜像卡住时使用的救急路径。它适合少量镜像，不适合日常发布。

### 5.2 离线交付清单

离线环境不要只搬“一个镜像”，要搬**交付包**：

- 容器镜像（按 digest 固定）
- Helm charts / manifests / values
- k3s 安装包、airgap images（如需要）
- 校验文件（SHA256）
- 版本说明、回滚说明、依赖清单

## 6. Harbor 选型：什么时候该上

Harbor 适合“团队开始认真管理镜像”时，而不是实验集群第一天。

| 需求 | 不上 Harbor | 上 Harbor |
|------|-------------|-----------|
| 只是拉镜像慢 | mirror/registries.yaml 足够 | 可能过重 |
| 需要内网统一仓库 | 简单 registry 也行 | 更合适 |
| 需要漏洞扫描、RBAC、审计、复制、保留策略 | 难 | 合适 |
| 需要镜像签名/供应链治理 | 需拼装多工具 | Harbor + Cosign/Notary/Trivy 生态更完整 |
| 当前双节点 2c/4GB 实验环境 | 推荐 | 不推荐现在装，资源和运维成本高 |

最小生产建议：

1. 先把 `registries.yaml` 和镜像版本策略管好。
2. 再上私有仓库（Harbor 或云厂商 Registry）。
3. 最后补扫描、签名、SBOM、准入策略（与 43/后续安全章联动）。

---

## 7. 供应链安全：扫描、签名、SBOM

| 控制项 | 目标 | 常见工具/方式 |
|--------|------|---------------|
| 漏洞扫描 | 发现 OS/依赖 CVE | Trivy, Grype, Harbor Scan |
| SBOM | 知道镜像里有什么 | Syft, Trivy SBOM |
| 签名/验签 | 确认镜像来源未被篡改 | Cosign, Sigstore, Notary |
| 准入策略 | 不合规镜像禁止进入集群 | Kyverno, OPA/Gatekeeper, admission webhook |
| 基础镜像治理 | 减少攻击面 | distroless/alpine/ubi minimal，定期重建 |

本项目第 43 章已有 Kyverno；后续可以扩展“只允许来自指定 registry / 必须带签名 / 禁止 latest”的策略，但这需要先有稳定的镜像发布流程。

## 8. 排障清单

### 8.1 Pod ImagePullBackOff

```bash
kubectl --kubeconfig ./kubeconfig describe pod <pod> -n <ns>
kubectl --kubeconfig ./kubeconfig get events -n <ns> --sort-by=.lastTimestamp | tail -n 30
```

检查：

- 镜像名/tag 是否存在；是否应改用 digest。
- 节点能否访问 registry/mirror。
- `registries.yaml` 是否配置了正确 endpoint/auth/CA。
- 私有仓库是否需要 `imagePullSecrets`（K8s 层）或 `registries.yaml`（节点 containerd 层）。

### 8.2 节点侧检查

```bash
sudo cat /etc/rancher/k3s/registries.yaml
sudo k3s crictl info | grep -i registry -n || true
sudo k3s ctr images ls | head
sudo journalctl -u k3s -n 100 --no-pager   # server
sudo journalctl -u k3s-agent -n 100 --no-pager
```

### 8.3 常见坑

1. **只改了仓库模板，没应用到节点**：Ansible/Vagrant provision 未执行，节点仍是旧配置。
2. **改了 registries.yaml 没重启 k3s**：拉镜像行为不符合预期。
3. **mirror 只代理 docker.io**：`registry.k8s.io/quay.io/gcr.io` 需要单独配置。
4. **把凭据写进 Git**：应使用 Vault/SOPS/Ansible Vault/CI Secret。
5. **离线只搬镜像不搬 chart/values**：部署版本不可复现。

## 9. 动手练习

1. **Mirror 配置草案**：为 `docker.io` 和 `registry.k8s.io` 写一份 `registries.yaml` mirror 草案，标注哪些字段会影响认证、TLS 和重启生效。
2. **ImagePullBackOff 排障**：模拟镜像 tag 不存在，按“kubectl describe -> 节点 crictl/journalctl -> registries.yaml -> imagePullSecret”顺序写排查记录。
3. **离线交付清单**：为一个 Helm 应用整理离线包清单：镜像 tar、chart tgz、values、校验和、目标 k3s/arch 版本，并说明导入后如何验证。

## 10. 清理

本章无强制实验资源。若你做了临时导入测试：

```bash
# 节点上删除测试镜像（确认无容器使用）
sudo k3s ctr images rm <image-ref>

# 删除临时 tar
rm -f /tmp/*.tar
```

若修改了 `registries.yaml` 做实验，请恢复原配置并重启对应 k3s 服务。

## 11. 小结

- `registries.yaml` 是 k3s/containerd 镜像拉取的关键配置，适合 mirror、私有仓库和 TLS/认证。
- 离线交付不是“拷个镜像”——要包含镜像、chart/manifests、校验和版本清单。
- 小团队先把 mirror、版本固定、导入流程做扎实；有审计/合规需求再上 Harbor + 扫描 + 签名 + 准入。
- 本项目已有 mirror 模板和应急导入实践，但节点实际配置可能漂移，运维时要同时检查“仓库期望”和“节点实际”。
