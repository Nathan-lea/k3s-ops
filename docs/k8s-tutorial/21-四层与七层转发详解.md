## 1. 概念：L4 与 L7 是什么

### 1.1 分层速览（只涉及相关三层）

```text
L7 应用层     HTTP/HTTPS 报文：Host、Path、Header、Cookie、Body
L4 传输层     TCP/UDP ：四元组 = 源IP + 源端口 + 目的IP + 目的端口
L3 网络层     IP 地址路由（K8s 里 flannel 负责这层，第 04 章）
```

- **L4 转发**：只看"包要发到哪个 IP:端口"，**不拆开报文看内容**。转发的是"数据流"。
- **L7 转发**：拆开 HTTP 报文，看 Host（域名）、Path（路径）、Header（头）等，再决定转发给谁。转发的是"请求"。

### 1.2 快递类比（帮助直觉）

```text
L4 转发 = 物流中心只按"收件城市+邮编"分拣包裹，不拆包裹看里面是啥
          （快、省事，但不知道包裹内容）
L7 转发 = 客服打开信封看内容，按"给财务部/给技术部"派单
          （能精细分流，但每封都要拆开看，要读懂内容）
```

### 1.3 一句话定义

> **L4 转发**：按 目标 IP + 端口（+协议）把流量送到后端，不碰内容；
> **L7 转发**：按 HTTP 语义（域名/路径/头）把请求路由到不同后端，可改写内容。

## 2. 特点对比：一张表吃透

| 维度 | **L4 转发**（传输层） | **L7 转发**（应用层） |
|------|---------------------|---------------------|
| 看到的东西 | 四元组：IP + 端口 + 协议 | HTTP 报文：Host / Path / Header / Cookie |
| 路由依据 | 目标端口（如 3306 → 数据库） | 域名 + 路径（如 `api.lab.com/v1/*` → A 服务） |
| 支持的协议 | **任意**：TCP / UDP / 任意二进制流 | **仅 HTTP / HTTPS** |
| 转发单位 | 一条连接（流） | 一个请求 |
| 性能 | 高（内核态/纯转发，几乎不透传开销） | 中（应用层代理，要解码报文） |
| TLS 终结 | ❌ 不终结（证书由后端自己处理） | ✅ 终结（证书挂在网关，后端可裸 HTTP） |
| 内容改写 | ❌ 不能改 | ✅ rewrite-target / redirect / add-header |
| 按内容分流 | ❌ 不能按路径/Cookie 分 | ✅ 按 path、header、cookie 金丝雀等 |
| 会话保持 | 源 IP | Cookie / sticky |
| 对客户端可见性 | 透明（后端看到真实客户端 IP? 否，通常要 proxy-protocol） | 代理（加 `X-Forwarded-For` 等） |
| 端口消耗 | 每后端一个端口/LB 规则 | **所有域名共享 80/443 两个端口**（核心差异） |

> 最核心的一条：**L7 让"一个入口端口"（80/443）接待无数域名/路径**；L4 是"一个端口对应一个后端"。这就是生产环境为什么"外面 4 层只开少数端口，里面 7 层做各种分流"。

## 3. 优劣与适用场景

### 3.1 L4 的优势与劣势

**优势**：
- 性能好、开销小（不需要解析 HTTP）
- **协议无关**：数据库（MySQL 3306）、Redis（6379）、消息队列（9092 Kafka）、gRPC、任意二进制协议都行
- 简单直接：端口即服务

**劣势**：
- **一个端口一个后端**，无法按域名/路径分流（端口资源有限 30000-32767）
- 不做 TLS 终结：证书要到应用层，后端全要配证书
- 无内容级功能（重写、重定向、熔断、金丝雀）

### 3.2 L7 的优势与劣势

**优势**：
- **一键多路由**：一个 Ingress 端口分流给 N 个服务（域名/路径）
- TLS 终结 + 证书自动管理（cert-manager，本集群已装）
- 丰富增强注解：rewrite-target（路径重写）、ssl-redirect、limit、金丝雀（canary）等
- 统一入口：认证、限流、监控都在网关层做

**劣势**：
- **只支持 HTTP(S)**：数据库/消息队列这种二进制协议进不来
- 性能开销（解码报文）；高并发下是瓶颈点（但通常够用）
- 平台绑定：要装对应的 Ingress 控制器（本集群 ingress-nginx）

### 3.3 选型决策表

| 流量 | 示例 | 用哪个 |
|------|------|--------|
| Web 页面/API（HTTP） | nginx 站点、REST API、前端 | **L7 Ingress** |
| 数据库/缓存/消息 | MySQL、Redis、Kafka、gRPC | **L4 Service**（NodePort/LB） |
| 内部服务互调 | 集群内任意服务 | L4 ClusterIP（默认） |
| 需要证书/重写/分流 | 多域名共享 80/443 | **L7 Ingress** |
| 大流量低延迟 | 内部高速转发 | L4（性能优先） |

## 4. K8s 中 4 层怎么实现：Service

### 4.1 三种形态

| 形态 | 暴露范围 | 访问方式 | 本集群 |
|------|---------|---------|--------|
| **ClusterIP** | 集群内 | `svc名.ns`（第 19 章） | 默认（kube-dns 10.43.0.10 等） |
| **NodePort** | 集群外（节点 IP + 端口） | `节点IP:NodePort`（30000-32767） | ✅ ingress-nginx / rancher / nginx-svc |
| **LoadBalancer** | 集群外（云 LB IP） | 云厂商分配外网 IP | ❌ 本集群无 MetalLB，不用 |

### 4.2 协议字段：TCP / UDP

```yaml
apiVersion: v1
kind: Service
metadata: { name: mysql-lb, namespace: lab }
spec:
  type: NodePort
  selector: { app: mysql }
  ports:
  - port: 3306          # 集群内访问端口
    targetPort: 3306    # 容器端口
    nodePort: 30306     # 节点端口（30000-32767）
    protocol: TCP       # ★ TCP / UDP 在这里选，这就是 4 层语义
```

> L4 的"层"就体现在 `protocol` 上：选 UDP 则整个管线按 UDP 转发（DNS 53、NTP、游戏流量）。

### 4.3 4 层数据流（对照第 11 章规则链）

```text
外部 ── 节点IP:32062 ──▶ KUBE-NODEPORTS ──▶ KUBE-SVC-XXX(负载均衡)
      ──▶ KUBE-SEP-XXX(DNAT) ──▶ Pod 10.42.0.57:80
```

第 11 章实测过全套链：`KUBE-SERVICES`（ClusterIP 入口）→ `KUBE-SVC-*`（随机分流）→ `KUBE-SEP-*`（DNAT 到 Pod IP）。

### 4.4 本集群真实 4 层实例（全部实测可达）

| Service | NodePort | 实际访问（宿主机实测） | 用途 |
|---------|----------|----------------------|------|
| `lab/nginx-svc` | **32062** | `curl http://192.168.56.10:32062/` → **200** | 直达 nginx-demo（不经过 Ingress） |
| `ingress-nginx/ingress-nginx-controller` | **30080 / 30444** | `curl http://192.168.56.10:30080/` → (转发 7 层) | 7 层的"物理入口" |
| `cattle-system/rancher` | **30443 (443)** | `curl -k https://192.168.56.10:30443/` → **200** | Rancher UI |
| `kube-system/kube-dns` | ClusterIP | 集群内 `10.43.0.10:53` | DNS（第 19 章） |

> 实测截图级证据（同一时刻）：
> ```text
> $ curl -w "%{http_code} %{remote_ip}:%{remote_port}" http://192.168.56.10:32062/
> HTTP 200 → 192.168.56.10:32062        ← 4 层直达，应答来自节点端口
> ```

## 5. K8s 中 7 层怎么实现：Ingress

### 5.1 Ingress API 三要素

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: nginx-ing
  namespace: lab
spec:
  ingressClassName: nginx        # ① 用哪个控制器（ingress-nginx）
  rules:
  - host: lab.k3s.local          # ② 域名（Host 头匹配）
    http:
      paths:
      - path: /                  # ③ 路径
        pathType: Prefix
        backend:
          service:
            name: nginx-svc      # ④ 转发到哪个 Service
            port: { number: 80 }
```

### 5.2 本集群实测：nginx-ing（7 层真实配置）

上面就是 `kubectl -n lab get ing nginx-ing -o yaml` 的核心内容。它的状态里有 `loadBalancer.ip: 10.43.197.40`——注意这是 ingress-nginx 控制器的 ClusterIP，**Ingress 本身不占端口，端口是控制器的 NodePort 30080/30444（4 层）给的**。

### 5.3 只有一个证据最能说明 7 层"看 Host 头"（实测对比）

```bash
# 带 Host 头（lab.k3s.local 匹配规则）→ 200
curl -s -o /dev/null -w "%{http_code}\n" -H "Host: lab.k3s.local" http://192.168.56.10:30080/
# 输出: 200

# 无 Host 头 / 不匹配的域名 → 404
curl -s -o /dev/null -w "%{http_code}\n" http://192.168.56.10:30080/
# 输出: 404        ← 7 层按域名路由，找不到规则就 404
```

**同一个端口 30080、同一个 IP**，差别只在 HTTP 头——这就是 7 层"拆报文看内容"的直接证明；换成 4 层（32062）就没有这个行为（**任何 Host 都 200**，因为它不看不匹配）。

### 5.4 TLS 终结与证书

```yaml
spec:
  tls:
  - hosts: [lab.k3s.local]
    secretName: lab-tls      # 证书放 Secret；本集群已装 cert-manager 可自动签发
```

- 7 层可终结 TLS：浏览器 ⇄ 网关加密，网关 ⇄ 后端可走明文
- 证书轮换对后端透明（后端不用动）——L4 做不到这点（后端各自配证书）

### 5.5 高级注解（ingress-nginx 专属，第 18 章已列）

| 注解 | 作用 |
|------|------|
| `nginx.ingress.kubernetes.io/rewrite-target: /` | 路径重写（剥掉前缀再转发） |
| `nginx.ingress.kubernetes.io/ssl-redirect: "true"` | 强制 HTTPS |
| `nginx.ingress.kubernetes.io/canary: "true"` + weight | 金丝雀灰度（按比例引流） |
| `nginx.ingress.kubernetes.io/proxy-body-size: 50m` | 上传大小限制 |
| `nginx.ingress.kubernetes.io/limit-rps` | 限流 |

> 这些是 L4 完全做不到的"内容级"能力——改注解 = 改路由行为（第 18 章"改 Annotation = 改行为"）。

### 5.6 7 层数据流（注意与 4 层的汇合点）

```text
外部 ── 30080 (NodePort, 4层!) ──▶ ingress-nginx 控制器 Pod
      ── 拆 HTTP: Host=lab.k3s.local, Path=/ ──▶ 查 Ingress 规则
      ── rewrite / 重定向 等注解处理 ──▶ nginx-svc (ClusterIP 10.43.23.169:80)
      ── Endpoints ──▶ Pod 10.42.0.57:80
```

**关键理解**：7 层的"物理接入"也是靠 4 层（NodePort 30080）完成的——**外层永远先走 4 层，内层才轮到 7 层判断**。这就是 §6 配合模式的由来。

## 6. 经典生产配合：4 层打底 + 7 层分流

### 6.1 标准架构图（本集群就是这个形态）

```text
                 ┌─────────── 4 层（NodePort/LB，只转发 IP:端口）───────────┐
外部流量 ──▶ 节点IP:30080/30444 ──▶ ingress-nginx 控制器 ──▶ 按域名/路径分流（7 层）
                                          │
                     ┌────────────────────┼─────────────────────┐
                     ▼                    ▼                     ▼
              app-a.lab.com → svc-a   api.lab.com/v1 → svc-b   lab.k3s.local → nginx-svc
              (多个域名/路径，全挤在这两个端口上)
```

### 6.2 为什么要这么分层

| 层 | 职责 | 价值 |
|----|------|------|
| 4 层（外层） | 暴露少数端口、承接高并发连接 | 端口集中管理、高可用（每节点都能接入） |
| 7 层（内层） | 按域名/路径分给各服务、TLS、限流、灰度 | 业务路由全部在网关层，后端专注业务 |

### 6.3 本集群现状盘点

```text
30080  (HTTP)   ──┐
30444  (HTTPS)  ──┼─▶ ingress-nginx ──▶ host: lab.k3s.local ──▶ nginx-svc ──▶ nginx-demo
                  │                     （7 层）
32062  (直接暴露 nginx-demo，4 层旁路，仅实验/演示用）
30443  (Rancher 直接 NodePort，不经过 Ingress，4 层)
```

> 生产规范：**业务流量只从 30080/30444 进（7 层），不要像 32062 那样绕过 Ingress 直连**——否则证书、限流、路由全失效。

### 6.4 需要额外 4 层入口时（TCP/UDP 服务/上一轮的话题）

要在 ingress-nginx 之外再开 4 层端口（如暴露 MySQL 3306），两种做法：

```yaml
# 做法一：直接用 Service NodePort（推荐，标准）
apiVersion: v1
kind: Service
metadata: { name: mysql, namespace: lab }
spec:
  type: NodePort
  selector: { app: mysql }
  ports: [{ port: 3306, targetPort: 3306, nodePort: 30306, protocol: TCP }]
```

```yaml
# 做法二：ingress-nginx 的 tcp/udp-services ConfigMap（借控制器进程跑 L4）
# 编辑 ingress-nginx/ingress-nginx-tcp（本集群已挂载该 CM，当前为空）
apiVersion: v1
kind: ConfigMap
metadata: { name: ingress-nginx-tcp, namespace: ingress-nginx }
data:
  "18888": "lab/nginx-svc:80"     # 节点18888 → lab/nginx-svc:80
# 并给 ingress-nginx-controller Service 增加 nodePort 18888
```

> 两者差异：做法一是显式 Service、语义清晰；做法二是把 L4 也收编进 ingress-nginx 控制器。一般用做法一——L4 就老老实实用 Service，别绕（简单优先）。

### 6.5 何时用 LoadBalancer 而不是 NodePort

- 云环境（AWS/GCP/Azure）：LB 分配公网 IP，即 `type: LoadBalancer`
- 本集群（本地 VirtualBox，无 MetalLB）：**NodePort 即可**（已在用）
- 补充：k3s 内置 ServiceLB 在本集群已禁用（`--disable servicelb`，第 04 章）

## 7. Rancher 界面设置（两种转发怎么点出来）

### 7.1 4 层：Workloads → Services → Create

| 界面字段 | 对应 K8s 字段 | 4 层操作 |
|---------|--------------|---------|
| 类型 | `spec.type` | 选 **NodePort**（本集群无 LB 选项可用） |
| 端口映射（Service Port ↔ Target Port） | `spec.ports[].port/targetPort` | 容器端口 ↔ 服务端口 |
| 协议（下拉） | `spec.ports[].protocol` | **TCP / UDP 二选一（这就是 4 层开关）** |
| Node Port | `spec.ports[].nodePort` | 不填自动分配 30000-32767；可手填 |

### 7.2 7 层：Service Discovery → Create → Ingress

| 界面字段 | K8s 字段 | 操作 |
|---------|---------|------|
| 规则 → 域名 | `rules[].host` | 填 `lab.k3s.local` |
| 路径 | `paths[].path/pathType` | `/` + Prefix |
| 后端（服务/端口） | `backend.service` | 选 `lab/nginx-svc:80` |
| 证书 | `spec.tls` | 选已有 Secret（或 cert-manager 签发） |
| 高级 | 注解 | YAML 里加（rewrite-target 等，无表单） |

### 7.3 Rancher 里没有表单的

- **tcp-services / udp-services ConfigMap**：需 Workloads → ConfigMaps → 编辑 YAML，或命令行 apply（§6.4 做法二）

## 8. 排障：4 层与 7 层的"不同死法"

### 8.1 现象 → 定位表（按序排查）

| 现象 | 最可能是哪层问题 | 第一命令 |
|------|----------------|---------|
| `connection timed out`（连不上 30080/32062） | **4 层**：防火墙/NodePort 未开/kube-proxy 规则缺失 | `ss -lnt | grep <nodePort>`；iptables（第 11 章）；从节点 `curl 127.0.0.1:<nodePort>` |
| 端口通但 `connection refused` | **4 层**：后端 Pod 没起/Endpoints 空/端口不对 | `kubectl get ep <svc>`；`kubectl get pods -o wide` |
| 能通但 **404** | **7 层**：Host/Path 不匹配、Ingress 规则没建 | `kubectl get ing -A`；带 Host 头 curl；看规则 pathType |
| 能通但 **502/503** | **7 层**：后端 svc 没有可用端点（Annotation 写错 svc 名） | `kubectl get ep`；`kubectl logs <ingress-nginx pod>` |
| 证书告警/HTTPS 异常 | **7 层 TLS**：证书 Secret 不存在/过期/未关联 | `kubectl get secret <tls>`；`kubectl describe ing` |
| 必须特定域名才通 | 这是 7 层**特性不是 bug**（回忆 §5.3 的 200/404） | 确认客户端带正确 Host / 配置了 DNS |
| UDP 服务不通 | **4 层**：`protocol: UDP` 忘写（默认 TCP） | 检查 svc 的 protocol；udp 用 `nc -u` 测试 |
| NodePort 起不来 | **4 层**：超出 30000-32767 范围 | 改回范围内 |

### 8.2 定位心法：先分清"层"

```bash
# ① 4 层测：直接 IP:NodePort（不经 Ingress）
curl -v http://192.168.56.10:32062/            # 通 → 4 层 OK；不通 → 查 Service/kube-proxy/防火墙

# ② 7 层测：同一端口 + 显式 Host
curl -v -H "Host: lab.k3s.local" http://192.168.56.10:30080/   # 404/502 → 查 Ingress 规则与后端

# ③ 集群内全链路测（绕开外部防火墙）
kubectl -n lab run curl-test --rm -i --restart=Never --image=curlimages/curl -- \
  curl -s -o /dev/null -w "%{http_code}\n" http://nginx-svc.lab.svc.cluster.local/
```

> 排障第一问永远是：**我在测哪一层？** 4 层的错在 iptables/EP/防火墙里找；7 层的错在 Host 头/Ingress 规则/控制器日志里找。混着测（比如不带 Host 头去测 Ingress）会得出错误结论。

## 9. 小结

- **L4 = 传输层转发**：认 IP+端口+协议，不碰内容；**L7 = 应用层转发**：拆 HTTP 报文，认域名/路径/头
- **L4 优点**：性能高、协议无关（数据库/消息队列随便转）；**缺点**：一端口一后端、无 TLS 终结
- **L7 优点**：一个 80/443 接所有域名、TLS 终结、注解增强；**缺点**：仅 HTTP(S)、有解析开销
- **K8s 4 层实现** = Service（ClusterIP/NodePort/LoadBalancer）+ kube-proxy 规则链（第 11 章）
- **K8s 7 层实现** = Ingress + ingress-nginx（host/path 路由 + 注解）
- 实测证据：同端口 30080 带 Host 头 200 / 不带 404；NodePort 32062 直连任何 Host 都 200
- **生产配合**：4 层打底暴露 80/443 → 7 层按域名/路径分流；额外 4 层服务用 Service NodePort（或 tcp-services CM）
- **排障分层**：先分清 4 层（防火墙/EP/iptables）还是 7 层（Host/规则/日志），再对症下药

5. 深度题：为什么说"7 层的前置物理入口也是 4 层"？如果 ingress-nginx 控制器的 NodePort 没开，外部还能访问集群内页面吗？

<details>
<summary>参考答案</summary>

1. 三种情况（带对 Host / 带错 Host / 不带 Host）**都是 200**——NodePort 是 4 层，只看 IP:端口不看 Host。这正是与 7 层（30080）的最大差异。
2. Ingress 核心字段：`host` 是域名匹配、`path`+`pathType` 决定路径规则、`backend.service` 指向目标 svc。模板参照 §5.1。
3. UDP Service 的 svc 会显示 `53/UDP`；NodePort 需选 30000-32767 内的空闲端口。删掉恢复（避免占端口）。
4. 4 层端口 30080 本身是通的（返回 404 说明连接建立了）；404 来自 7 层 ingress-nginx 找不到匹配的 Host 规则——对应 8.1 表"能通但 404 → 7 层 Host/Path 不匹配"这一行。
5. 因为 ingress-nginx 控制器本身是一个被 4 层 Service（NodePort 30080/30444）暴露的 Pod；外部流量先通过 4 层规则到达控制器，控制器才做 7 层判断。若 NodePort 未开，7 层的规则再全也收不到外部流量——这就是"外层 4 层、内层 7 层"的分层必然性。
</details>
