# 03 工作负载：如何部署和管理应用

## 本章目标

- 理解 Pod 与各类工作负载资源（Deployment/ReplicaSet/StatefulSet/DaemonSet/Job）
- 掌握 kubectl 的部署、查看、扩缩容、更新、回滚、进入容器、日志等操作
- 理解 imagePullPolicy 与镜像拉取机制（离线环境的坑）
- 会用 Rancher Workload 页面管理同样的对象

---

## 1. 核心概念

### 1.1 Pod —— 最小调度单元

Pod 是 K8s 中**能运行容器的最小逻辑单元**：一个或多个容器的组合（共享网络栈、存储卷）。
- 每个 Pod 有唯一集群内 IP（10.42.x.x）
- Pod 是**短暂**的：删除后重建会得到新 IP、新名字
- 通常不直接创建 Pod，而是交给上层控制器管理

### 1.2 控制器资源（Workload）

| 资源 | 用途 | 例子 |
|------|------|------|
| **Deployment** | 无状态应用，支持滚动更新/回滚/扩缩容 | Web 服务、API |
| **ReplicaSet** | 维护固定副本数（通常由 Deployment 托管，不直接使用） | 中间层 |
| **StatefulSet** | 有状态应用，稳定网络标识+有序部署 | 数据库、消息队列 |
| **DaemonSet** | 每个节点运行一个副本 | 日志采集、监控代理 |
| **Job** | 一次性任务（跑完即退） | 数据迁移、批处理 |
| **CronJob** | 定时任务 | 定时备份 |

**Deployment → ReplicaSet → Pod 的层级关系**（这是理解 K8s 的关键）：

```
Deployment (期望状态: 5 个 nginx)
   └── ReplicaSet (version1: 管理模板 hash=abc123)
         └── Pod nginx-demo-abc123-xxxx (实际运行的容器)
         └── Pod nginx-demo-abc123-yyyy
         └── ...
```

## 2. 组件作用与通讯

- **用户**（kubectl）→ API Server：提交 Deployment 期望状态
- **Deployment 控制器**（controller-manager 内）→ 确保 RS 副本数正确
- **ReplicaSet 控制器** → 创建/删除 Pod
- **Scheduler** → 为 Pod 选节点
- **kubelet** → 在节点上实际创建容器，回传状态

## 3. 本集群实站对照

### 3.1 准备：独立命名空间，避免污染现有资源

### 3.2 创建 Deployment

```bash
kubectl -n lab create deployment nginx-demo --image=nginx:latest --replicas=3
```

用三个镜像参数创建后查看结果：

```bash
kubectl -n lab get deploy,rs,pods -o wide
```

预期输出（本环境真实，nodeSelector 限 server-1，见 3.6 说明）：

```
NAME                         READY   UP-TO-DATE   AVAILABLE   AGE   CONTAINERS   IMAGES         SELECTOR
deployment.apps/nginx-demo   3/3     3            3           12s   nginx        nginx:latest   app=nginx-demo

NAME                                    DESIRED   CURRENT   READY   AGE   CONTAINERS   IMAGES         SELECTOR
replicaset.apps/nginx-demo-689745b8fd   3         3         3       12s   nginx        nginx:latest   app=nginx-demo,pod-template-hash=689745b8fd

pod/nginx-demo-689745b8fd-djxt5   1/1     Running  0          12s   10.42.0.240   k3s-demo-server-1   <none>
```

观察：
- `deployment/nginx-demo` → `replicaset/nginx-demo-689745b8fd`（模板 hash）→ `pod/nginx-demo-689745b8fd-<随机后缀>`
- Pod 的 IP 在 `10.42.0.x`（Pod 网段，第 04 章细讲）
- 本例中 3 个 Pod 都跑在 server-1（无污点可调度 + 本环境的 nodeSelector 约束）

### 3.3 查看 Deployment 详情

```bash
kubectl -n lab describe deploy nginx-demo
```

预期输出（节选）：

```
Name:                   nginx-demo
Selector:               app=nginx-demo
Replicas:               3 desired | 3 updated | 3 total | 3 available | 0 unavailable
StrategyType:           RollingUpdate
```

- `StrategyType: RollingUpdate`：默认更新策略，先起新再删旧，保证不中断

```bash
# 进入容器执行命令（交互式）
kubectl -n lab exec nginx-demo-689745b8fd-djxt5 -- sh -c 'echo hello-from-nginx; head -1 /etc/os-release'
```

预期输出：

```

```

```bash
# 查看容器日志（-f 跟随）
kubectl -n lab logs nginx-demo-689745b8fd-djxt5 --tail=5
```

预期输出（nginx 启动日志）：

```
2026/10/03 01:00:17 [notice] 1#1: start worker processes

```

```bash
# 端口转发：把 Pod 的 80 映射到本机 18080
kubectl -n lab port-forward nginx-demo-689745b8fd-djxt5 18080:80
```

预期输出：

```

```

```bash

```

> `port-forward` 是调试利器：集群内没有暴露服务的 Pod，也能从本机直接访问。

### 3.6 滚动更新与回滚

更新镜像版本（会触发 RollingUpdate）：

```bash
kubectl -n lab set image deployment/nginx-demo nginx=nginx:1.27-alpine
```

命令原则：`set image deployment/<名称> <容器名>=<新镜像>`。若想显式记录变更原因：

```bash
kubectl -n lab rollout history deployment/nginx-demo
```

预期输出（未加注解时）：

```
deployment.apps/nginx-demo
REVISION  CHANGE-CAUSE
1         <none>
```

回滚到上一版本：

```bash
kubectl -n lab rollout undo deployment/nginx-demo
```

**不中断重启 Pod**（保留模板，只是滚动重建）：

```bash
kubectl -n lab rollout restart deployment/nginx-demo
```

预期输出（摘要）：

```
deployment.apps/nginx-demo restarted
Waiting for deployment "nginx-demo" rollout to finish: 0 out of 5 new replicas have been updated...
...
deployment "nginx-demo" successfully rolled out
```

> ⚠️ 本环境（离线、镜像源不稳定）执行 `set image` 到新 tag 时可能因拉不到镜像而卡住。这不是 K8s 概念问题，而是环境网络限制 —— 详见下方「镜像拉取」专题。

### 3.7 镜像拉取机制（离线环境的坑，实战亲历）

现象：`kubectl create deployment ... --image=nginx:1.27` 后 Pod 一直 `ImagePullBackOff`。

排查链路：

```bash
kubectl -n lab get pods                      # 看到 ImagePullBackOff
kubectl -n lab describe pod <pod名>          # Events 段显示具体失败原因
```

本环境真实事件摘录：

```
Failed to pull image "nginx:1.27": failed to resolve reference "docker.io/library/nginx:1.27":
  Head "https://docker.1panel.live/v2/library/nginx/manifests/1.27": dial tcp: lookup docker.1panel.live: Try again
```

**结论**：`nginx:1.27` 这个 tag 在镜像加速源上解析失败，且 **`imagePullPolicy` 默认对 `latest` 是 `Always`（每次都重新拉取验证）**，导致连本地缓存都不直接用。

三个取值：
| imagePullPolicy | 行为 |
|-----------------|------|
| `Always` | 每次启动都从远程校验/拉取（`latest` 默认） |
| `IfNotPresent` | 本地有就用本地（明确 tag 默认） |
| `Never` | 只用本地，绝不远程 |

**本集群的实践**：先确认哪些镜像已缓存在节点 containerd：

```bash
# 在 server-1 节点上执行（k3s 自带 ctr）
sudo /var/lib/rancher/k3s/data/current/bin/ctr -n k8s.io images list | grep nginx
```

若已有缓存镜像，用 YAML 指定 `imagePullPolicy: IfNotPresent`，避免触发远程拉取：

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-demo
  namespace: lab
spec:
  replicas: 3
  selector:
    matchLabels: { app: nginx-demo }
  template:
    metadata:
      labels: { app: nginx-demo }
    spec:
      containers:
        - name: nginx
          image: nginx:latest
          imagePullPolicy: IfNotPresent   # 用本地缓存，不强制远程
```

### 3.8 节点选择（nodeSelector）

把 Pod 调度到指定节点（本环境中 server 有镜像缓存时很实用）：

```yaml
spec:
  nodeSelector:
    kubernetes.io/hostname: k3s-demo-server-1
```

## 4. Rancher 界面对照

Rancher → 集群 → 左侧 **Workload**：
- **Deployments** 页 = `kubectl get deploy -A`
- 点进某个 Deployment 可看 **Pod 列表、日志（点 Pod 的 ⋮ → View Logs）、进入容器终端（Execute Shell）**
- **右侧的 + 号** 可以图形化创建 Deployment（等于 UI 版的 kubectl apply）
- 上方命名空间下拉框切换 namespace

## 5. 小结

- Deployment → ReplicaSet → Pod 是标准层级；理解后其他控制器都类似
- 调试三板斧：`get`（看状态）/ `describe`（看事件）/ `logs`（看日志）
- `exec` / `port-forward` 用于进入容器、临时访问
- 滚动更新/回滚/restart 是一条命令的事
- 镜像拉取在离线环境是最大变数，`imagePullPolicy` 要按需设置
