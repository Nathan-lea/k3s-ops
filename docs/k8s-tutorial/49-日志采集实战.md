# 49 日志采集实战：Loki + Promtail + Grafana

## 章节信息

| 项目 | 内容 |
|------|------|
| 适用平台 | Linux / macOS（标准路径）；Windows（ops VM 路径，在 ops VM 内执行 kubectl/helm） |
| 前置章节 | 08/10/34/36/47 |
| 预计耗时 | 60-90 分钟 |
| 破坏性操作 | 中：Helm 安装会创建 namespace、PVC、DaemonSet、StatefulSet、Service；日志组件会占用节点资源和本地磁盘。建议用独立 `logging` namespace，并限制保留期。 |
| 实测环境 | k3s v1.30.2+k3s2，双节点（server-1 2c/4GB + agent-1 2c/4GB），默认 StorageClass `local-path`，见 [00-README](00-README.md) |

## 本章目标

- 理解日志采集的最小闭环：**容器 stdout/stderr → Promtail 采集 → Loki 存储索引 → Grafana/LogQL 查询**
- 在资源紧张的实验集群上部署一套**轻量** Loki 日志栈
- 会按 namespace、Pod、关键字、时间范围排查报错
- 理解 Loki 与 Elasticsearch 类方案的差异、适用边界和清理方式

---

## 1. 日志采集最小闭环

```text
Pod/Container stdout|stderr
        │
        ▼
  节点日志文件 (/var/log/pods/...)
        │
        ▼
  Promtail (DaemonSet, 每节点一个)
        │  push
        ▼
  Loki (存储日志块 + 标签索引)
        │
        ├──> Grafana Explore / Dashboard (LogQL)
        └──> API / logcli / kubectl port-forward
```

与第 08/47 章的区别：

- **08 章**：`kubectl logs`、`events`、`top`，偏单点排查。
- **47 章**：Prometheus/Grafana/Alertmanager，偏**指标和告警**。
- **49 章**：Loki/Promtail/Grafana，偏**日志集中查询和排障**。

> 关键点：Loki 不像 Elasticsearch 那样全文索引日志内容，它主要索引**标签（labels）**，日志正文按流压缩存储。优点是轻量、成本低；代价是标签设计要克制，高基数字段（如 request_id、user_id）不要当标签。

## 3. 轻量方案设计

本章采用实验环境折中方案：

| 组件 | 角色 | 本章配置 | 说明 |
|------|------|----------|------|
| Loki | 日志存储与查询 | `SingleBinary`，1 副本，钉在 agent-1 | 不用分布式模式，省资源 |
| Promtail | 日志采集 agent | DaemonSet，全节点 | 每个节点读本机 `/var/log/pods` |
| Grafana | 日志可视化 | 1 副本，NodePort `30301`，钉在 agent-1 | 预配 Loki datasource |
| Storage | 持久化 | local-path PVC，Loki 5Gi / Grafana 1Gi | 实验用，注意磁盘 |
| Retention | 日志保留 | 72h | 避免日志把 local-path 打满 |

### 3.1 为什么钉到 agent-1

server-1 承担 control-plane + etcd，当前 CPU/内存已高。把 Loki/Grafana 放到 agent-1 可以避免控制面被日志组件挤压。Promtail 必须全节点运行，否则采不到 server-1 上的系统 Pod 日志，但它是轻量 agent。

### 3.2 资源与端口规划

```text
Grafana NodePort: 30301  (仓库 addons/monitoring 里 Grafana 用 30300)
Loki Service:     loki.logging.svc.cluster.local:3100
Namespace:        logging
```

为本章创建轻量 values（示例放 `/tmp/opencode/ch49/`，不必入库）：

### 4.1 `loki-values.yaml`

```yaml
deploymentMode: SingleBinary

loki:
  auth_enabled: false
  commonConfig:
    replication_factor: 1
  storage:
    type: filesystem
  schemaConfig:
    configs:
      - from: "2024-01-01"
        store: tsdb
        object_store: filesystem
        schema: v13
        index:
          prefix: index_
          period: 24h
  limits_config:
    retention_period: 72h
    allow_structured_metadata: true
    volume_enabled: true
  compactor:
    retention_enabled: true
    delete_request_store: filesystem

singleBinary:
  replicas: 1
  nodeSelector:
    kubernetes.io/hostname: k3s-demo-agent-1
  resources:
    requests:
      cpu: 100m
      memory: 256Mi
    limits:
      cpu: 500m
      memory: 768Mi
  persistence:
    enabled: true
    storageClass: local-path
    size: 5Gi

# Disable scalable/simple-scalable targets
backend:
  replicas: 0
read:
  replicas: 0
write:
  replicas: 0

# Disable caches for lightweight lab
chunksCache:
  enabled: false
resultsCache:
  enabled: false

gateway:
  enabled: false
minio:
  enabled: false

test:
  enabled: false
lokiCanary:
  enabled: false
```

关键点：

- `auth_enabled: false`：实验单租户；生产多租户要打开并规划 tenant。
- `SingleBinary + replication_factor: 1`：最小部署，不是 HA。
- `retention_period: 72h` + compactor：避免 local-path 被日志填满。
- `chunksCache/resultsCache` 关闭：减少组件数，牺牲查询性能。

### 4.2 `promtail-values.yaml`


## 6. 验证日志链路

### 6.1 Loki ready 检查

```bash
kubectl -n logging port-forward svc/loki 3100:3100
curl -s http://127.0.0.1:3100/ready
```

期望看到 `ready`。

### 6.2 写入一条测试日志

```bash
curl -H "Content-Type: application/json" -XPOST -s \
  "http://127.0.0.1:3100/loki/api/v1/push" \
  --data-raw "{\"streams\": [{\"stream\": {\"job\": \"ch49-test\"}, \"values\": [[\"$(date +%s)000000000\", \"hello-loki\"]]}]}"
```

查询：

```bash
curl -G -s "http://127.0.0.1:3100/loki/api/v1/query_range" \
  --data-urlencode 'query={job="ch49-test"}' \
  --data-urlencode 'limit=5' | jq .data.result
```

### 6.3 查真实 Pod 日志（LogQL）

Grafana 地址：`http://192.168.56.10:30301`（NodePort 落到任一节点 IP 都可），账号 `admin/admin`。

常用 LogQL：

```logql
# 查看某 namespace 最近日志
{namespace="kube-system"}

# 查看某 Pod
{namespace="logging", pod=~"loki.*"}

# 关键字过滤（内容匹配，注意性能）
{namespace="kube-system"} |= "error"

# 不区分大小写
{namespace="kube-system"} |~ "(?i)error|warn|fail"

# 排除噪音
{namespace="kube-system"} |= "error" != "context canceled"

# 统计每分钟错误日志数
sum(count_over_time({namespace="kube-system"} |= "error" [1m]))
```

## 7. 排查报错的实战套路

### 7.1 Pod 启动失败 / CrashLoop

```bash
kubectl -n <ns> get pods
kubectl -n <ns> describe pod <pod>
```

Grafana Explore / LogQL：

```logql
{namespace="<ns>", pod="<pod>"}
```

如果要看重启前日志，仍用 kubectl：

```bash
kubectl -n <ns> logs <pod> --previous --tail=100
```

### 7.2 按 namespace 看最近错误

```logql
{namespace="lab"} |~ "(?i)error|exception|panic|fail"
```

先缩小标签范围（namespace/pod/container），再做 `|=`/`|~` 内容过滤。不要一上来 `{job=~".+"} |= "error"` 全集群扫。

### 7.3 与告警/审计联动

- **47 告警触发**：先在 Grafana/Prometheus 看时间窗口和对象，再跳 Loki 用同一 namespace/pod/time range 查日志。
- **36 Runbook**：把 LogQL、时间窗口、关键日志行贴到 Runbook 证据区。
- **55 审计**：如果是 Secret/RBAC/资源被改动导致故障，日志只能看到应用症状，审计日志才能看到“谁改了什么”。

```logql
# 示例：某 namespace 在 15m 内的 error 日志
{namespace="<ns>"} |= "error"
```

```bash
# 审计侧补充证据（启用 55 章后）
vagrant ssh k3s-demo-server-1 -c "sudo grep '<resource-name>' /var/lib/rancher/k3s/server/logs/audit.log | tail -n 20"
```

### 7.4 按节点/组件排查

Promtail 会采集全节点 Pod 日志，因此 server-1 上的 control-plane 组件日志也能查：

```logql
{namespace="kube-system"} |~ "k3s|etcd|apiserver" |~ "(?i)error|warn"
```

### 7.5 Loki 自己出问题

```bash
kubectl -n logging get pods
kubectl -n logging logs statefulset/loki -c loki --tail=100
kubectl -n logging describe pvc
kubectl top pods -n logging
```

常见问题：

| 现象 | 原因 | 处理 |
|------|------|------|
| `readiness probe failed: 503` | Loki 刚启动，尚未 ready | 等 1-2 分钟；看 logs 确认无报错 |
| Promtail `ContainerCreating` 久 | 镜像拉取慢/失败 | `describe pod` 看事件；按镜像源策略处理 |
| 查询慢/超时 | 标签范围太大、全量 regex | 先按 namespace/pod 缩小，再过滤内容 |
| PVC Pending | local-path provisioner 异常或磁盘问题 | `kubectl -n logging describe pvc`、查 node 磁盘 |
| 日志缺失 | Promtail 没跑在该节点 / client URL 错 | 查 Promtail DaemonSet、targets、日志 |

### 7.6 常见坑

| 现象 | 原因 | 处理 |
|------|------|------|
| Grafana Explore 没数据 | Loki datasource 配置错误、时间范围不对、标签选择过窄 | 检查 datasource URL `http://loki:3100`；扩大时间范围；先用 `{namespace="kube-system"}` 验证 |
| Promtail Running 但查不到日志 | `/var/log/pods` 挂载/权限问题、`__path__` 不匹配 | `kubectl -n logging logs ds/promtail`；检查 volumeMount 和 scrape config |
| 查询很慢或 OOM | 标签高基数、全量 regex、时间窗口过大 | 先限定 namespace/pod/container，再用 `|=`/`|~`；避免 `{job=~".+"}` |
| Chart 下载超时 | GitHub release asset 网络受限 | 先本地下载 tgz，再 `helm upgrade --install ... ./chart.tgz` |
| `admin/admin` 被滥用 | 实验默认密码 | 仅实验使用；生产改 Secret、SSO 或随机密码，并限制 NodePort 暴露面 |

## 8. 生产化注意事项

本章是**轻量实验方案**，不是生产 HA 方案：

- **SingleBinary + 1 副本**：Loki Pod 或 agent-1 挂了，日志查询不可用。
- **local-path**：节点盘故障会丢日志；生产应使用可靠存储或对象存储（S3/MinIO）。
- **Promtail**：已进入维护模式，生产新项目可评估 Grafana Alloy / Fluent Bit / Vector。
- **保留期**：72h 仅演示；生产要按合规、磁盘、对象存储成本设置。
- **多租户/鉴权**：本章 `auth_enabled: false`；生产应启用租户与 Grafana 权限控制。
- **告警联动**：日志告警可用 Loki ruler 或 Grafana Alerting；本章先不加，避免增加资源。

## 9. 动手练习

1. **LogQL 定位**：在 Grafana Explore 用 `{namespace="kube-system"} |= "error"` 查最近 15 分钟日志，再缩小到具体 Pod，记录你缩小范围的过程。
2. **联动 Runbook**：模拟一个 Pod 重启告警，按 47（告警/Dashboard）→ 49（LogQL）→ 55（audit log，如涉及配置变更）写一条 36 Runbook 证据链。
3. **标签基数判断**：解释为什么 `pod` 适合作为标签，而请求 ID 不适合；给出一个“高基数标签导致 Loki 变慢”的排查思路。

## 10. 清理

```bash
# 卸载 Helm releases
KUBECONFIG=./kubeconfig helm uninstall grafana -n logging
KUBECONFIG=./kubeconfig helm uninstall promtail -n logging
KUBECONFIG=./kubeconfig helm uninstall loki -n logging

# 删除 PVC（会删除本地日志数据）
kubectl -n logging delete pvc --all

# 删除 namespace
kubectl delete ns logging --ignore-not-found
```

如需保留 Loki 历史日志，不要删除 PVC。

## 11. 小结

- 日志栈最小闭环：**Promtail 采集 → Loki 存储/索引 → Grafana/LogQL 查询**。
- Loki 轻量的关键是**标签索引、内容不全索引**；查询时先缩小标签范围。
- 资源紧张集群要把重组件钉到空闲节点，并限制保留期、PVC 大小、requests/limits。
- 本章实操验证了“轻量可用”；生产化还要考虑 HA、对象存储、鉴权、告警和采集器演进（Alloy/Vector）。
