## 2. local-path 到底是什么，不是什么

`local-path` 是 k3s 默认带的 Local Path Provisioner。它在 PVC 被 Pod 调度后，在目标节点本地目录创建卷目录，并通过 hostPath/local PV 形式挂给 Pod。

### 2.1 它擅长什么

- **轻量**：无额外存储集群组件，适合实验、边缘、单节点、开发环境。
- **简单**：开箱即用，`WaitForFirstConsumer` 让卷跟着 Pod 落到同一节点。
- **够用**：对于不要求跨节点漂移的有状态应用，能快速跑通 PVC 流程。

### 2.2 它不擅长什么

- **不跨节点迁移数据**：Pod 漂移到另一节点时，原节点目录里的数据不会自动跟过去。
- **节点故障即数据可用性风险**：节点盘坏、VM 丢失、目录误删，数据就危险。
- **不是共享文件系统**：默认不提供 RWX 多节点共享语义。
- **备份不是内建能力**：必须配合快照、文件备份、应用级备份（第 48 章）。

### 2.3 关键配置含义

| 字段 | local-path 实测值 | 含义 |
|---|---|---|
| `provisioner` | `rancher.io/local-path` | 由 Local Path Provisioner 动态创建 PV |
| `volumeBindingMode` | `WaitForFirstConsumer` | 等 Pod 调度后再绑定，避免卷绑错节点 |
| `reclaimPolicy` | `Delete` | PVC 删除后 PV/底层目录按策略清理（需谨慎） |
| `allowVolumeExpansion` | `false` | 不支持在线扩容；改容量通常需要迁移数据 |

> 教学经验：`WaitForFirstConsumer` 是 local-path 的关键保护。没有它，PVC 可能先在错误节点建卷，Pod 再也调度不过去。

## 3. 存储选型四问

选存储前先问这四个问题，比直接装 Longhorn 更重要：

1. **数据能不能丢？** 能丢的是缓存/临时数据；不能丢就要备份、复制、恢复演练。
2. **Pod 能不能固定节点？** 能固定，local-path 可能够用；要跨节点漂移，需要网络存储或复制存储。
3. **需要什么访问模式？** RWO（单节点读写）最常见；RWX（多节点共享读写）要 NFS/CephFS 等。
4. **团队能运维多复杂的存储？** 分布式存储不是“装上就有 HA”，它本身是需要监控、扩容、升级、故障处理的系统。

## 4. 常见方案对比

| 方案 | 典型能力 | 优点 | 缺点/风险 | 适用场景 |
|---|---|---|---|---|
| **local-path / hostPath** | 节点本地 RWO | 最轻量、简单、快 | 不跨节点、节点故障风险、扩容/迁移弱 | 实验、单机、边缘、可容忍节点绑定 |
| **NFS / NAS** | 网络共享，常见 RWX | 简单易懂，已有 NAS 时接入快 | NFS 服务端成关键依赖；性能/锁语义/权限要评估 | 共享文件、读多写少、传统 NAS 环境 |
| **Longhorn** | Kubernetes 原生分布式块存储 | UI/备份/快照/复制较友好，K8s 体验好 | 资源开销明显；网络/磁盘/节点稳定性要求高 | 小中型 K8s，需要副本和卷管理 |
| **Rook-Ceph** | 块/文件/对象全家桶 | 能力强、扩展性好 | 复杂度高，运维门槛高，资源要求高 | 有存储团队、较大规模、多种存储需求 |
| **云盘/云存储 CSI** | 云厂商块存储/文件存储 | 与云平台集成好、运维负担低 | 依赖云厂商、成本模型不同、离线环境不适用 | 公有云生产集群 |
| **local PV + 应用自身复制** | 例如数据库主从/集群 | 性能好，可靠性交给应用 | 应用复杂，需要懂数据库复制 | Redis/Postgres/etcd/Kafka 等有复制能力的系统 |

### 快速选型建议

- **教学/PoC/单节点**：local-path。
- **已有 NAS、需要 RWX**：NFS CSI/Subdir Provisioner。
- **小型 K8s 想要卷复制和快照 UI**：评估 Longhorn，但先算资源。
- **大型平台、多租户、多存储类型**：评估 Rook-Ceph 或商业存储。
- **数据库类**：优先考虑应用自身高可用 + 备份，不要迷信“存储有副本就万事大吉”。

## 5. 本实验集群的现实约束

当前环境：双节点，各 2c/4GB，已有 Rancher/Kyverno/Gateway 等组件，server-1 负载长期偏高。

| 方案 | 在当前集群建议 | 原因 |
|---|---|---|
| local-path | **继续保留** | 已稳定、轻量、章节依赖多 |
| NFS | **可作为下一步轻量实验** | 需要外部 NFS 服务或单独 VM；集群内组件压力较小 |
| Longhorn | **暂不实装** | 控制器、引擎、副本、快照、CSI 组件较多；双节点 2c/4GB 容易雪上加霜 |
| Rook-Ceph | **不建议** | 复杂度和资源需求远超当前实验规模 |

> 结论：第 54 章以“选型与边界”为主，不在当前集群强行安装 Longhorn。生产/资源充足环境再做独立实装章。

## 6. local-path 运维要点

### 6.1 数据目录与节点绑定

local-path 默认目录：`/var/lib/rancher/k3s/storage`。每个 PV 会在节点本地创建子目录。

排查时关注：

```bash
kubectl --kubeconfig ./kubeconfig get pv -o wide
kubectl --kubeconfig ./kubeconfig describe pvc <name> -n <ns>
vagrant ssh k3s-demo-server-1 -c "sudo ls /var/lib/rancher/k3s/storage | head"
```

### 6.2 Pod 漂移陷阱

StatefulSet 配合 local-path 时，Pod 通常会被绑定到已有 PV 所在节点。看起来“漂移失败”，其实是存储在保护数据一致性。

处理方式：

- 接受节点绑定：适合实验环境。
- 迁移数据：备份恢复到新卷。
- 换存储方案：需要跨节点漂移时选网络存储/复制存储。

### 6.3 ReclaimPolicy 风险

`Delete` 意味着 PVC 删除后底层卷可能被回收。生产重要数据可考虑：

- 关键 PV 使用 `Retain`；
- 删除前做备份；
- 用 GitOps/审计控制 PVC 删除权限。

### 6.4 扩容与迁移

local-path 不支持在线扩容（实测 `allowVolumeExpansion: false`）。常见迁移路径：

1. 新建更大的 PVC。
2. 用 Job/rsync/应用工具复制数据。
3. 切换 Deployment/StatefulSet 挂载。
4. 验证后再删除旧 PVC。

## 7. 走向生产时的检查清单

- [ ] 明确 RWO/RWX/ROX 访问模式需求。
- [ ] 明确 RPO/RTO：允许丢多少数据、多久恢复。
- [ ] 存储有备份，且备份做过恢复演练（第 48 章）。
- [ ] StorageClass 的 reclaim、binding、expansion 行为被团队理解。
- [ ] 监控容量、inode、延迟、IOPS、重建状态。
- [ ] 节点磁盘独立规划，不与系统盘混用到危险水位。
- [ ] 变更有回滚：扩容、迁移、升级前先快照/备份。

## 9. 小结

- local-path 是 k3s 教学和轻量场景的好默认值，但它不是高可用共享存储。
- 存储选型先看数据重要性、节点漂移、访问模式和运维能力，再决定是否上 NFS/Longhorn/Ceph。
- 当前双节点实验集群适合继续使用 local-path；Longhorn/Rook-Ceph 等重型方案应在资源充足、目标明确时再实装。
