```text
deployment.apps/nginx-demo   5/5   5   5   ...   nginx:latest
deployment.apps/probe-demo   2/2   2   2   ...   nginx:latest
deployment.apps/sched-demo   0/2   2   0   ...   nginx:latest   ← Pod 卡在 agent 拉镜像（环境镜像源抖动）

ingress.networking.k8s.io/nginx-ing   nginx   lab.k3s.local   10.43.197.40   80

persistentvolumeclaim/nginx-data   Bound   pvc-6172...   1Gi   RWO   local-path
```

**排障任务**：`sched-demo` 为什么 0 可用？用第 08 章的方法定位：

```bash
kubectl -n lab get pods | grep sched-demo
kubectl -n lab describe pod -l app=sched-demo | grep -A5 'Events:'
kubectl get events -n lab --sort-by=.lastTimestamp | grep -i sched
```

结论方向：Pod 已成功调度到 agent-1（NODE 列有值），卡在镜像拉取（离线环境常见）。改用 `imagePullPolicy: IfNotPresent` + 节点已有镜像可解（第 03 章）。

## 实验二：从零重建一个「完整应用」（核心实验）

目标：把前面学的所有东西串起来 —— 用 YAML 一次性定义 Deployment + Service + Ingress + ConfigMap + PVC。

```yaml
# full-app.yaml  —— 完整应用定义（一个文件全搞定）
apiVersion: v1
kind: Namespace
metadata:
  name: app
---
apiVersion: v1
kind: ConfigMap
metadata:
  name: demo-config
  namespace: app
data:
  index.html: |
    <h1>Hello from K8s Tutorial Lab</h1>
    <p>env: test</p>
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
  namespace: app
spec:
  replicas: 2
  selector:
    matchLabels: { app: web }
  template:
    metadata:
      labels: { app: web }
    spec:
      nodeSelector:
        kubernetes.io/hostname: k3s-demo-server-1
      containers:
        - name: nginx
          image: nginx:latest
          imagePullPolicy: IfNotPresent
          ports:
            - containerPort: 80
          readinessProbe:
            httpGet: { path: /, port: 80 }
            initialDelaySeconds: 3
            periodSeconds: 5
          volumeMounts:
            - name: html
              mountPath: /usr/share/nginx/html
      volumes:
        - name: html
          configMap:
            name: demo-config
---
apiVersion: v1
kind: Service
metadata:
  name: web-svc
  namespace: app
spec:
  selector: { app: web }
  ports:
    - port: 80
      targetPort: 80
---
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: web-ing
  namespace: app
spec:
  ingressClassName: nginx
  rules:
    - host: web.k3s.local
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: web-svc
                port: { number: 80 }
```

```bash
kubectl apply -f full-app.yaml
kubectl -n app rollout status deployment/web --timeout=90s
```

**验证链路**（从外到内）：

```bash
# 1) Ingress 入口（域名带自定义页面 == ConfigMap 生效）
curl -s -H "Host: web.k3s.local" http://192.168.56.10:30080/
# 预期: <h1>Hello from K8s Tutorial Lab</h1> ...

# 2) Service 名 DNS 解析（在容器里）
kubectl -n app exec deploy/web -- curl -s -o /dev/null -w "%{http_code}\n" http://web-svc.app/
# 预期: 200

# 3) 端到端路径确认
kubectl -n app get ingress web-ing
kubectl -n app get endpoints web-svc
```

这个实验一次覆盖了：Namespace、ConfigMap、Deployment、Probe、Service、Ingress、DNS 七种对象。**能独立完成并讲清楚每一步 = 前 06 章合格**。

## 实验三：故障演练 —— 自愈与就绪探针（15 分钟）

```bash
# 1) 杀掉一个 web Pod，看 Deployment 是否自动重建
WEB_POD=$(kubectl -n app get pod -l app=web -o name | head -1)
kubectl -n app delete $WEB_POD
kubectl -n app get pods          # 观察新 Pod 出现，旧 Pod 没有名字重复

# 2) 破坏就绪探针：更新 deployment 的 readiness path 为 /notfound
kubectl -n app set env deployment/web --dry-run=client -o yaml >/dev/null  # 示意
# 实际修改 YAML 后：
#   kubectl apply -f <改过的 yaml>
# 观察 READY 0/1 → Service 摘流量 → curl 返回 502/503

# 3) 恢复
```

演练目的：理解「为什么 deployment 能自愈」「为什么探针失败服务不报错而是摘除」。

## 实验六：清理（结束必做）

```bash
kubectl delete ns app
kubectl delete ns lab            # ⚠️ 连带删除 lab 下所有资源（含 PVC 数据）
kubectl delete pv --all          # 若还残留
kubectl -n lab delete hpa sched-demo    # HPA 在 ns 删除时一并删除
```

> `lab` 与 `app` 都是练习命名空间，全部删掉不影响集群其他部分（Rancher/cert-manager/ingress 都在各自命名空间）。**PVC 删除默认会连数据一起删**（local-path Delete 策略），确认没有要保留的数据再清理。

## 参考答案要点

- sched-demo 不可用：调度已完成（NODE 有值），卡镜像拉取 → `get events`/`describe` 定位 → `imagePullPolicy: IfNotPresent` 或导入镜像解决。
- 自愈：ReplicaSet 控制器 watch 到副本数不足自动补建。
- 探针失败：readiness 失败摘流量（Pod 仍 Running），Service 返回 502/503；liveness 失败重启容器。
- RBAC：Role 只作用绑定它的命名空间；集群级要用 ClusterRoleBinding。
