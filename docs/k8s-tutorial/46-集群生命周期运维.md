# 46 集群生命周期运维：扩容、缩容与升级

## 章节信息

| 项目 | 内容 |
|------|------|
| 适用平台 | Linux / macOS（标准路径）；Windows（ops VM 路径，Vagrant 生命周期在宿主机，`k3s-ops.sh` 在 ops VM 内执行） |
| 前置章节 | 00/03/08/10/12/38/45 |
| 预计耗时 | 60-90 分钟 |
| 破坏性操作 | 中-高：`add-node/remove-node/upgrade/restore` 会改变集群状态；务必先备份、确认节点名、按流程执行 |
| 实测环境 | k3s v1.30.2+k3s2，见 [00-README](00-README.md) |

## 本章目标

- 理解 `k3s-ops.sh` 在本项目中的生命周期职责边界
- 掌握节点扩容、缩容、升级、备份恢复的标准流程
- 能把 `vagrant/nodes.yml`、Vagrant、Ansible playbook、kubectl 状态串成一条运维链路
- 知道哪些操作安全可反复做，哪些操作必须先备份和确认影响范围

---

## 1. 为什么需要这一章

前面的章节大多在讲 **Kubernetes 对象怎么工作**；这一章补上 **这个仓库怎么管理 k3s 集群生命周期**。

本项目的关键事实：

- **拓扑定义**在 `vagrant/nodes.yml`（标准路径）或 `win/nodes.windows.yml`（Windows 路径）。
- **VM 生命周期**由 Vagrant 管理：`up/down/destroy`。
- **k3s 生命周期**由 `k3s-ops.sh` + Ansible playbook 管理：`install/add-node/remove-node/upgrade/backup/restore`。
- **kubectl 视角**是最终验收：节点 Ready、Pod 正常、版本符合预期、etcd 快照存在。

> 一句话：**改拓扑不等于改集群，改集群不等于删 VM**。生命周期操作要按顺序做。

## 2. 命令全景与职责边界

### 2.1 `k3s-ops.sh` 命令分层

```bash
./k3s-ops.sh
```

实测输出（节选）：

```text
Usage: k3s-ops.sh <command> [options]

Commands:
  init                       检查环境依赖
  up [node]                  vagrant up（可选指定节点）
  down [node] [options]      关闭 VM 释放资源（-f 强制关机 / -s 挂起）
  install                    首次完整安装 k3s 集群
  add-node <node>            将新节点加入集群
  remove-node -n <name>      移除指定节点
  upgrade -v <version>       升级 k3s 版本
  backup                     etcd 快照备份
  restore -f <snapshot>      从快照恢复
  deploy-rancher             部署 Rancher UI
  reset-rancher-admin        重置 Rancher admin 密码
  deploy-ingress             部署 nginx-ingress
  status                     集群健康检查
  destroy                    销毁所有 VM
  ssh <node>                 SSH 到指定节点
  kubeconfig [node]          获取 kubeconfig
```

### 2.2 职责边界

| 层面 | 工具 | 典型操作 | 不负责 |
|------|------|----------|--------|
| VM 生命周期 | Vagrant / `k3s-ops.sh up/down/destroy` | 创建、启动、停止、销毁 VM | 不安装 k3s，不处理 Kubernetes 节点对象 |
| 集群生命周期 | `k3s-ops.sh` + Ansible | install/add/remove/upgrade/backup/restore | 不自动修改 `nodes.yml` 设计意图 |
| 集群状态观察 | kubectl / Rancher | 节点、Pod、事件、资源 | 不直接变更 VM |
| 设计事实源 | `vagrant/nodes.yml`、`docs/architecture.md` | 拓扑、版本、网络、组件 | 不是运行时状态 |

## 4. 扩容节点（add-node）

### 4.1 标准流程

```text
1. 编辑 vagrant/nodes.yml（新增节点定义）
2. ./k3s-ops.sh up <node>        # 创建并启动 VM
3. ./k3s-ops.sh add-node <node>  # 安装 k3s agent/server 并加入集群
4. kubectl get nodes -o wide     # 验收
```

### 4.2 nodes.yml 示例（新增 agent）

```yaml
  - name: agent-2
    role: agent
    ip: 192.168.56.21
    cpus: 2
    memory: 4096
```

### 4.3 实际执行的命令链

从 `k3s-ops.sh` 可见：

- `add-node <node>` 会 `resolve_host` 解析短名/完整主机名；
- 读取节点角色；
- `role=server` 时运行 `k3s-add-server.yml -l <full_host>`；
- `role=agent` 时运行 `k3s-add-agent.yml -l <full_host>`。

也就是说，**add-node 只对目标节点执行加入流程**，不是全量重装。

### 4.4 验收清单

```bash
kubectl get nodes -o wide
kubectl get pods -A -o wide | grep <node>
kubectl describe node <node-name>
```

关注点：

- `STATUS=Ready`
- `VERSION` 与集群一致
- `INTERNAL-IP` 与 `nodes.yml` 一致
- 节点无 `NotReady`/`DiskPressure`/`MemoryPressure`

### 4.5 常见坑

- **只改 nodes.yml 不执行 add-node**：VM 可能已存在，但还没加入 k3s。
- **对已加入节点重复 add-node**：可能重启该节点 k3s 服务，属预期风险；应先确认节点状态。
- **忘记镜像架构**：Apple Silicon/arm64 环境要确认镜像为 `linux/arm64` 或 multi-arch。

## 5. 缩容节点（remove-node）

### 5.1 标准流程

```text
1. ./k3s-ops.sh remove-node -n <node>   # cordon/drain/delete + 从集群移除
2. kubectl get nodes                    # 确认节点对象已消失
3. vagrant destroy -f <full-host>       # 销毁 VM（可选但通常需要）
4. 从 vagrant/nodes.yml 删除节点定义    # 保持拓扑事实源干净
```

### 5.2 真实命令行为

`remove-node` 实际调用：

```bash
run_playbook "k3s-remove-node.yml" -l "${full_host}"
```

脚本最后会提示：

```text
You can now run: vagrant destroy ${full_host}
```

这说明 **remove-node 不会自动 destroy VM**。这是刻意的安全边界：先从 Kubernetes 控制面安全摘除，再由操作者决定是否销毁虚拟机。

### 5.3 ⚠️ 缩容前检查

```bash
kubectl get nodes -o wide
kubectl get pods -A -o wide | grep <node-name>
kubectl drain <node-name> --dry-run=client --ignore-daemonsets --delete-emptydir-data
```

检查项：

- 节点上是否有单副本关键业务？
- 是否有本地数据（emptyDir/local-path PV）？
- 是否有 PDB 阻止驱逐？（见第 38 章）
- 如果缩的是 server，要考虑 etcd 仲裁与最小 server 数量。

### 5.4 验收

```bash
kubectl get nodes
./k3s-ops.sh status
```

确认被移除节点不再出现在 `kubectl get nodes` 中，再决定是否 `vagrant destroy`。

## 6. 升级 k3s（upgrade）

### 6.1 标准流程

```text
1. 备份：./k3s-ops.sh backup
2. 检查当前版本：kubectl get nodes -o wide
3. 升级：./k3s-ops.sh upgrade -v v1.31.x+k3s1
4. 验收：kubectl get nodes -o wide && ./k3s-ops.sh status
5. 验证业务：关键 Pod/Ingress/Rancher 可用
```

### 6.2 命令行为

`upgrade` 实际调用：

```bash
run_playbook "k3s-upgrade.yml" -e "k3s_upgrade_version=${version}"
```

说明升级版本通过 extra var 传入，不是只改 `nodes.yml` 的展示字段。升级完成后，应同步检查 `vagrant/nodes.yml` 中的 `k3s_version` 是否需要更新，避免配置事实源漂移。

### 6.3 ⚠️ 升级注意事项

- **先备份 etcd**：`./k3s-ops.sh backup`。
- **先看 release notes**：尤其是跨 minor 版本升级。
- **不要跳太多版本**：按 Kubernetes/k3s 官方支持路径升级。
- **关注组件兼容性**：Rancher、Ingress、Gateway、Kyverno、监控栈可能有版本约束。
- **升级后验收**：节点版本、系统 Pod、业务 Pod、Ingress、证书、存储。

```bash
kubectl get nodes -o wide
kubectl get pods -A
kubectl get events -A --sort-by=.lastTimestamp | tail -n 30
```

## 7. 备份与恢复（backup / restore）

### 7.1 备份

```bash
./k3s-ops.sh backup
```

实际调用 `k3s-backup.yml`，用于创建 etcd 快照备份。日常运维建议：

- 升级前备份
- 重大变更前备份
- 定期备份并异地拷贝快照文件

### 7.2 恢复

```bash
./k3s-ops.sh restore -f <snapshot_file>
```

实测代码行为：

- 缺少 `-f` 会报 usage；
- 执行前会打印 warning；
- 要求交互确认 `Continue? [y/N]`；
- 确认后调用 `k3s-restore.yml -e snapshot_file=...`。

```text
Restoring from snapshot: <snapshot_file>
This will stop all server nodes and restart the cluster!
Continue? [y/N]
```

> ⚠️ 恢复是高风险操作。它影响整个集群控制面状态，不是“恢复一个 Pod”。务必在维护窗口、已确认快照来源、已评估数据回滚影响后执行。

### 7.3 恢复后验收

```bash
kubectl get nodes
kubectl get pods -A
kubectl get csidrivers,storageclass
./k3s-ops.sh status
```

必要时还要验证 Rancher、Ingress、Gateway、业务数据与 PVC 绑定关系。

## 8. 本项目推荐的生命周期 Runbook

| 场景 | 推荐顺序 | 验收 |
|------|----------|------|
| 新增 agent | 编辑 nodes.yml → `up` → `add-node` | `kubectl get nodes -o wide` |
| 移除 agent | `remove-node -n` → 确认节点消失 → `vagrant destroy` → 清理 nodes.yml | `kubectl get nodes` |
| 升级 k3s | `backup` → `upgrade -v` → 验证业务 → 更新 nodes.yml 版本 | nodes 版本 + pods 状态 |
| 关闭实验环境 | `down` / `down -s` | VM 已停止/挂起 |
| 重建环境 | `destroy` → `up` → `install` → 部署 addon → `kubeconfig` | `status` 全绿 |

## 9. Rancher / kubectl 对照

- **节点列表**：Rancher → Cluster → Nodes；等价于 `kubectl get nodes -o wide`。
- **节点排空/封锁**：Rancher Node 菜单可做 Cordon/Drain；CLI 对应 `kubectl cordon/drain/uncordon`。
- **系统 Pod**：Rancher → Workloads / Pods（所有命名空间）；CLI 对应 `kubectl get pods -A`。
- **事件**：Rancher → Cluster → Events；CLI 对应 `kubectl get events -A --sort-by=.lastTimestamp`。

Rancher 适合看状态和做简单运维；涉及本仓库拓扑事实源、Ansible 编排、Vagrant 生命周期时，应以 `k3s-ops.sh` + `nodes.yml` 为准。

---

## 10. 小结

- `nodes.yml` 是拓扑事实源，`k3s-ops.sh` 是生命周期入口，`kubectl` 是最终验收。
- 扩容：**先 VM，后加入集群**；缩容：**先从集群移除，后销毁 VM**。
- 升级和恢复都是高风险操作：先备份、再执行、后验收。
- `remove-node` 不会自动删除 VM；`restore` 会要求确认；这些都是安全边界，不要绕过。

<summary>参考答案要点</summary>

1. 以实际输出为准；当前实测为 server-1/agent-1 Ready，v1.30.2+k3s2。
