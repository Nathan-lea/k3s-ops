# 46 集群生命周期运维：标准流程与 k3s-ops 实践

## 章节信息

| 项目 | 内容 |
|------|------|
| 适用平台 | Linux / macOS（标准路径）；Windows（ops VM 路径，Vagrant 生命周期在宿主机，`k3s-ops.sh` 在 ops VM 内执行） |
| 前置章节 | 00/03/08/10/12/38/45 |
| 预计耗时 | 60-120 分钟 |
| 破坏性操作 | 中-高：扩容/缩容/升级/恢复会改变集群状态；销毁 VM 不可逆。务必先备份、确认节点名、确认影响范围。 |
| 实测环境 | k3s v1.30.2+k3s2，双节点（server-1 192.168.56.10，agent-1 192.168.56.20），见 [00-README](00-README.md) |

## 本章目标

- 区分 **通用标准生命周期操作** 与 **本仓库 `k3s-ops.sh` 封装**，避免把项目脚本误当成 k3s 标准。
- 掌握 Day-0/Day-1/Day-2 常见动作：初始化、安装、扩容、缩容、升级、备份恢复、状态检查、部署组件、关停销毁。
- 能把 `vagrant/nodes.yml`、Vagrant、Ansible、k3s systemd、kubectl 串成一条可验收的运维链路。
- 知道每个操作的验收点、风险点和回退思路。

> **边界声明**：`k3s-ops.sh` 是本仓库的自动化入口，适合本项目 Vagrant+Ansible+k3s 实验环境；它封装的是 k3s/Kubernetes/Helm/systemd 等通用能力，不替代上游文档。离开本仓库时，应优先参考对应的标准命令。

## 1. 生命周期全景

```text
Day-0 准备        Day-1 变更              Day-2 运维
init/up/install   add/remove/upgrade      backup/restore/status
kubeconfig        deploy-*                logs/events/drain
                  config change           down/destroy
        \______________|____________________/
                       kubectl 验收
```

| 层面 | 通用标准工具 | 本仓库封装/事实源 | 验收 |
|------|-------------|------------------|------|
| VM 生命周期 | VirtualBox/Vagrant/云 API/物理机装机 | `vagrant/nodes.yml`、`k3s-ops.sh up/down/destroy` | VM 运行、SSH 可达 |
| k3s 安装与节点 | k3s install script、`/etc/rancher/k3s/config.yaml`、systemd | `k3s-ops.sh install/add-node/remove-node`、Ansible roles | `kubectl get nodes` |
| 版本升级 | install script + `INSTALL_K3S_VERSION`、system-upgrade-controller | `k3s-ops.sh upgrade -v` | 节点版本一致 |
| 备份恢复 | `k3s etcd-snapshot save/ls`、restore 流程 | `k3s-ops.sh backup/restore` | 快照存在、恢复后 API/数据正常 |
| 组件部署 | Helm/kubectl manifest | `k3s-ops.sh deploy-rancher/deploy-ingress` | Pod/Service/Ingress Ready |
| 状态观察 | kubectl、journalctl、crictl、Rancher | `k3s-ops.sh status` | 节点/Pod/事件健康 |

## 2. 命令矩阵（双轨对照）

| 生命周期 | 通用标准做法 | 本仓库封装 | 执行位置 | 破坏性 | 主要验收 |
|---|---|---|---|---|---|
| 环境检查 | 检查 vagrant/ansible/kubectl/helm/ssh 等版本 | `./k3s-ops.sh init` | 宿主机/ops VM | 低 | 依赖齐全 |
| 创建/启动 VM | `vagrant up [node]` | `./k3s-ops.sh up [node]` | 宿主机；Windows 宿主机用 `win/up.ps1` | 低-中 | `vagrant status`、SSH 可达 |
| 关闭/挂起 VM | `vagrant halt/suspend` | `./k3s-ops.sh down [-f|-s] [node]` | 宿主机 | 中 | VM stopped/saved |
| 首次安装 k3s | k3s install script + config.yaml + systemd | `./k3s-ops.sh install` | 宿主机/ops VM | 中 | nodes Ready、kubeconfig 可用 |
| 扩容节点 | 准备 VM → 安装 k3s server/agent → 加入集群 | `nodes.yml` + `up` + `add-node` | VM 由 Vagrant；安装由 k3s-ops | 中 | 新节点 Ready |
| 缩容节点 | drain → delete node → 停服务/清理 → 关/删 VM | `remove-node -n` + `vagrant destroy -f` | ops VM/宿主机 + 宿主机 | 高 | node 消失、Pod 迁移 |
| 升级 k3s | install script 指定版本 / system-upgrade-controller | `./k3s-ops.sh upgrade -v <ver>` | 宿主机/ops VM | 高 | `kubectl get nodes` 版本一致 |
| 备份 etcd | `k3s etcd-snapshot save` | `./k3s-ops.sh backup` | 宿主机/ops VM | 低 | `k3s etcd-snapshot ls` |
| 恢复 | k3s restore 流程（离线、停服务、恢复、重启） | `./k3s-ops.sh restore -f <snap>` | 宿主机/ops VM | 极高 | API 恢复、数据一致 |
| 健康检查 | `kubectl get nodes/pods/events`、组件检查 | `./k3s-ops.sh status` | 宿主机/ops VM | 低 | 无异常事件/Pod |
| 获取 kubeconfig | 从 server `/etc/rancher/k3s/k3s.yaml` 拉取并改 server 地址 | `./k3s-ops.sh kubeconfig [node]` | 宿主机/ops VM | 低 | `kubectl --kubeconfig` 可用 |
| SSH 到节点 | `ssh` / `vagrant ssh` | `./k3s-ops.sh ssh <node>` | 宿主机/ops VM | 低 | 登录成功 |
| 部署 Rancher/Ingress | Helm install/upgrade + values | `./k3s-ops.sh deploy-rancher/deploy-ingress` | 宿主机/ops VM | 中 | Pod/Service/证书就绪 |
| 销毁环境 | `vagrant destroy -f` | `./k3s-ops.sh destroy` | 宿主机 | 极高 | VM 删除 |

> Windows ops VM 路径：`up/down/destroy` 在 Windows 宿主机执行（`win/*.ps1`）；`install/add-node/remove-node/upgrade/backup/restore/deploy-*/status/ssh/kubeconfig` 在 `k3s-demo-ops` VM 内执行。

## 3. Day-0：准备、启动、安装

### 3.1 环境检查

**通用标准**：确认虚拟化、Vagrant、Ansible、kubectl、helm、ssh 等依赖满足要求；确认宿主机资源足够。

```bash
vagrant --version
ansible --version
kubectl version --client
helm version
```

**本仓库封装**：

```bash
./k3s-ops.sh init
```

**验收**：命令输出依赖正常；Windows 路径先看 `win/README.md`。

### 3.2 启动 VM

**通用标准**：按拓扑创建并启动节点 VM，保证网络互通、SSH 可达。

```bash
vagrant status
vagrant up
# 或指定节点
vagrant up k3s-demo-server-1
```

**本仓库封装**：

```bash
./k3s-ops.sh up
./k3s-ops.sh up k3s-demo-agent-1
```

**验收**：`vagrant status` 显示 running；`vagrant ssh <node> -c hostname` 正常。

### 3.3 首次安装 k3s

**通用标准**：在 server 节点安装 k3s（可 `cluster-init` 启用嵌入式 etcd），agent 通过 `K3S_URL` + `K3S_TOKEN` 加入；配置写入 `/etc/rancher/k3s/config.yaml`，由 systemd 管理。

```bash
# server 示例（通用思路）
curl -sfL https://get.k3s.io | sh -s - server --cluster-init
# agent 示例
curl -sfL https://get.k3s.io | K3S_URL=https://<server>:6443 K3S_TOKEN=<token> sh -s - agent
```

**本仓库封装**：

```bash
./k3s-ops.sh install
./k3s-ops.sh kubeconfig
./k3s-ops.sh status
```

`install` 会通过 Ansible playbook 应用 `k3s-server`/`k3s-agent` 角色，生成 config.yaml、安装 k3s、拉取 kubeconfig。

**验收**：

```bash
kubectl --kubeconfig ./kubeconfig get nodes -o wide
kubectl --kubeconfig ./kubeconfig get pods -A
```

## 4. Day-1：扩容、缩容、升级、组件部署

### 4.1 扩容节点

**通用标准**：

1. 准备新 VM/机器（CPU/内存/磁盘/网络/时间同步/内核参数满足要求）。
2. 配置 k3s 参数（server/agent、token、server URL、registry、disable 项）。
3. 安装 k3s 并启动服务。
4. 在控制面验收节点 Ready。

**本仓库封装**：

```bash
# 1) 编辑拓扑事实源
# vagrant/nodes.yml 或 win/nodes.windows.yml

# 2) 创建 VM
./k3s-ops.sh up k3s-demo-agent-2

# 3) 加入集群（新空节点）
./k3s-ops.sh add-node agent-2
```

**验收**：

```bash
kubectl --kubeconfig ./kubeconfig get nodes -o wide
kubectl --kubeconfig ./kubeconfig describe node k3s-demo-agent-2 | grep -A5 Conditions
```

**常见坑**：
- `add-node` 只用于**新起空节点**；对已加入节点重复执行会重启 k3s 服务。
- 节点名接受短名/完整名，由 `lib/nodes.sh` 统一解析；不要手写前缀拼接。
- 镜像架构不匹配：Apple Silicon/arm64 节点需要 `linux/arm64` 或 multi-arch 镜像。

### 4.2 缩容节点

**通用标准**：

```bash
kubectl drain <node> --ignore-daemonsets --delete-emptydir-data
kubectl delete node <node>
# 节点上停止/卸载 k3s-agent 或 k3s
# 最后再关机/删 VM
```

**本仓库封装**：

```bash
./k3s-ops.sh remove-node -n agent-2
# 确认 Kubernetes 节点已移除后，再销毁 VM
vagrant destroy -f k3s-demo-agent-2
```

**验收**：

```bash
kubectl --kubeconfig ./kubeconfig get nodes
kubectl --kubeconfig ./kubeconfig get pods -A -o wide | grep agent-2 || true
```

**风险**：
- 先确认无关键单副本有状态负载绑死该节点；必要时先备份 PV。
- 不要把“删 VM”和“删 Kubernetes Node”当成同一步。

### 4.3 升级 k3s

**通用标准**：

- 阅读 release notes，确认版本兼容和已知问题。
- 备份 etcd/关键数据。
- 逐节点升级，先 server 再 agent（或按官方 HA 策略）。
- 每步验收节点 Ready、核心组件正常、业务 Pod 恢复。

```bash
# 通用安装脚本升级思路
curl -sfL https://get.k3s.io | INSTALL_K3S_VERSION=v1.x.y+k3sN sh -s - server
```

生产多集群常见标准方案还有 **system-upgrade-controller**；本仓库当前封装是 Ansible 驱动的升级流程。

**本仓库封装**：

```bash
./k3s-ops.sh backup
./k3s-ops.sh upgrade -v v1.30.2+k3s2
./k3s-ops.sh status
```

**验收**：

```bash
kubectl --kubeconfig ./kubeconfig get nodes -o wide
kubectl --kubeconfig ./kubeconfig get pods -A
```

**风险**：
- 不要跳过备份。
- 不要在集群已有严重告警/NotReady 时升级。
- 资源紧张时升级窗口要拉长，避免控制面被驱逐或重启超时。

### 4.4 部署组件（Rancher / Ingress）

**通用标准**：使用 Helm/kubectl 部署组件，values 纳入版本管理，部署后检查 Pod、Service、Ingress、证书、Webhook。

```bash
helm repo add rancher-latest https://releases.rancher.com/server-charts/latest
helm upgrade --install rancher rancher-latest/rancher -n cattle-system --create-namespace -f values.yaml
```

**本仓库封装**：

```bash
./k3s-ops.sh deploy-ingress
./k3s-ops.sh deploy-rancher
./k3s-ops.sh reset-rancher-admin   # 仅在明确需要时
```

**验收**：

```bash
kubectl --kubeconfig ./kubeconfig get pods -A
kubectl --kubeconfig ./kubeconfig get svc -A | grep -E 'ingress|rancher'
```

## 5. Day-2：备份恢复、状态检查、关停销毁

### 5.1 备份

**通用标准**：

```bash
# k3s 内置 etcd 快照
sudo k3s etcd-snapshot save --name before-upgrade
sudo k3s etcd-snapshot ls
```

还要考虑 PV/应用级备份（见第 48 章），etcd 快照不等于所有数据都安全。

**本仓库封装**：

```bash
./k3s-ops.sh backup
```

**验收**：快照文件存在；记录快照名、时间、集群版本、操作人。

### 5.2 恢复

**通用标准**：恢复是高风险操作。通常需要停 k3s、恢复 snapshot、重启服务、检查数据一致性。多 server 嵌入式 etcd 恢复需严格按 k3s 官方流程。

**本仓库封装**：

```bash
./k3s-ops.sh restore -f <snapshot_file>
```

**验收**：

```bash
kubectl --kubeconfig ./kubeconfig get nodes
kubectl --kubeconfig ./kubeconfig get pods -A
# 关键业务数据抽样检查
```

> 详细实操、PV 备份恢复、验收清单见 [48 备份恢复演练](48-备份恢复演练.md)。

### 5.3 状态检查

**通用标准**：

```bash
kubectl get nodes -o wide
kubectl get pods -A
kubectl get events -A --sort-by=.lastTimestamp | tail -n 30
```

**本仓库封装**：

```bash
./k3s-ops.sh status
```

`status` 适合作为变更前后统一门禁：变更前先看基线，变更后再看是否回到健康状态。

### 5.4 关停与销毁

**通用标准**：临时释放资源用关机/挂起；彻底删除环境用 destroy。销毁前确认备份和数据保留需求。

**本仓库封装**：

```bash
./k3s-ops.sh down            # 优雅关机
./k3s-ops.sh down -s         # 挂起
./k3s-ops.sh down -f         # 强制关机
./k3s-ops.sh destroy         # 销毁所有 VM
```

## 6. k3s-ops.sh 命令速查

| 命令 | 标准等价 | 说明 | 主要风险 |
|---|---|---|---|
| `init` | 依赖检查 | 检查本地工具 | 无 |
| `up [node]` | `vagrant up` | 创建/启动 VM | 资源占用 |
| `down [-f|-s] [node]` | `vagrant halt/suspend` | 关机/挂起 | 未保存工作 |
| `install` | k3s install script + 配置 | 首次安装集群 | 覆盖配置/安装失败半状态 |
| `add-node <node>` | VM + k3s agent/server join | 新节点加入 | 对已有节点重复执行会重启服务 |
| `remove-node -n <node>` | drain/delete/清理 | 移除节点 | 数据丢失、服务中断 |
| `upgrade -v <ver>` | install script/system-upgrade | 升级 k3s | 版本不兼容、中断 |
| `backup` | `k3s etcd-snapshot save` | etcd 快照 | 快照未异地保存 |
| `restore -f <snap>` | k3s restore | 快照恢复 | 数据回滚、服务中断 |
| `deploy-rancher` | Helm install rancher | 部署 Rancher | 证书/资源/镜像问题 |
| `reset-rancher-admin` | Rancher 管理命令 | 重置 admin 密码 | 影响登录 |
| `deploy-ingress` | Helm install ingress-nginx | 部署 Ingress | 端口冲突/Webhook |
| `status` | kubectl/journalctl 检查 | 健康检查 | 只读 |
| `ssh <node>` | ssh/vagrant ssh | 登录节点 | 误操作 |
| `kubeconfig [node]` | 拷贝 k3s.yaml | 拉取 kubeconfig | 覆盖本地文件 |
| `destroy` | `vagrant destroy -f` | 销毁 VM | 不可逆 |

## 7. 常见坑与排障

| 现象 | 原因 | 排查 | 处理 |
|---|---|---|---|
| `add-node` 后节点 NotReady | k3s-agent 未启动、token/server 地址错误、网络不通 | `kubectl describe node`、节点 `journalctl -u k3s-agent -n 200` | 修复配置后重试；必要时清理节点重装 |
| `remove-node` 后 Pod 卡 Pending | 单副本/无其他可调度节点/PVC 绑定 | `kubectl get pods -A -o wide`、`kubectl describe pod` | 扩容节点、调整调度、恢复 PV |
| 升级后组件异常 | 版本跳跃、镜像不兼容、CRD 变化 | `kubectl get pods -A`、`kubectl get events -A` | 回滚/恢复快照、按组件升级说明处理 |
| `restore` 后数据不对 | 快照时间点不对、PV 数据不在 etcd 快照内 | 核对快照时间、检查 PV 备份 | 用正确快照恢复；结合应用/PV 备份 |
| `status` 正常但业务异常 | 应用层问题、DNS、证书、Ingress | `kubectl logs/describe`、Rancher、Loki | 转 36/47/49 Runbook |

## 8. 小结

- k3s-ops.sh 是**项目封装**，k3s/K8s/systemd/Helm 才是**通用标准能力**；两者应并列理解。
- 生命周期运维要按 Day-0/Day-1/Day-2 看：先准备，再变更，再运维与恢复。
- 每次变更前后都要有验收：`kubectl get nodes/pods/events`、版本、快照、业务抽样。
- 高风险操作（remove/upgrade/restore/destroy）必须先备份、先确认范围、先有回退路径。
