## 1. 概念与作用

### 1.1 什么是资源定义文件

K8s 里**所有东西都是对象**（Pod、Deployment、Service…），每个对象都用一份**结构化描述**来声明"我想要什么"，这份描述就是资源定义文件，通常以 **YAML**（少数 JSON）书写：

```yaml
apiVersion: v1          # 使用的 API 版本
kind: Pod               # 对象类型
metadata:               # 元数据（名字、标签…）
  name: my-pod
spec:                   # 期望状态（用户声明的"要什么"）
  containers:
  - name: nginx
    image: nginx:latest
```

这份文件就是"蓝图"：交给你想要的**期望状态（spec）**，K8s 控制面负责把它变成**实际状态（status）**并持续调谐（reconcile）直到两者一致。

### 1.2 为什么用"声明式"而不是"命令式"

| 维度 | 命令式（`docker run` / `kubectl create`） | 声明式（`kubectl apply -f xx.yaml`） |
|------|------------------------------------------|--------------------------------------|
| 做什么 | 一步步告诉系统"先做什么再做什么" | 告诉系统"最终要什么" |
| 幂等性 | 重复执行会出错（已存在） | **可重复执行**（无变化时返回 unchanged） |
| 可审计 | 无记录 | 文件即记录（可放 Git，GitOps） |
| 集群漂移 | 易被手动改动搞乱 | apply 持续收敛回文件状态 |
| 本环境实测 | `kubectl create deployment` 只能建一次 | 见 5.1：`created` → `unchanged` |

> **本环境实测**（`kubectl apply -f cm-demo.yaml` 连跑两次）：
>
> ```text
> configmap/chapter16-demo created      ← 第一次
> configmap/chapter16-demo unchanged    ← 第二次（内容没变，告诉你不做任何事）
> ```
>
> 如果把 YAML 里的 `demo: "1"` 改成 `"2"` 再 apply，会输出 `configmap/chapter16-demo configured`——只应用差异。

### 1.3 从大到小：资源的组织层级

```
K8s 集群（所有对象都存在这台"逻辑机器"里）
├── 命名空间（逻辑隔离，类似"文件夹/项目空间"）── 集群级资源（如 Node/PV）不分 NS
│   ├── 工作负载：Pod / Deployment / ReplicaSet / DaemonSet / StatefulSet / Job / CronJob
│   ├── 网络：Service / Endpoints / Ingress / NetworkPolicy
│   ├── 存储：PVC / ConfigMap / Secret
│   ├── 配置与安全：ServiceAccount / Role / RoleBinding / ResourceQuota / LimitRange
│   └── 管控：HPA / PDB / PodTemplate
└── 集群级（无命名空间）：Namespace / Node / PV / StorageClass / ClusterRole / ClusterRoleBinding /
    IngressClass / PriorityClass / RuntimeClass / CRD / Namespace 本身
```

**判断一个资源是集群级还是命名空间级**——`kubectl api-resources` 的 `NAMESPACED` 列：

```bash
kubectl api-resources | grep -E 'configmaps|persistentvolumes|deployments|storageclasses'
```

真实输出（本集群 v1.30.2+k3s2，客户端 v1.37.1）：

```text
configmaps            cm    v1                               true         ConfigMap        ← true = 命名空间级
deployments           deploy apps/v1                         true         Deployment
persistentvolumes     pv    v1                               false        PersistentVolume ← false = 集群级
storageclasses        sc    storage.k8s.io/v1                false        StorageClass
```

## 2. 通用骨架：五个顶层字段

**所有** K8s 对象的 YAML 都长一个模样，五个字段从上到下：

```yaml
apiVersion: <组>/<版本>     # ① 用哪套 API 定义（相当于"类型所属的命名空间 + 版本"）
kind: <资源类型>            # ② 是什么对象
metadata:                  # ③ 元数据：身份 + 标签 + 注释 + 归属
  name: xxx
  labels: {}
  annotations: {}
spec:                      # ④ 期望状态：用户声明"要什么"（核心！）
  ...
status:                    # ⑤ 实际状态：系统回写"现在是什么"（只读，别手写）
  ...
```

### 2.1 apiVersion：API 组与版本

| 形式 | 含义 | 本集群常见例子 |
|------|------|---------------|
| `v1` | 核心组（无组名） | Pod、Service、ConfigMap、Secret、Node、Namespace、PV、PVC |
| `apps/v1` | 应用组 | Deployment、ReplicaSet、StatefulSet、DaemonSet |
| `networking.k8s.io/v1` | 网络组 | Ingress、IngressClass、NetworkPolicy |
| `storage.k8s.io/v1` | 存储组 | StorageClass、CSIDriver |
| `batch/v1` | 批处理组 | Job、CronJob |
| `rbac.authorization.k8s.io/v1` | 权限组 | Role、ClusterRole、RoleBinding、ClusterRoleBinding |
| `autoscaling/v2` | 自动扩缩组 | HorizontalPodAutoscaler |
| `cert-manager.io/v1` | 第三方（CRD） | Certificate、Issuer、ClusterIssuer |

**怎么查某个资源用哪个 apiVersion？**

```bash
kubectl api-resources | grep -i ingress
# ingressclasses  networking.k8s.io/v1  false  IngressClass
# ingresses       networking.k8s.io/v1  true   Ingress
```

> 版本后缀含义：`v1` 稳定版；`v1beta1/v1alpha1` 测试版（可能变更/废弃）。第三方 CRD（如 Rancher 的 `management.cattle.io/v3`、cert-manager 的 `cert-manager.io/v1`）用它们自己的组。

### 2.2 kind：资源类型

`kind` 必须与 apiVersion 配套。写错组合（如 `apiVersion: apps/v1` + `kind: Pod`）apply 时会直接报错：

```text
error: unable to recognize "x.yaml": no matches for kind "Pod" in version "apps/v1"
```

### 2.3 metadata：元数据（身份与归属）

上面的 `-o yaml` 里 metadata 有很多字段，逐个拆解（以本集群真实 Pod 为例）：

```yaml
metadata:
  annotations:
    kubectl.kubernetes.io/restartedAt: "2026-10-03T09:01:57+08:00"   # 非标识键值（可任意内容）
  creationTimestamp: "2026-10-03T01:01:56Z"    # 系统回写：创建时间（只读）
  generateName: nginx-demo-559f959666-         # 前缀 + 随机后缀生成名字（Deployment 建 Pod 用）
  labels:
    app: nginx-demo                            # 标识键值（检索/选择用）
    pod-template-hash: 559f959666
  name: nginx-demo-559f959666-59frr            # 名字（命名空间内唯一）
  namespace: lab
  ownerReferences:                             # ★ 归属链：谁创建了我（见第 7 节）
  - apiVersion: apps/v1
    blockOwnerDeletion: true
    controller: true
    kind: ReplicaSet
    name: nginx-demo-559f959666
    uid: 6e91e0a6-947a-4842-b2b2-a3adf19ac50e
  resourceVersion: "392188"                    # 系统回写：etcd 版本号（并发控制，只读）
  uid: 6a20cc7f-c77a-4e13-b009-5e4c7f58d57c    # 系统回写：全局唯一 ID（只读）
```

**labels vs annotations 的区别**（第 13 章有详情，这里提关键差异）：

| | labels | annotations |
|---|--------|-------------|
| 目的 | **标识/选择**（给 selector 用） | 附带信息（不用于选择） |
| 可被 selector 匹配 | ✅ | ❌ |
| 内容限制 | key 有规范约束 | 可放任意字符串（如 JSON、配置） |
| 本环境例子 | `app=nginx-demo` | `kubectl.kubernetes.io/restartedAt`、`field.cattle.io/publicEndpoints` |

> **哪些字段你写，哪些别写**：`name/labels/annotations` 你写；`uid/resourceVersion/creationTimestamp` 由系统生成——**手写会被忽略或报冲突**（`resourceVersion` 用于乐观锁，改错会 409 Conflict）。

### 2.4 spec：期望状态（用户声明，核心）

`spec` 是**你要什么**，随资源类型不同结构千差万别（第 3 节逐类详解）。共同点：**只写期望，不写现状**。比如 Deployment 你只写 `replicas: 5`，不需要告诉它"现在有 3 个"。

### 2.5 status：实际状态（系统回写，只读）

`status` 是**控制面汇报现状**，由各 controller 持续写入。以本环境 PVC 为例：

```yaml
status:
  accessModes:
  - ReadWriteOnce
  capacity:
    storage: 1Gi
  phase: Bound          # Pending → Bound → Released / Failed
```

**为什么你永远不该手写 status？** 因为 controller 会覆盖它；写错了也可能造成假象。备份文件里通常把 status 删掉再 apply（apply 本来就会忽略 status）。

## 3. 资源全览：由大到小逐类详解（本集群真实对象）

> 每组给：作用一句话 → YAML 骨架 → 关键字段 → 本环境真实对象/输出。

### 3.1 集群级资源

#### 3.1.1 Namespace（命名空间）

- **作用**：逻辑隔离、资源配额边界、权限边界。
- **关键字段**：`metadata.name`；`spec.finalizers: [kubernetes]`（删除时先清空内容）。

本环境 `lab` 命名空间真实 YAML：

```yaml
apiVersion: v1
kind: Namespace
metadata:
  annotations:
    cattle.io/status: '{"Conditions":[{"Type":"ResourceQuotaInit","Status":"True",...}]}'
    lifecycle.cattle.io/create.namespace-auth: "true"    # Rancher 打的
  creationTimestamp: "2026-10-03T00:22:48Z"
  labels:
    kubernetes.io/metadata.name: lab        # ★ 自动标签（1.20+），值 = 名字
  name: lab
  resourceVersion: "274954"
  uid: 5156fac7-375b-4a02-aa3b-93260a3d2595
spec:
  finalizers:
  - kubernetes
status:
  phase: Active
```

> 本集群的命名空间大多是 Rancher 建的（`cattle-*`），`lab` 是教程手工创建的实验空间。

#### 3.1.2 Node（节点）

- **作用**：一台物理/虚拟机；承载 Pod。
- **关键字段（spec）**：`podCIDR`（分配给该节点的 Pod 网段）、`taints`（污点）。
- **status**：`addresses`（InternalIP/Hostname）、`nodeInfo`（OS/内核/容器运行时）、`conditions`（Ready 等）、`capacity/allocatable`（算力资源）。

本环境 `k3s-demo-server-1` 真实 metadata 节选（注意 k3s/flannel/etcd 自动注入的大量 annotation）：

```yaml
metadata:
  annotations:
    alpha.kubernetes.io/provided-node-ip: 192.168.56.10
    etcd.k3s.cattle.io/node-address: 192.168.56.10
    flannel.alpha.coreos.com/backend-type: vxlan      # flannel 网络后端
    k3s.io/hostname: k3s-demo-server-1
    k3s.io/internal-ip: 192.168.56.10
    k3s.io/node-args: '["server","--node-name","k3s-demo-server-1",...]'  # 启动参数（排障利器！）
  labels:
    beta.kubernetes.io/arch: amd64
    kubernetes.io/arch: amd64
    kubernetes.io/hostname: k3s-demo-server-1
    node-role.kubernetes.io/control-plane: "true"
    node-role.kubernetes.io/etcd: "true"
    node-role.kubernetes.io/master: "true"
spec:
  podCIDR: 10.42.0.0/24
  podCIDRs:
  - 10.42.0.0/24
  taints: []                      # 本集群 server 不设污点（见 AGENTS.md 设计决策）
status:
  addresses:
  - address: 192.168.56.10
    type: InternalIP
  - address: k3s-demo-server-1
    type: Hostname
  capacity:
    cpu: "2"
    memory: 4040444Ki
  nodeInfo:
    containerRuntimeVersion: containerd://1.7.17-k3s1
    kernelVersion: 5.15.0-160-generic
    osImage: Ubuntu 22.04.5 LTS
```

> `k3s.io/node-args` 这个 annotation 排障极有用：忘了当初怎么启动的 k3s？一条命令看全：`kubectl get node k3s-demo-server-1 -o jsonpath='{.metadata.annotations.k3s\.io/node-args}'`。

#### 3.1.3 PV（持久卷）与 StorageClass

- **PV**：集群级存储池（独立于命名空间存在）；**对象是 admin 或存储插件创建的**。
- **StorageClass**：存储"模板"——声明用什么 provisioner、什么回收策略，用户只要 PVC 指名 StorageClass，系统自动动态创建 PV（动态供给）。

本环境 StorageClass `local-path` 真实 YAML：

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  annotations:
    storageclass.kubernetes.io/is-default-class: "true"   # ★ 默认类：PVC 不写 storageClassName 就用它
  name: local-path
provisioner: rancher.io/local-path    # 真正创建 PV 的插件（k3s 自带）
reclaimPolicy: Delete                 # 删除 PVC 时连带删 PV 及数据
volumeBindingMode: WaitForFirstConsumer  # 等第一个使用它的 Pod 调度后再绑定（本地存储必须先知道跑在哪个节点）
```

本环境 PV（由上述 SC 动态创建，1Gi）：

```text
NAME                                       CAPACITY   ACCESS MODES   RECLAIM POLICY   STATUS   CLAIM            STORAGECLASS   AGE
pvc-61720575-6d78-4437-8d50-553a7b4c8fc8   1Gi        RWO            Delete           Bound    lab/nginx-data   local-path     2d
```

> 观察 `STATUS=Bound` 后 `kubectl get pv pvc-... -o yaml` 里会有 `claimRef`（指向 lab/nginx-data）——PV↔PVC 是一对一绑定关系。

#### 3.1.4 RBAC：ClusterRole / ClusterRoleBinding / ClusterRole 族

- **Role**（NS 级）、**ClusterRole**（集群级）：定义"能对哪些资源做哪些操作"的规则集合。
- **RoleBinding / ClusterRoleBinding**：把"谁（user/group/SA）"绑定到"哪个 Role"。
- 关键字段：`rules: [{apiGroups, resources, verbs}]`。

本环境 `clusterrole/system:basic-user` 真实 YAML：

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  annotations:
    rbac.authorization.kubernetes.io/autoupdate: "true"
  labels:
    kubernetes.io/bootstrapping: rbac-defaults
  name: system:basic-user
rules:
- apiGroups:
  - authorization.k8s.io
  resources:
  - selfsubjectaccessreviews
  - selfsubjectrulesreviews
  verbs:
  - create
```

> 想验证"我现在能不能干某件事"用 `kubectl auth can-i`（见第 16 章）：`kubectl auth can-i create pods -n lab` → `yes`。

#### 3.1.5 其他集群级资源速览

| 资源 | 作用 | 本环境真实对象 |
|------|------|---------------|
| `IngressClass` | 声明 Ingress 由哪个控制器处理 | `nginx`（nginx-ingress） |
| `PriorityClass` | Pod 优先级（抢占） | 默认若干（`system-cluster-critical` 等） |
| `RuntimeClass` | 选择容器运行时 | 无（默认 containerd） |
| `CustomResourceDefinition` | **定义你自己的资源类型**（CRD） | 本集群 116 个（Rancher/cert-manager/fleet 等安装时注入） |
| `k3s.cattle.io/v1 ETCDSnapshotFile` | k3s 的 etcd 快照对象 | （第 12 章用过） |

> **CRD 是本集群一个重要的"从大到小"观察点**：`kubectl get crd | wc -l` → 116。Rancher 全家桶（`management.cattle.io`、`cattle.io`…）+ cert-manager（`cert-manager.io`）+ fleet + k3s（`k3s.cattle.io`）都靠 CRD 扩展 API。你写的自定义 `kind` 就是走 CRD，与内置资源地位相同。

### 3.2 命名空间级资源

#### 3.2.1 Pod（最小调度单元）

- **作用**：一组容器的"运行环境"；K8s 不直接调度容器，而是调度 Pod。
- **spec 关键字段**：`containers[]`（镜像/端口/资源/探针）、`nodeSelector`（第 13 章）、`restartPolicy`、`volumes`、`serviceAccountName`。
- **status 关键字段**：`podIP`、`nodeName`、`phase`（Pending/Running/Succeeded/Failed/Unknown）、`conditions`（Ready 等）。

本环境 `lab` 里一个 nginx Pod 的 spec/status 真实内容（节选）：

```yaml
spec:
  containers:
  - image: nginx:latest
    imagePullPolicy: IfNotPresent
    name: nginx
    ports:
    - containerPort: 80
      protocol: TCP
    resources: {}
    terminationMessagePath: /dev/termination-log
    terminationMessagePolicy: File
    volumeMounts:
    - mountPath: /var/run/secrets/kubernetes.io/serviceaccount
      name: kube-api-access-4xv2x          # 自动挂载的 SA 令牌
      readOnly: true
  dnsPolicy: ClusterFirst
  enableServiceLinks: true
  nodeName: k3s-demo-server-1
  nodeSelector:
    kubernetes.io/hostname: k3s-demo-server-1   # 第 06 章实验加的：钉在 server-1
  preemptionPolicy: PreemptLowerPriority
  priority: 0
  restartPolicy: Always
  schedulerName: default-scheduler
  serviceAccountName: default
  tolerations: []                               # 本 Pod 无污点容忍
status:
  conditions:
  - lastProbeTime: null
    lastTransitionTime: "2026-10-05T01:06:11Z"
    status: "True"
    type: Ready
  containerStatuses:
  - containerID: containerd://12485c1eaf...
    image: nginx:latest
    imageID: docker.io/library/nginx@sha256:abe477...
    ready: true
    restartCount: 2
    started: true
    state:
      running:
        startedAt: "2026-10-05T01:06:11Z"
  hostIP: 192.168.56.10
  phase: Running
  podIP: 10.42.0.28
  podIPs:
  - ip: 10.42.0.28
  qosClass: BestEffort

```

> `restartCount: 2` + `state.running`：说明这个 Pod 曾重启过 2 次（此前有 `Last State: Terminated`）。排障口诀：**看 Pod 先看 `kubectl describe pod` 的 Events 段**（见第 16 章）。

#### 3.2.2 Deployment（无状态应用）

- **作用**：管理 N 个相同副本的"控制器"，负责滚动更新/回滚/扩缩容。
- **spec 关键字段**：`replicas`、`selector.matchLabels`（**不可变**，见第 13 章练习 5）、`strategy`（RollingUpdate / Recreate）、`template`（Pod 模板，改它=触发滚动更新）、`revisionHistoryLimit`。

本环境 `lab/nginx-demo` 真实 YAML 要点：

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  annotations:
    deployment.kubernetes.io/revision: "2"     # 滚动更新版本号
    field.cattle.io/publicEndpoints: '[{"port":32062,...,"serviceName":"lab:nginx-svc",...}]'
    kubectl.kubernetes.io/last-applied-configuration: |   # ★ apply 时自动存的"上次提交内容"（3 方合并基础）
      {"apiVersion":"apps/v1","kind":"Deployment","metadata":{"annotations":{},...},"spec":{"replicas":3,...}}
  creationTimestamp: "2026-10-03T01:00:15Z"
  generation: 7            # 每次 spec 被改 +1
  name: nginx-demo
  namespace: lab
  uid: e0c04b42-...
spec:
  progressDeadlineSeconds: 600
  replicas: 5
  revisionHistoryLimit: 10
  selector:
    matchLabels:
      app: nginx-demo
  strategy:
    rollingUpdate:
      maxSurge: 25%        # 最多允许多出 25% 副本
      maxUnavailable: 25%  # 最多允许 25% 不可用
    type: RollingUpdate
  template:
    metadata:
      labels:
        app: nginx-demo
    spec:
      containers:
      - image: nginx:latest
        imagePullPolicy: IfNotPresent
        name: nginx
        ports:
        - containerPort: 80
          protocol: TCP
      nodeSelector:
        kubernetes.io/hostname: k3s-demo-server-1
status:
  availableReplicas: 5
  observedGeneration: 7
  readyReplicas: 5
  replicas: 5
  updatedReplicas: 5
```

> `last-applied-configuration` 是 `kubectl apply` 的"记忆"：apply 时拿"上次我 apply 的内容"与"当前服务器上的内容"和"这次的新内容"做三方合并，只动差异。这也是 apply 幂等的底层机制。
>
> **Deployment → ReplicaSet → Pod 的关系**见第 7 节关联性。

#### 3.2.3 ReplicaSet（副本集，Deployment 的"手"）

- **作用**：维持"指定数量的同模板 Pod 在运行"；Deployment 通过它实现滚动更新（每次更新新建一个 RS）。
- **关键字段**：`replicas`、`selector.matchLabels`（自动附带 `pod-template-hash`）、`template`。

本环境真实 RS（两个：当前 5 副本 + 旧版 0 副本，滚动更新后旧 RS 被保留用于回滚）：

```text
NAME                    DESIRED   CURRENT   READY   AGE
nginx-demo-559f959666   0         0         0       2d     ← 旧版本（更新前的哈希）
nginx-demo-7fb649d588   5         5         5       2m     ← 当前版本
```

> `pod-template-hash` 哈希值不同 = Pod 模板不同。看到多个 RS 是**正常**的；`rollout history` 就是读这些 RS 的历史。

#### 3.2.4 Service 与 Endpoints（稳定入口）

- **Service**：把一组 Pod 包装成**稳定的虚拟 IP（ClusterIP）+ 域名**入口；`spec.selector` 决定收录哪些 Pod（第 11 章 iptables 讲了它的实现）。
- **Endpoints**：Service 的"后端清单"，由控制面根据 selector 自动维护（第 13 章演示了联动）。

本环境 `lab/nginx-svc` 真实 YAML：

```yaml
apiVersion: v1
kind: Service
metadata:
  annotations:
    field.cattle.io/publicEndpoints: '[{"port":32062,"protocol":"TCP","serviceName":"lab:nginx-svc","allNodes":true}]'
  creationTimestamp: "2026-10-03T01:02:49Z"
  name: nginx-svc
  namespace: lab
  uid: 1226dd25-...
spec:
  clusterIP: 10.43.23.169          # 虚拟 IP（Service CIDR 内，本集群 10.43.0.0/16）
  clusterIPs:
  - 10.43.23.169
  externalTrafficPolicy: Cluster
  internalTrafficPolicy: Cluster
  ipFamilies:
  - IPv4
  ipFamilyPolicy: SingleStack
  ports:
  - nodePort: 32062               # NodePort 类型的宿主机端口
    port: 80                      # Service 端口（虚拟）
    protocol: TCP
    targetPort: 80                # Pod 容器端口
  selector:
    app: nginx-demo
  sessionAffinity: None
  type: NodePort                  # ClusterIP | NodePort | LoadBalancer | ExternalName
status:
  loadBalancer: {}
```

对应的 Endpoints（控制面自动维护，`targetRef` 指向实际 Pod）：

```yaml
subsets:
- addresses:
  - ip: 10.42.0.28
    nodeName: k3s-demo-server-1
    targetRef:
      kind: Pod
      name: nginx-demo-559f959666-59frr
      namespace: lab
      uid: 6a20cc7f-...
```

> **三种 Service 类型一句话**：ClusterIP 只在集群内；NodePort 在每个节点开端口映射到 ClusterIP；LoadBalancer 依赖云厂商/`servicelb`（本集群已禁用 servicelb，用 NodePort + Ingress）。

#### 3.2.5 Ingress（七层入口）

- **作用**：用**域名 + 路径**把外部流量路由到 Service（第 04 章详述）；本集群控制器是 **nginx-ingress**。
- **关键字段**：`ingressClassName`、`rules[{host, http.paths[{path, pathType, backend}]}]`、`tls`。

本环境 `lab/nginx-ing` 真实 YAML：

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  annotations:
    field.cattle.io/publicEndpoints: '[{"addresses":["10.43.197.40"],"port":80,...}]'
  creationTimestamp: "2026-10-03T01:02:59Z"
  generation: 1
  name: nginx-ing
  namespace: lab
  uid: e7159c6f-...
spec:
  ingressClassName: nginx
  rules:
  - host: lab.k3s.local
    http:
      paths:
      - backend:
          service:
            name: nginx-svc
            port:
              number: 80
        path: /
        pathType: Prefix
```

> **pathType**：`Prefix`（前缀匹配，`/` 匹配一切）vs `Exact`（精确匹配）。访问 `http://lab.k3s.local:30080/` → nginx-ingress（30080 是 HTTP NodePort）→ nginx-svc → 后端 Pod。

#### 3.2.6 ConfigMap 与 Secret（配置挂载）

- **ConfigMap**：非机密配置（明文）；**Secret**：机密配置（base64 编码存储）。
- **关键字段**：`data`（键值对）。

本环境两个真实对象：

```yaml
# ConfigMap lab/app-config
apiVersion: v1
data:
  app.env: test
  app.name: nginx-demo
  app.port: "80"
kind: ConfigMap
metadata:
  name: app-config
  namespace: lab

# Secret lab/app-secret —— kubectl get secret app-secret -o yaml 里 data 是 base64
apiVersion: v1
data:
  password: YWRtaW4=        # base64("admin")，演示用途
kind: Secret
metadata:
  name: app-secret
  namespace: lab
type: Opaque               # Opaque|kubernetes.io/tls|kubernetes.io/service-account-token...
```

> **Secret 的 base64 不是加密**（看一眼就能解码），只防"明文出现在配置里"。真正的加密要配 KMS/外部密钥。查看解码值：`kubectl get secret app-secret -o jsonpath='{.data.password}' | base64 -d`。

#### 3.2.7 PVC（持久卷声明）——从先到后的关键一环

- **作用**：用户"申请存储"的声明；系统（通过 StorageClass）绑一个 PV 给它。
- **关键字段（spec）**：`accessModes`（RWO/RWX/ROX）、`resources.requests.storage`、`storageClassName`、`volumeMode`。

本环境 `lab/nginx-data` 真实 YAML：

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  annotations:
    pv.kubernetes.io/bind-completed: "yes"          # 绑定完成（系统写）
    pv.kubernetes.io/bound-by-controller: "yes"
    volume.beta.kubernetes.io/storage-provisioner: rancher.io/local-path
    volume.kubernetes.io/selected-node: k3s-demo-server-1   # WaitForFirstConsumer 选中节点
  finalizers:
  - kubernetes.io/pvc-protection
  name: nginx-data
  namespace: lab
spec:
  accessModes:
  - ReadWriteOnce
  resources:
    requests:
      storage: 1Gi
  storageClassName: local-path
  volumeMode: Filesystem
  volumeName: pvc-61720575-...     # 绑定到的 PV 名（系统写）
status:
  accessModes:
  - ReadWriteOnce
  capacity:
    storage: 1Gi
  phase: Bound
```

> **从先到后第一课**：PVC 通常**先于**使用它的 Deployment 创建（或同批次），因为 Pod 调度时就要决定"绑到哪个 PV、跑在哪个节点"（尤其 `WaitForFirstConsumer` 的本地存储）。第 6 节有完整顺序。

#### 3.2.8 HPA（水平自动扩缩）

- **作用**：根据 CPU/内存/自定义指标自动调 Deployment/RS/STS 的副本数。
- **关键字段**：`scaleTargetRef`（扩谁）、`minReplicas/maxReplicas`、`metrics`。

本环境 `lab/sched-demo` 的真实 HPA：

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: sched-demo
  namespace: lab
spec:
  maxReplicas: 6
  metrics:
  - resource:
      name: cpu
      target:
        averageUtilization: 50     # CPU 平均使用率超 50% 就扩容
        type: Utilization
    type: Resource
  minReplicas: 2
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: sched-demo
status:
  currentReplicas: 2
  desiredReplicas: 2
```

命令快照：

```text

sched-demo  Deployment/sched-demo   cpu: 0%/50%   2         6         2          2d
```

## 4. 从先到后：一个应用从零到可用的完整编排

把上面的资源按**依赖顺序**串起来（这就是"从先到后"——后面的资源依赖前面的）：

```
① Namespace lab          （决定资源放哪个"文件夹"）
② ConfigMap app-config   （先准备好配置，Deployment 引用它的名字即可）
   Secret    app-secret
③ PVC nginx-data         （存储编排 → 绑定 PV）
④ Deployment nginx-demo  （工作负载；引用 ②③：envFrom/volume）
⑤ Service nginx-svc      （用 selector 指向 Deployment 的 Pod 标签）
⑥ Ingress nginx-ing      （把域名路由到 Service）
```

本环境实际顺序正是如此（时间戳可证）：

```bash
kubectl get -n lab ns,cm,secret,pvc,deploy,svc,ing -o custom-columns='KIND:.kind,NAME:.metadata.name,AGE:.metadata.creationTimestamp'
```

真实输出：

```text
KIND        NAME           AGE
Namespace   lab            2026-10-03T00:22:48Z   ← 最早
ConfigMap   app-config     2026-10-03T01:04:13Z
Secret      app-secret     2026-10-03T01:04:13Z
PersistentVolumeClaim  nginx-data  2026-10-03T01:04:21Z
Deployment  nginx-demo     2026-10-03T01:00:15Z
Service     nginx-svc      2026-10-03T01:02:49Z
Ingress     nginx-ing      2026-10-03T01:02:59Z
```

**为什么是这个顺序？**

1. **NS 最前**：没有它，后面所有 `namespace: lab` 都建不出来（除非自动创建策略）。
2. **CM/Secret 先于工作负载**：Deployment 只写"引用 app-config"，**内容变了只需改 CM 不必改 Deployment**；反过来先建 Deployment 会因为"找不到 CM"启动失败（env 注入失败、挂载目录为空）。
3. **PVC 先于 Deployment**：Deployment 的 Pod 模板里写 `claimName: nginx-data`，调度时就绑定；先有 PVC 才能保证 Pod 一次调度成功（尤其本地存储）。
4. **Service 后于 Deployment**：Service 的 selector 要能匹配到 Pod 才算有效；Pod 没起来时 Service 只是"空壳"。
5. **Ingress 最后**：它依赖 Service 的存在（backend.service.name 必须真实存在，否则配置无效但不会报错——这常是"访问 404"的坑）。

## 5. 如何修改与使用（apply / edit / patch / set / delete）

### 5.1 apply：声明式（推荐，幂等）

```bash
kubectl apply -f file.yaml        # 文件
kubectl apply -f dir/             # 目录（递归读所有 yaml/yml/json）
kubectl apply -f -                # 从标准输入（管道/heredoc）
kubectl apply --dry-run=client|server -f file.yaml   # 先演练，不真正应用
```

本环境实测（同一文件 apply 两次）：

```text
configmap/chapter16-demo created      # 第一次
configmap/chapter16-demo unchanged    # 第二次：无变化，不动
```

修改 YAML 里 `demo: "1"` → `"2"` 再 apply：

```text
configmap/chapter16-demo configured   # 有变化，只应用差异
```

### 5.2 edit：交互式编辑（命令式入口）

```bash
kubectl -n lab edit deploy nginx-demo
# 用 $KUBE_EDITOR / $EDITOR（默认 vi）打开完整 YAML，保存即 apply
```

edit 的本质：拉取完整对象 → 你改 → 提交。**适合临时小改**；不适合大规模/批量（无法复用、无 Git 记录）。

### 5.3 patch：只改指定字段（命令式，精准）

```bash
kubectl patch <res> <name> --type=merge -p '{"spec":{"replicas":5}}'
kubectl patch <res> <name> --type=json -p '[{"op":"replace","path":"/spec/replicas","value":5}]'
```

本环境实测（merge patch ConfigMap 的 data）：

```text
configmap/chapter16-demo patched
```

> `--type`：`merge`（合并 map）、`json`（RFC 6902 JSON Patch，可增删改数组）、`strategic`（默认，K8s 特有合并策略）。
> **patch 的好处**：不动其他字段（例如只改一个标签/一个端口），比 edit 更可控。

### 5.4 set：改常用字段的"快捷命令"

```bash
kubectl set image deploy/nginx-demo nginx=nginx:1.27      # 换镜像（会触发滚动更新）
kubectl set resources deploy/sched-demo --limits=cpu=200m,memory=256Mi --requests=cpu=100m,memory=128Mi
kubectl set env deploy/nginx-demo FOO=bar                  # 加环境变量
```

本环境实测（给 sched-demo 设资源限额）：

```text
deployment.apps/sched-demo resource requirements updated
```

验证（jsonpath 抽 resources）：

```json
{"limits":{"cpu":"200m","memory":"256Mi"},"requests":{"cpu":"100m","memory":"128Mi"}}
```

### 5.5 delete：删除（注意级联）

```bash
kubectl delete -f file.yaml              # 删文件里声明的所有资源
kubectl delete deploy nginx-demo         # 按名字删
kubectl delete pod -l app=nginx-demo     # 按标签删一批
kubectl delete ns lab                    # 删整个命名空间（连同里面的一切）
kubectl delete deploy nginx-demo --cascade=orphan   # 只删控制器，留下 Pod 成孤儿
```

本环境实测（删临时演示 ConfigMap；以及 `--dry-run` 预演按标签删）：

```text
configmap "chapter16-demo" deleted from lab namespace
pod "nginx-demo-559f959666-59frr" deleted from lab namespace (dry run)   ← --dry-run 只是预演
```

> **级联删除**：删 Deployment 会连带删除它管的 RS 和 Pod（靠 ownerReferences，见第 7 节）。`--cascade=orphan` 可解绑。

### 5.6 生产建议：文件化 + Git

- 所有资源写 YAML 存 Git（这是 Rancher/Helm/GitOps 的根基）
- 改东西：改文件 → `kubectl apply -f`；不要在生产上直接 `edit`/`patch` 后不落文件
- 备份：`kubectl get deploy -o yaml > deploy.yaml`（注意剔除 status 与 resourceVersion）

## 6. 关联性：资源之间怎么"连"起来

### 6.1 归属链（ownerReferences）：谁生了我，谁就管我、删我

```
Deployment (apps/v1) ──owner──▶ ReplicaSet ──owner──▶ Pod
```

真实验证（Pod 的 ownerReferences 指向 RS；RS 的指向 Deployment）：

```bash
kubectl -n lab get pod nginx-demo-7fb649d588-xxxxx -o jsonpath='{.metadata.ownerReferences[0].kind}/{.metadata.ownerReferences[0].name}'
# replicaset/nginx-demo-7fb649d588
kubectl -n lab get rs nginx-demo-7fb649d588 -o jsonpath='{.metadata.ownerReferences[0].kind}/{.metadata.ownerReferences[0].name}'
# deployment/nginx-demo
```

**ownerReferences 的三大作用**：

1. **级联删除（GC）**：父删除 → 子跟随删除（垃圾回收器执行）
2. **归属控制**：`controller: true` 标记唯一"主导者"（防止两个控制器抢一个 Pod）
3. **冲突保护**：`blockOwnerDeletion: true` 防止删除父时子还在空中

### 6.2 选择链（selector）：我"认领"哪些对象

```
Deployment.spec.selector.matchLabels  → 认领 ReplicaSet（app=nginx-demo 模板哈希）
Service.spec.selector                → 认领 Pod（app=nginx-demo）→ 生成 Endpoints
HPA.spec.scaleTargetRef              → 认领 Deployment（sched-demo）
PVC.spec.volumeName / PV.spec.claimRef → PVC ↔ PV 绑定
Ingress.spec.rules[].backend.service → 认领 Service（nginx-svc）
```

**一条链跑通**（本环境 nginx 流量路径，第 04/11 章详述）：

```text
Ingress(nginx-ing)
  └─▶ Service(nginx-svc, selector: app=nginx-demo)
        └─▶ Endpoints(5 个 Pod IP：10.42.0.28/30/...)
              └─▶ Pods(app=nginx-demo + pod-template-hash)
```

### 6.3 标签关联（Label）

第 13 章已详述，这里补"关联性"视角：**Label 是贯穿上述所有链的"胶水"**——selector 匹配的就是 Label；没有 Label，Service 就找不到 Pod，Deployment 就管不了 RS。系统中自动注入的 Label 也在参与关联：`kubernetes.io/metadata.name`（NS 过滤）、`pod-template-hash`（RS 版本区分）、`k8s-app`（组件关联 Service）。

### 6.4 finalizer：删除被"卡住"的机制

前面见过的 `finalizers: [kubernetes.io/pvc-protection]` / `finalizers: [kubernetes]`（Namespace）。**finalizer 是删除前的"闸门"**：一个对象带 finalizer，删除时只会打上 `deletionTimestamp`，**真正被删要等 finalizer 清空**。

典型现象与排查：

```bash
kubectl get ns cattle-fleet-clusters-system   # 一直 Terminating
# → 里面有对象没清完或 finalizer 卡住
```

```bash
kubectl get ns <卡住的ns> -o jsonpath='{.metadata.finalizers}'
```

> 遇到 `Terminating` 卡死：先查里面残留资源；确认安全后可以删 finalizer 强制释放（慎用）：
> `kubectl patch ns <name> -p '{"metadata":{"finalizers":[]}}'`。

### 6.5 status 回写：控制面在持续"对账"

```
你写 spec ──▶ API Server (etcd) ──▶ Controller 读取 ──▶ 执行动作 ──▶ 回写 status
                    ▲                                                      │
                    └──────────── 持续调谐（reconcile）直到 spec == status ──┘
```

例：`kubectl scale deploy nginx-demo --replicas=6` → 只改了 `spec.replicas=6` → Deployment controller 建新 Pod → 一段时间后 `status.replicas/readyReplicas` 也变成 6（第 13 章的端点联动就是这条链的可见部分）。

| fleet | `fleet.cattle.io/v1alpha1` | GitRepo、Bundle、Cluster |
| k3s | `k3s.cattle.io/v1` | Addon、ETCDSnapshotFile |
| cluster-api (turtles) | `cluster.x-k8s.io/v1beta2` | Cluster、Machine、MachineDeployment |

> **CRD 不只给"别人"用**：你也可以定义自己的（`kubectl create crd` / 写一份 CRD YAML）。到时候你的资源就是"和 Pod 平级"的一等公民——本章第 3 节讲的所有概念（metadata/spec/status/ownerReferences）全部适用。

## 9. 小结

- **一切皆对象**：`apiVersion`（用哪套定义）+ `kind`（什么对象）+ `metadata`（身份/标签）+ `spec`（我要什么）+ `status`（现在是什么）
- **从大到小**：集群 → 命名空间 → 资源类别 → 对象 → 字段；集群级（Node/PV/SC/RBAC-CR）vs 命名空间级（Pod/Deploy/SVC/CM/Secret/PVC...）用 `api-resources` 的 NAMESPACED 列判断
- **从先到后**：NS → CM/Secret/PVC → Deployment → Service → Ingress，依赖前置
- **关联性**：ownerReferences（归属+级联删除）、selector（认领+端点）、label（胶水）、finalizer（删除闸门）、status 回写（对账闭环）
- **修改方式**：`apply` 声明式幂等（推荐）＞ `edit`/`patch`/`set` 命令式精准改 ＞ `delete`（级联）
- **看全资源**：`kubectl api-resources` + `explain`（字段字典）就是你的"资源地图"和"字段字典"

## 动手练习

5. 深入：`kubectl get deploy nginx-demo -o jsonpath='{.spec.template.metadata.labels}'` 与 `kubectl get rs nginx-demo-xxx -o jsonpath='{.spec.selector.matchLabels}'` 对比——解释 `pod-template-hash` 是从哪一层加进去的。

<details>
<summary>参考答案</summary>

1. `--namespaced=false` 输出中 `customresourcedefinitions` 是内置；`clusters.management.cattle.io`、`certificates.cert-manager.io`、`addons.k3s.cattle.io` 等都是 CRD（`kubectl get crd` 里能查到名字）。
2. `spec.clusterIP`/`spec.selector`/`spec.type` 是你（或教程）写的期望；`clusterIPs`、`status.loadBalancer`（空）、`resourceVersion`/`uid`/`creationTimestamp` 是系统回写。注意 `clusterIP` 本身虽然写在你声明的 YAML 里，但值由系统从 Service CIDR 分配。
3. apply 三次分别输出 `created`（首次）、`configured`（内容变了）、`changed`/`unchanged`（再变/不变），**这是声明式幂等的关键体验**。
4. scale 后 `status.replicas` 会先于 `status.readyReplicas` 变化（Pod 起来需要时间）——这就是"期望 vs 实际"在 Status 里的微观体现。
5. Deployment 的 template labels 只有 `app=nginx-demo`；RS 的 selector 除了 `app` 还多了 `pod-template-hash`。**哈希是在 Deployment 生成 RS 时由控制器加进 template 的**——用来区分不同模板版本的 RS。修改 template 任何地方（哪怕换镜像），哈希就变，产生新 RS。
</details>
