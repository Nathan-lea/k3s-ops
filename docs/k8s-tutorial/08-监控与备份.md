# 08 监控与备份：健康检查 / 事件日志 / etcd 快照

## 本章目标

- 掌握应用健康检查三件套：readinessProbe / livenessProbe / startupProbe
- 理解 K8s 事件（Events）的作用与查看方法
- 掌握集群日志查看与排障流程
- 会用 k3s 内置命令做 etcd 快照（备份与恢复）

---

## 1. 为什么需要健康检查

K8s 靠 **探针（Probe）** 判断容器死活，从而决定：要不要重启、要不要把流量打进来、要不要摘流量。

| 探针 | 回答的问题 | 失败后果 |
|------|-----------|---------|
| **readinessProbe**（就绪） | 服务能接流量了吗？ | 从 Service 后端**摘除**（不重启） |
| **livenessProbe**（存活） | 进程还活着吗？ | **重启容器** |
| **startupProbe**（启动） | 慢启动应用准备好没？ | 重启，保护慢应用不被误杀 |

三种探测方式：

| 方式 | 适合 | 示例 |
|------|------|------|
| `httpGet` | HTTP 服务 | 请求 `/healthz` 返回 2xx/3xx 即健康 |
| `tcpSocket` | 任意端口服务 | 端口能连上即健康 |
| `exec` | 无 HTTP 的进程 | 容器内跑命令，退出码 0 即健康 |

## 2. 本集群实站对照

### 2.1 创建带探针的 Deployment

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: probe-demo
  namespace: lab
spec:
  replicas: 2
  selector:
    matchLabels: { app: probe-demo }
  template:
    metadata:
      labels: { app: probe-demo }
    spec:
      nodeSelector:
        kubernetes.io/hostname: k3s-demo-server-1
      containers:
        - name: nginx
          image: nginx:latest
          imagePullPolicy: IfNotPresent
          ports:
            - containerPort: 80
          readinessProbe:
            httpGet: { path: /, port: 80 }
            initialDelaySeconds: 3     # 启动后等 3 秒再开始探测
            periodSeconds: 5           # 每 5 秒探一次
          livenessProbe:
            httpGet: { path: /, port: 80 }
            initialDelaySeconds: 5
            periodSeconds: 10
```

```bash
kubectl apply -f probe-demo.yaml
kubectl -n lab rollout status deployment/probe-demo --timeout=90s
```

预期输出：

```text
deployment.apps/probe-demo created
Waiting for deployment "probe-demo" rollout to finish: 0 of 2 updated replicas are available...
Waiting for deployment "probe-demo" rollout to finish: 1 of 2 updated replicas are available...
deployment "probe-demo" successfully rolled out
```

观察：`rollout status` 等待的「available」正是等待 readinessProbe 通过 —— 不通过永远不会标记可用。

### 2.2 查看探针配置（describe）

```bash
kubectl -n lab describe pod -l app=probe-demo | grep -E 'Liveness|Readiness|Ready:'
```

预期输出（本环境真实）：

```text
Ready:          True
Liveness:       http-get http://:80/ delay=5s timeout=1s period=10s successThreshold=1 failureThreshold=3
Readiness:      http-get http://:80/ delay=3s timeout=1s period=5s successThreshold=1 failureThreshold=3
```

参数含义：

- `delay=5s` = initialDelaySeconds（启动后等 5s 才第一次探测）
- `period=10s` = periodSeconds（探测间隔）
- `timeout=1s` = 单次探测超时
- `failureThreshold=3` = 连续失败 3 次才判定失败

### 2.3 让探针失败的观察实验（可选）

把 readinessProbe 的路径改成不存在的 `/nil` 再 apply，观察：

```bash
kubectl -n lab rollout status deployment/probe-demo --timeout=10s   # 会一直等不到可用
```

Pod 状态会出现 `0/1 Running`（容器在跑，但未就绪）—— 此时 Service 不会把流量打进这些 Pod。改回 `/` 即恢复。

### 2.4 查看事件（Events）—— 排障的第一现场

K8s 的所有重要动作都会产生事件对象（不持久化，约 1 小时滚动清理）：

```bash
kubectl get events -A --sort-by=.lastTimestamp | tail
```

预期输出（本环境真实，节选）：

```text
lab     67s   Normal   Started    pod/probe-demo-586b969fd-hb2vz   Started container nginx
lab     67s   Normal   Pulled     pod/probe-demo-586b969fd-hb2vz   Container image "nginx:latest" already present on machine
default 40s   Normal   ETCDSnapshotCreated  etcdsnapshotfile/...  Snapshot manual-demo-... saved on k3s-demo-server-1
lab     8s    Warning  FailedGetResourceMetric  hpa/sched-demo     failed to get cpu utilization: unable to get metrics...
```

只看某个命名空间：

```bash
kubectl -n lab get events --sort-by=.lastTimestamp | tail
```

事件字段：时间、类型（Normal/Warning）、原因（Reason）、涉及对象、消息（Message）。**Warning 类型的事件是排障抓手**。

> 例如上面的 `FailedGetResourceMetric` 就来自我们第 06 章创建的 HPA —— 它拿不到 CPU 指标（sched-demo 的 Pod 未就绪/无指标）。事件直接告诉你「哪坏了、为什么」。

### 2.5 日志查看

```bash
kubectl -n lab logs probe-demo-<pod名> --tail=20     # 最近 20 行
kubectl -n lab logs -l app=probe-demo --tail=5       # 按标签批量
kubectl -n lab logs <pod名> -f                       # 实时跟随
```

多容器 Pod 指定容器：`kubectl -n lab logs <pod> -c <容器名>`。

### 2.6 资源用量监控

```bash
kubectl top nodes
kubectl -n lab top pods
```

（依赖 metrics-server，第 06 章已见输出）。

## 3. 备份：etcd 快照（k3s 内置）

**etcd 是集群的「数据库」**，存着所有资源定义（含 Secret）。节点级别备份 ≠ 集群备份。回到第 05 章的问题：local-path 是 `Delete` 回收策略，数据容易丢，集群级备份必须靠快照。

### 3.1 查看已有快照

```bash
vagrant ssh k3s-demo-server-1 -- "sudo k3s etcd-snapshot list 2>/dev/null | grep -E 'Name|\.zip'"
```

预期输出（有自动快照的话）：

```text
Name                                     Location ...  Size      Created
manual-demo-k3s-demo-server-1-1790989734 file:///var/lib/rancher/k3s/server/db/snapshots/...  17469472  2026-10-03T01:08:54Z
```

> 开启自动快照（k3s 服务端常驻）：`--etcd-snapshot-schedule-cron="0 */6 * * *"` + `--etcd-snapshot-retention=14`（每 6 小时一次，保留 14 个）。

### 3.2 手动打快照

```bash
vagrant ssh k3s-demo-server-1 -- "sudo k3s etcd-snapshot save --name manual-demo"
```

预期输出：

```text
Snapshot manual-demo-k3s-demo-server-1-1790989734 saved.
```

快照文件位置（server 节点上）：

```text
/var/lib/rancher/k3s/server/db/snapshots/manual-demo-k3s-demo-server-1-1790989734
```

刚才我们创建的备份大约 17MB（Size 列 17469472 字节 = etcd 数据压缩后的体积）。

### 3.3 查看快照文件与导出

```bash
# 快照文件实际落在 VM 内；如需异地保存，拷出 VM
vagrant ssh k3s-demo-server-1 -- "sudo ls -lh /var/lib/rancher/k3s/server/db/snapshots/"
```

### 3.4 恢复快照（破坏性操作，仅灾难演练时执行）

```bash
# 进入恢复流程（会重启 k3s 并重建 etcd）
vagrant ssh k3s-demo-server-1 -- "sudo k3s server --cluster-reset --cluster-reset-restore-path=/var/lib/rancher/k3s/server/db/snapshots/<快照名>"
```

> ⚠️ 恢复是**整个集群级**操作：会清空现有 etcd 数据并用快照内容重建，涉及停机。生产恢复前务必先备份当前数据、断开业务流量。这里只演示命令存在，**不要**在实际集群随意执行。

### 3.5 备份的完整性建议

| 层 | 内容 | 工具 |
|----|------|------|
| 集群状态 | etcd（含所有资源、Secret） | k3s etcd-snapshot / velero |
| 应用数据 | PV 里的业务数据 | velero + restic / 应用自身备份 |
| 镜像 | 离线环境关键镜像 | 节点 containerd 导出（第 03 章方法） |
| 配置 | 项目代码、kubeconfig | Git 仓库（本项目即是） |

## 4. Rancher 界面对照

Rancher → 集群 → **Monitoring**（若启用）：指标/告警可视化。
Rancher → 集群 → **Events** 页面：等于 `kubectl get events -A`。
Rancher → 某工作负载 → **⋮ → View Logs**：等于 `kubectl logs`。
备份恢复：建议走 kubectl/k3s 命令（Rancher 无内置 etcd 快照 UI，备份属集群管理职责）。

## 5. 小结

- 探针三兄弟：readiness（流量）、liveness（重启）、startup（慢启动）
- 排障第一现场：`kubectl get events` 看 Warning；`kubectl logs` 看日志
- `kubectl top` 看实时用量（依赖 metrics-server）
- 恢复源：etcd 快照（集群状态）+ 应用数据备份（PV 内容），两手都要硬
- k3s 一条命令打快照：`sudo k3s etcd-snapshot save --name <名>`

2. 把 readinessProbe 的 path 改成 `/not-exist`，观察 `kubectl -n lab get pods` 的 READY 变成 `0/1`，再改回来。
3. 用 `kubectl get events -A --sort-by=.lastTimestamp | grep Warning | tail` 找出集群最近 5 条 Warning 各是什么。
4. 手动打一个名为 `weekly-lab` 的 etcd 快照并在 `list` 中确认出现。
5. 思考：为什么「节点磁盘完整克隆」不能替代 etcd 快照？

<details>
<summary>参考答案</summary>

1. 在容器 spec 加 `startupProbe: {...}` 后 apply，describe 出现 `Startup: ...` 行。
2. READY 列变成 `0/1`（容器 Running 但未就绪），事件出现 `Unhealthy`；改回 `/` 后恢复 `1/1`。
3. 例如 HPA 的 `FailedGetResourceMetric`、镜像相关的 `Failed` 等，逐条看 Message 理解原因。
4. `sudo k3s etcd-snapshot save --name weekly-lab`，list 中出现 `weekly-lab-k3s-demo-server-1-...`。
5. 节点磁盘克隆只反映「那台机器」的磁盘，而集群状态在 etcd（可能分布在多节点、且节点磁盘损坏或整机失联时克隆不可用）；etcd 快照是集群一致性的权威来源。配合应用数据备份才是完整方案。
</details>
