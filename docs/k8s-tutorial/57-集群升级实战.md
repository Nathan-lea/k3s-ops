# 57 集群升级实战：从 v1.30.2 到 v1.30.14

## 章节信息

| 项目 | 内容 |
|------|------|
| 适用平台 | Linux / macOS（标准路径）；Windows（ops VM 路径，命令在 ops VM 内执行） |
| 前置章节 | 00/08/12/38/45/46/48/56 |
| 预计耗时 | 60-120 分钟（含备份、逐节点升级、验收） |
| 破坏性操作 | **高**：升级会重启 k3s/k3s-agent，控制面/API 短时中断，工作负载可能重调度或重启；错误版本/错误顺序可能导致集群不可用。必须先做 etcd 快照并准备回滚。 |
| 实测环境 | k3s v1.30.2+k3s2（2 节点：server-1 192.168.56.10，agent-1 192.168.56.20，embedded etcd）-> v1.30.14+k3s2；实测日期 2026-11-26。 |

## 本章目标

- 理解 k3s/Kubernetes 升级的**通用标准流程**：版本评估 -> 备份 -> server -> agent -> 验收 -> 回写基线。
- 掌握本仓库 `k3s-ops.sh upgrade -v` 的能力边界，并能用标准命令独立完成一次保守升级。
- 能识别单 server embedded etcd、Kyverno webhook 单点、组件兼容性等升级风险。
- 能给出“何时升级、何时止损、不做什么”的判断。

> **边界声明**：本章记录的是一次**同 minor patch 升级**（`v1.30.2+k3s2 -> v1.30.14+k3s2`），不是跨 minor 升级，也不是生产 HA 升级演练。`k3s-ops.sh` 是项目封装；真实升级以 k3s 官方手册和组件兼容矩阵为准。

## 1. 升级前先想清楚

```text
版本评估/兼容性 -> 备份(etcd快照+配置) -> 升级 server -> 验收控制面
                                                |
                                                v
                                       升级 agent(逐台) -> 全量验收 -> 回写基线/文档
                                                |
                                                v
                                           异常? 止损/回滚
```

| 问题 | 本次决策 | 原因 |
|------|----------|------|
| 升到哪个版本？ | `v1.30.14+k3s2` | 同 minor 最新 patch，兼容风险最低；`https://update.k3s.io/v1-release/channels` 显示 `v1.30` 通道为 `v1.30.14+k3s2` |
| 能否跳 minor？ | 不能 | Kubernetes/k3s 升级遵循版本 skew 策略，不支持跳 minor；要上 `v1.31+` 必须逐级 |
| 主流程用什么？ | 标准命令 | 通用、可迁移；`k3s-ops.sh upgrade -v` 作为对照边界记录，未重复执行 |
| agent-1 上 Kyverno 风险怎么处理？ | 接受短时 webhook 拦写风险 | 本次是教学实验集群；已知 Kyverno 4 控制器钉在 agent-1，`failurePolicy=Fail`，重启窗口可能拦写。生产应评估摘 webhook/扩副本/维护窗口 |
| 升级后回退吗？ | 不回退 | 同 minor patch 收益/风险不对称；回退会再次中断。保留快照和旧二进制备份作为止损资产 |

## 2. 备份：先拿到回滚资产

### 2.1 etcd 快照（必须）

```bash
vagrant ssh k3s-demo-server-1 -c \
  "sudo k3s etcd-snapshot save --name before-upgrade-v1.30.14-$(date +%Y%m%d-%H%M%S)"
```

实测输出（节选）：

```text
time="2026-11-26T11:16:39Z" level=info msg="Snapshot before-upgrade-v1.30.14-20261126-191629-k3s-demo-server-1-1795691798 saved."
```

校验快照存在：

```bash
vagrant ssh k3s-demo-server-1 -c "sudo k3s etcd-snapshot ls | tail -5"
```

实测可见快照：

```text
before-upgrade-v1.30.14-20261126-191629-k3s-demo-server-1-1795691798   file:///var/lib/rancher/k3s/server/db/snapshots/...   11362336   2026-11-26T11:16:39Z
```

> 快照是 embedded etcd 单节点升级的关键止损资产。没有快照不升级；本章未实跑 restore（48 章说明 restore 需隔离演练），生产应提前演练。

### 2.2 备份旧二进制（建议）

```bash
# server
vagrant ssh k3s-demo-server-1 -c \
  "sudo cp /usr/local/bin/k3s /usr/local/bin/k3s.bak.v1.30.2+k3s2 && ls -lh /usr/local/bin/k3s*"
# agent
vagrant ssh k3s-demo-agent-1 -c \
  "sudo cp /usr/local/bin/k3s /usr/local/bin/k3s.bak.v1.30.2+k3s2 && ls -lh /usr/local/bin/k3s*"
```

这不是 etcd 数据回滚，只是快速回退二进制的便利手段。

## 3. 升级 server（先控制面）

k3s 官方手动升级要点：替换二进制，重启 k3s 服务；多节点先 server 再 agent。单 server 场景控制面会有中断窗口。

### 3.1 下载并替换二进制

```bash
TARGET=v1.30.14+k3s2
# k3s 下载路径中的 + 要写成 -
VER_URL=${TARGET//+/-}

vagrant ssh k3s-demo-server-1 -c "\
  curl -fsSL -o /tmp/k3s.${TARGET} \
    https://rancher-mirror.rancher.cn/k3s/${VER_URL}/k3s && \
  sudo install -m 0755 /tmp/k3s.${TARGET} /usr/local/bin/k3s && \
  /usr/local/bin/k3s --version | head -2"
```

实测输出：

```text
k3s version v1.30.14+k3s2 (071b1ead)
go version go1.23.10
```

### 3.2 重启并验收

```bash
vagrant ssh k3s-demo-server-1 -c "sudo systemctl restart k3s && sleep 10 && sudo systemctl is-active k3s"
kubectl --kubeconfig ./kubeconfig get nodes -o wide
```

实测：

```text
active
```

## 4. 升级 agent

### 4.1 风险提示（Kyverno）

本集群 Kyverno 4 控制器钉在 `k3s-demo-agent-1`，webhook `failurePolicy=Fail`。agent-1 重启期间，依赖这些 webhook 的命名空间写入可能被拦截。**本次实测选择接受该短时风险**。

若要降低风险，可在维护窗口执行 Kyverno 逃生两步（顺序不可反）：

```bash
# 1) 缩容控制器
kubectl -n kyverno scale deploy --all --replicas=0
# 2) 删除 webhook（仅删除 kyverno 管理的）
kubectl delete validatingwebhookconfiguration,mutatingwebhookconfiguration \
  -l webhook.kyverno.io/managed-by=kyverno
```

恢复：

```bash
kubectl -n kyverno scale deploy --all --replicas=1
# 控制器会自愈重建 webhook，需验收
kubectl get validatingwebhookconfiguration,mutatingwebhookconfiguration | grep kyverno || true
```

### 4.2 下载、替换、重启

```bash
TARGET=v1.30.14+k3s2
VER_URL=${TARGET//+/-}

vagrant ssh k3s-demo-agent-1 -c "\
  curl -fsSL -o /tmp/k3s.${TARGET} \
    https://rancher-mirror.rancher.cn/k3s/${VER_URL}/k3s && \
  sudo install -m 0755 /tmp/k3s.${TARGET} /usr/local/bin/k3s && \
  /usr/local/bin/k3s --version | head -2"

vagrant ssh k3s-demo-agent-1 -c "sudo systemctl restart k3s-agent && sleep 10 && sudo systemctl is-active k3s-agent"
```

实测：

```text

active
```

节点验收：


## 5. 升级后验收与异常处理

### 5.1 基线验收

```bash
export KUBECONFIG=./kubeconfig
kubectl get nodes -o wide
kubectl get pods -A --no-headers | awk '$4!="Running" && $4!="Completed" {print}'
kubectl version
```

实测关键结果：

```text
# kubectl version（节选）
Client Version: v1.37.2
Kustomize Version: v5.8.1
Server Version: v1.30.14+k3s2
Warning: version difference between client (1.37) and server (1.30) exceeds the supported minor version skew of +/-1
```

> 客户端/服务端 skew 警告是环境现状（kubectl 较新），不是本次升级引入的阻断；建议后续按需对齐 kubectl，但不要在升级窗口同时改动过多变量。

### 5.2 本次遇到的异常：CoreDNS Pod 卡在 ContainerCreating

现象：agent 升级后，一个新 CoreDNS Pod `coredns-645bdb8675-scvvt` 在 `k3s-demo-agent-1` 上 `ContainerCreating`，`kubectl describe` 未显示明确致命事件，等待一段时间仍未恢复。

处理（低风险，系统组件可由控制器重建）：

```bash
kubectl --kubeconfig ./kubeconfig delete pod -n kube-system coredns-645bdb8675-scvvt --force --grace-period=0
kubectl --kubeconfig ./kubeconfig get pods -n kube-system -o wide | grep coredns
```

结果：新 Pod `coredns-645bdb8675-5299b` 调度到 `k3s-demo-server-1`，短暂 `ContainerCreating` 后变为 `Running`。集群回到“仅 3 个已知 policy-demo Unknown 残留”的基线。

**判断原则**：先确认是否升级引入、是否影响核心功能、是否可由控制器自愈；不要把“旧残留”当新事故，也不要把“偶发拉起慢”升级成破坏性操作。

### 5.3 应抽样验证的组件

| 组件 | 验收命令 | 本次说明 |
|------|----------|----------|
| 节点/系统 Pod | `kubectl get nodes,pods -A` | 两节点 Ready；系统 Pod 恢复正常 |
| Ingress | `kubectl -n ingress-nginx get pods,svc` | 建议抽样；本次未变更 ingress 配置 |
| Gateway/NGF | `kubectl -n nginx-gateway get pods,gateway` | 建议抽样 |
| cert-manager | `kubectl -n cert-manager get pods` | 建议抽样 |
| Rancher/Fleet | `kubectl -n cattle-system get pods` | 建议抽样；Rancher Helm 历史 `failed` 为既有状态 |
| Kyverno | `kubectl -n kyverno get pods,validatingwebhookconfiguration` | agent-1 重启后应确认 webhook/控制器恢复 |

## 7. k3s-ops.sh upgrade 的边界

仓库封装：

```bash
./k3s-ops.sh upgrade -v v1.30.14+k3s2
```

它实际做的事（`k3s-ops.sh` -> `ansible/playbooks/k3s-upgrade.yml` -> `k3s-manage/tasks/upgrade.yml`）：

- 逐节点 `serial: 1` 执行。
- 从 `rancher-mirror.rancher.cn` 下载目标 `k3s` 二进制覆盖 `/usr/local/bin/k3s`。
- `systemctl restart k3s` 或 `k3s-agent`。
- 在 `first_server_host` 上 `kubectl wait --for=condition=Ready node/<node> --timeout=120s`。

它**没有**做的事（需要人工/标准流程补）：

- 升级前版本兼容性检查（不阻止跳 minor）。
- etcd 快照、备份校验、回滚点管理。
- cordon/drain、PDB/业务中断评估。
- 组件兼容性矩阵检查（Rancher/Fleet/Kyverno/Ingress 等）。
- 升级后全量 smoke 验收与基线回写。

**结论**：`k3s-ops.sh upgrade -v` 可作为受控环境的便利封装；本次实战选择标准命令主流程，是为了把边界、证据和止损点讲清楚。后续可在隔离场景补一次封装对照实测。

## 8. 回滚与止损思路

本次未回退；以下是“何时停、怎么退”的最小原则。

| 场景 | 建议动作 |
|------|----------|
| server 升级后未 Ready/API 异常 | 停止升级 agent；检查 `journalctl -u k3s`、`/var/log/syslog`、etcd；必要时用旧二进制恢复 server 并评估快照恢复 |
| agent 升级后 NotReady | 停止其他 agent；检查 `journalctl -u k3s-agent`、containerd、镜像拉取、网络；必要时回退该 agent 二进制 |
| 核心组件大面积异常 | 停止变更，保留现场证据；按 36 Runbook 分诊；评估快照恢复窗口 |
| 仅个别 Pod 异常 | 先判断是否旧残留/偶发；优先低风险重建（如 CoreDNS）；不要扩大变更面 |

> embedded etcd 单 server 的快照恢复是高风险操作，应在隔离环境演练后再用于生产。旧二进制备份可用于“服务起不来”的快速回退，但不等于数据面回滚。

## 10. 小结

- 同 minor patch 升级是最保守的实战入口：先备份、先 server、再 agent、每步验收。
- 标准命令是主流程；`k3s-ops.sh upgrade -v` 是便利封装，但缺少快照/兼容性/业务中断/全量验收等护栏。
- 单 server embedded etcd + Kyverno 单点是本环境的真实风险点，升级前必须显式决策。
- 升级后要回写仓库基线（nodes.yml/group_vars/architecture），避免“集群已升、配置未升”。
