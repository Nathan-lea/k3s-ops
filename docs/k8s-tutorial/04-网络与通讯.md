# 04 网络与通讯：Service / Ingress / DNS / 流量路径

## 本章目标

- 理解组件间通讯的完整链路（kubectl → apiserver → etcd → kubelet → 容器）
- 掌握三种流量的区别：Pod 间、Pod↔Service（ClusterIP/NodePort）、集群外部→Ingress
- 会用 kubectl 查看 Service/Endpoints/Ingress/DNS，并动手暴露一个应用
- 理解本集群用到的 flannel（VXLAN）与 nginx-ingress

---

## 1. 网络模型总览

K8s 网络模型四大铁律：
1. 每个 Pod 有**独立的集群内 IP**，Pod 间可直接通信（无需 NAT）
2. 节点上的 **kube-proxy** 实现 Service 的负载均衡与转发
3. **DNS**（coredns）提供集群内服务名解析
4. **Ingress** 把外部 HTTP(S) 流量按域名/路径路由到 Service

```
                   外部流量
                      │
                      ▼
            ┌──────────────────┐
            │ Ingress-nginx     │  :30080 (HTTP) / :30444 (HTTPS)
            │ (ingress-nginx ns)│  ← 真正的"大门"
            └────────┬─────────┘
                     │ 按 Host/Path 路由
                     ▼
            ┌──────────────────┐
            │ Service (ClusterIP│  10.43.23.169
            │ 或 NodePort)      │  ← 稳定的虚拟入口
            └────────┬─────────┘
                     │ kube-proxy (iptables 轮询)
                     ▼
        ┌────────────┼────────────┐
        ▼            ▼            ▼
    Pod 10.42.0.245 Pod 10.42.0.246 Pod 10.42.0.247   ← 实际干活的容器
```

## 2. 组件通讯链路（纵向回顾）

```
kubectl apply -f xxx.yaml
   │  HTTPS → 192.168.56.10:6443
   ▼
kube-apiserver (认证/授权/校验 → 写 etcd)
   │ watch 通知
   ├──► scheduler: 选节点、写绑定
   ├──► controller-manager: 创建 RS、Pod
   └──► kubelet (node): 收到分给我的 Pod → containerd 创建容器
                      └─ coredns 为 Service 提供名字解析
                      └─ kube-proxy 生成 iptables 规则
```

**核心记忆**：哪个组件都不"直接"连别人（业务流量除外），全走 apiserver；etcd 只服务 apiserver。

## 3. Service 五种类型

| 类型 | ClusterIP | 后端 | DNS 返回 | 负载均衡 | 典型场景 |
|------|-----------|------|---------|---------|---------|
| **ClusterIP** | ✅ | 集群内 Pod | 1 条虚拟 IP | kube-proxy | 默认内网服务互调 |
| **NodePort** | ✅ | 集群内 Pod | 1 条虚拟 IP | kube-proxy | 外部访问（无 LB 时） |
| **LoadBalancer** | ✅ | 集群内 Pod | 1 条虚拟 IP | 云 LB + kube-proxy | 公有云外部访问 |
| **Headless** | ❌（None） | 集群内 Pod | **多条真实 Pod IP** | **客户端自己做** | 有状态应用/自定义负载均衡 |
| **ExternalName** | ❌ | **外部域名** | **CNAME 别名** | N/A | 外部服务接入/迁移过渡 |

> 前三种（ClusterIP/NodePort/LoadBalancer）是"虚拟 IP 家族"——都有 ClusterIP、都由 kube-proxy 做负载均衡；后两种是"特殊形态"，详见 3.1/3.2。
> k3s 内置 ServiceLB（`--disable-servicelb` 已禁用），所以本集群用 NodePort + Ingress。

### 3.1 Headless Service（无头服务：`clusterIP: None`）

**是什么**：把 Service 的 `spec.clusterIP` 设为 `None`，K8s 就不分配虚拟 IP、也不生成 kube-proxy 转发规则——这个 Service 名下只有 DNS 记录，没有"门牌地址"。

**核心差异：DNS 返回什么**（与普通 Service 的全部区别）：

```text
普通 Service : redis.lab.svc.cluster.local → 10.43.x.x     一条虚拟 IP（kube-proxy 做 LB）
Headless     : redis.lab.svc.cluster.local → 10.42.0.57    多条真实 Pod IP（客户端自己选）
                                            10.42.0.58
                                            10.42.0.66
              : pod-0.redis.lab.svc.cluster.local → 10.42.0.57   ★ 还能按 Pod 名精确解析
```

**典型场景**：
1. **有状态应用直连**：数据库集群通过 `pod-0.redis.xxx.svc...` 固定访问 0 号实例——StatefulSet 标配（第 05 章存储同理，Pod 名固定）
2. **客户端自己做负载均衡**：Redis Cluster / MongoDB 副本集需要"拿到全部节点，自己发现主从"，不想要虚拟 IP 挡在中间
3. **P2P 协议**：etcd、Cassandra 这类要真实节点地址

```yaml
apiVersion: v1
kind: Service
metadata: { name: redis, namespace: lab }
spec:
  clusterIP: None            # ★ 就这一个字段，普通 Service 变 Headless
  selector: { app: redis }
  ports: [{ port: 6379, targetPort: 6379 }]
```

> 特点：**没有负载均衡**（LB 责任移交给客户端）；选它 = 明确告诉 K8s"后端寻址我自己管"。

### 3.2 ExternalName（外部名服务）

**是什么**：`type: ExternalName + externalName: 外部域名`。它**不选择任何 Pod、不创建 Endpoints**，DNS 直接返回一条 **CNAME 别名**：

```text
ext-db.lab.svc.cluster.local  ──CNAME──▶  db.example.com  ──▶ 外部真实 IP
```

**典型场景**：
1. **外部服务包装**：云数据库、SaaS API、老系统域名，包成集群内名字——应用代码零改动
2. **迁移过渡桥**：代码先用内网名指向旧系统（ExternalName）；迁进集群后把 Service 改成普通类型即可，**代码一行不改**
3. **跨集群引用**：间接访问别的集群的服务域名

```yaml
apiVersion: v1
kind: Service
metadata: { name: ext-db, namespace: lab }
spec:
  type: ExternalName          # ★ 类型字段
  externalName: db.example.com   # 必须是 DNS 名，不能填 IP
```

**限制（容易踩的坑）**：
- **只有 DNS 层生效**：解析结果直接跳到外部 IP，没有端口转发/流量路径——`ports` 只是给客户端看的参考
- **`externalName` 不能填 IP**（API 校验拒绝），必须是合法域名
- 依赖解析器支持 CNAME（集群内 CoreDNS 支持，无问题）

## 4. 本集群实站对照

### 4.1 暴露 nginx 服务（NodePort）

基于第 03 章的 `nginx-demo` Deployment 创建 Service：

```bash
kubectl -n lab expose deployment nginx-demo --type=NodePort --port=80 --target-port=80 --name=nginx-svc
```

预期输出：

```
service/nginx-svc exposed
```

```bash
kubectl -n lab get svc nginx-svc -o wide
```

预期输出（本环境真实）：

```
NAME        TYPE       CLUSTER-IP     EXTERNAL-IP   PORT(S)        AGE   SELECTOR
nginx-svc   NodePort   10.43.23.169   <none>        80:32062/TCP   1s    app=nginx-demo
```

两个关键端口：
- `80` = ClusterIP 上的端口（集群内访问用）
- `32062` = NodePort（外部 `节点IP:32062` 访问用）

### 4.2 查看 Service 背后的 Pod（Endpoints）

```bash
kubectl -n lab get endpoints nginx-svc
```

预期输出：

```
NAME        ENDPOINTS                                                  AGE
nginx-svc   10.42.0.245:80,10.42.0.246:80,10.42.0.247:80 + 2 more...  34s
```

Endpoints 就是 Service selector 命中的 Pod 列表 —— **kube-proxy 根据它生成转发规则**。

### 4.3 从宿主机访问 NodePort

```bash
curl -s -o /dev/null -w "%{http_code}\n" http://192.168.56.10:32062/
```

预期输出：`200`

### 4.4 集群内通过 Service 名访问（DNS）

在任意容器内（这里是 nginx 容器）：

```bash
kubectl -n lab exec <pod名> -- curl -s -o /dev/null -w "%{http_code}\n" http://nginx-svc.lab/
```

预期输出：`200`

DNS 解析规则（记住这个格式）：

```
<service>.<namespace>.svc.cluster.local
   nginx-svc . lab     .svc.cluster.local
```

查看集群 DNS 服务：

```bash
kubectl -n kube-system get svc kube-dns
```

预期输出：

```
NAME       TYPE        CLUSTER-IP   EXTERNAL-IP   PORT(S)                  AGE
kube-dns   ClusterIP   10.43.0.10   <none>        53/UDP,53/TCP,9153/TCP   130d
```

`10.43.0.10` 是每个 Pod 的 `/etc/resolv.conf` 里配置的 DNS 服务器（coredns）。

### 4.5 Ingress —— 按域名路由（推荐生产方式）

创建 Ingress 把 `lab.k3s.local` 路由到 `nginx-svc:80`：

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: nginx-ing
  namespace: lab
spec:
  ingressClassName: nginx
  rules:
    - host: lab.k3s.local
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: nginx-svc
                port:
                  number: 80
```

```bash
kubectl apply -f ingress.yaml
kubectl -n lab get ingress
```

预期输出：

```
NAME        CLASS   HOSTS           ADDRESS   PORTS   AGE
nginx-ing   nginx   lab.k3s.local             80      1s
```

```bash
kubectl -n lab describe ingress nginx-ing
```

预期输出（节选，关键在 Backends）：

```
  lab.k3s.local
                 /   nginx-svc:80 (10.42.0.245:80,10.42.0.246:80,10.42.0.247:80 + 2 more...)
Events:
  Normal  Sync  nginx-ingress-controller  Scheduled for sync
```

从宿主机携带 Host 头访问（nginx-ingress 监听 nodePort **30080** HTTP）：

```bash
curl -s -o /dev/null -w "%{http_code}\n" -H "Host: lab.k3s.local" http://192.168.56.10:30080/
```

预期输出：`200`

> 没有 DNS 就把 `lab.k3s.local` 写进本机 `/etc/hosts`（192.168.56.10），即可用域名访问。

### 4.6 流量路径总结（从外到内，背下来）

```
curl http://192.168.56.10:30080/   (Host: lab.k3s.local)
  1. 到达任一节点 :30080 (nginx-ingress NodePort)
  2. ingress-nginx-controller 按 Host 匹配 Ingress 规则
  3. 路由到 Service  nginx-svc:80
  4. kube-proxy iptables 规则 → 随机选一个 endpoint
  5. 到达 Pod (10.42.0.x) 内容器 → 响应返回
```

## 5. 集群与外部如何通讯

| 方向 | 机制 |
|------|------|
| 外部→集群 | Ingress（30080/30444）或 NodePort；本环境也可端口转发（Vagrant 把 30443→8443 等） |
| 集群→外部 | Pod 出网经节点 NAT（SNAT）；节点再经宿主机/VirtualBox NAT 上网 |

```bash
# 验证 Pod 出网（nginx 容器内）
kubectl -n lab exec <pod名> -- curl -sI -m 5 https://www.baidu.com | head -1
```

## 6. Rancher 界面对照

Rancher → 集群 → **Service Discovery → Services**：看到所有 Service（含 NodePort）
- **Service Discovery → Ingresses**：Ingress 列表，点进可看按域名分组的路由
- 集群 → **Service Discovery → DNS**：查看集群 DNS 配置

## 7. 小结

- Service 是稳定的虚拟入口，Endpoints 是背后的真实 Pod，kube-proxy 负责转发
- DNS 名格式：`<svc>.<ns>.svc.cluster.local`
- NodePort 适合临时暴露，Ingress 适合生产（域名/路径/TLS 管理）
- 外部入口在本集群是 nginx-ingress 的 30080/30444
