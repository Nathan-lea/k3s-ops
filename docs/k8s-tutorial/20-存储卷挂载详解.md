## 本章目标

- 理解 **Volume（存储卷）为什么存在**：容器文件系统是"一次性"的，卷把数据/配置与容器解耦

## 1. 概念与原理：为什么需要卷

### 1.1 容器文件系统的"一次性"

容器由**镜像层（只读）+ 容器层（可写）**构成：

```text
镜像层（只读）: nginx:alpine 的 OS + 程序，所有容器共享
容器层（可写）: 容器运行时写入（日志、缓存、改动）
```

问题：**容器删除 = 容器层销毁**。容器崩溃重建、Deployment 滚动更新（第 03 章）→ 新容器从头开始。镜像又是只读的，应用想"把数据留下"无处可写。

### 1.2 Volume 的本质：Pod 级目录声明

K8s 的答案：**Volume 是 Pod 级的一块"可挂载目录"，声明在 Pod 上，与 Pod 同生命周期**：

```text
Pod
├── 容器 A ──mount──▶ /data   ──┐
├── 容器 B ──mount──▶ /shared ──┤ Volume（独立于容器的存储单元）
└── volumes: []（Pod 清单里声明）┘
```

两个关键性质：

1. **卷活过容器**：容器重建，卷里的数据还在（只要 Pod 还在）
2. **多个容器可共享**：同一 Pod 的多个容器挂同一卷，可做"sidecar 模式"（主容器写日志 → sidecar 读/转发）

### 1.3 三个生命周期层级（核心概念，先记住这张表）

| 层级 | 谁创建的 | 活得多久 | 删除时 | 典型卷 |
|------|---------|---------|--------|--------|
| **容器层** | 运行时 | 同容器 | 随容器销毁 | （无卷） |
| **Pod 级卷** | Pod spec | 同 Pod | 随 Pod 删除**一并销毁** | emptyDir、hostPath（引用节点目录除外） |
| **集群级卷（PV）** | 管理员/SC 动态供给 | **独立于 Pod** | 按 reclaimPolicy（Delete/Retain） | PVC 背后的 PV、NFS、云盘 |

> **一句话**：emptyDir 是"给 Pod 的临时抽屉"，PV 是"租给 Pod 的保险箱"——保险箱不随人走，抽屉随人撤。

### 1.4 挂载的本质：两处声明、一个动作

挂载 = 把 Pod 清单里**已经存在的卷**，标一个**容器内的路径**（挂点）：

```yaml
# ① Pod 级：声明有哪些卷（volumes）
spec:
  volumes:
  - name: data            # 卷的名字（引用句柄）
    persistentVolumeClaim:
      claimName: nginx-data
  containers:
  - name: nginx
    # ② 容器级：声明把哪个卷挂到哪（volumeMounts）
    volumeMounts:
    - name: data
      mountPath: /data
```

- `volumes[].name` 与 `volumeMounts[].name` **必须一致**（凭名字对接）
- `mountPath` 是容器内路径；**目录已存在也没关系，卷会"盖"上去**（见 §5.5 覆盖陷阱）

## 2. 六类卷全览（本集群全部真实存在）

### 2.0 全集群统计（`kubectl get pods -A -o json` 逐卷统计）

```text
 32 projected       ← 服务账号 token 注入（几乎每个 Pod 都有）★
  7 emptyDir        ← 临时空间（coredns / ingress-nginx 等）
  7 configMap       ← 配置文件注入（coredns 等）
  3 hostPath        ← 节点目录（system-upgrade-controller 挂 CA 证书）
  2 secret          ← 证书注入（ingress-nginx webhook-cert）
  1 persistentVolumeClaim  ← 持久盘（pvc-writer → nginx-data）
```

> 这组数字本身就是教学：**绝大多数卷是"配置/身份注入"（projected+CM+Secret ≈ 41 个）**，真正"存数据"的（PV）只有 1 个——说明集群里大多数挂载不是为了持久化，而是为了"把东西送进容器"。

### 2.1 emptyDir：Pod 级临时目录（删 Pod 即毁）

```yaml
volumes:
- name: tmp
  emptyDir: {}          # 默认在节点磁盘；可加 medium: Memory 用内存(tmpfs)
```

| 项 | 值 |
|----|----|
| 生命周期 | **同 Pod**：Pod 删，emptyDir 连同数据一起消失；容器重启不丢 |
| 存储位置 | Pod 所在节点的磁盘（或内存） |
| 典型用途 | 日志中转、缓存、临时文件、sidecar 之间传文件 |
| 本集群样例 | coredns 与 ingress-nginx 的 `tmp` 卷（实测 7 个） |

> 排障提醒：emptyDir **不随 Pod 迁移**（第 17 章"数据单节点"）——drain 驱逐后重建的 Pod 是新目录，旧数据没了。它是"活的临时区"，不是"存数据的地方"。

### 2.2 hostPath：直接映射节点目录（慎用）

```yaml
volumes:
- name: etc-ssl
  hostPath:
    path: /etc/ssl          # 节点上这个目录
    type: DirectoryOrCreate # 不存在就建
```

| 项 | 值 |
|----|----|
| 生命周期 | **节点目录**：与 Pod 无关，节点在数据就在 |
| 谁的文件 | 节点文件系统——**与宿主机共享**，容器能读能写 |
| 典型用途 | 需要访问节点系统文件/设备的系统组件（CA 证书、docker.sock、日志目录）；**业务负载尽量避免** |
| 本集群样例 | system-upgrade-controller 挂 `/etc/ssl`、`/etc/pki`、`/etc/ca-certificates` 三个 CA 目录（实测 DirectoryOrCreate） |

> 为什么慎用：① 把 Pod 钉死在节点上（换了节点目录不一定有）；② 权限大，容器逃逸风险点；③ 数据不受 K8s 管理，备份/迁移都麻烦。**能用 PVC/NFS 就别用 hostPath**。

### 2.3 ConfigMap / Secret：把配置和证书"送"进容器

```yaml
volumes:
- name: config-volume
  configMap:
    name: coredns          # 整个 CM 变目录：每个 key 是一个文件
- name: webhook-cert
  secret:
    secretName: ingress-nginx-admission  # 同样，每个 key 是文件
```

| 项 | 值 |
|----|----|
| 生命周期 | **API 对象**（etcd）管理的配置；卷内容是它的"快照" |
| 内容形态 | 卷 = 目录，CM/Secret 的**每个 key 变成一个文件**，value 是文件内容 |
| 热更新 | **整卷挂载会热同步**（改 CM，容器内文件自动更新，几秒内）——见 §5.6 边界 |
| 只读建议 | 配置类一律 `readOnly: true` |
| 本集群样例 | coredns 两个 CM 卷（`config-volume → /etc/coredns`、`custom-config-volume → /etc/coredns/custom`）；ingress-nginx 的 `webhook-cert` Secret 卷：**32 个 projected 里也内含 CM** |

> Secret 的"机密"程度别高估：**value 只 base64 编码，非加密**（第 05 章实测过），别当密码保险库用。

### 2.4 downwardAPI + projected：把"元数据"送进容器

**downwardAPI**：把 Pod 自身的元数据（名字、命名空间、IP、标签）暴露成文件或环境变量：

```yaml
volumes:
- name: podmeta
  downwardAPI:
    items:
    - path: namespace
      fieldRef: { fieldPath: metadata.namespace }
```

**projected（投影卷）**：把**多种来源合并成一个目录**——K8s 1.20+ 给 Pod 注入服务账号信息就靠它。本集群 coredns 实测完整定义：

```yaml
volumes:
- name: kube-api-access-rfp9f
  projected:
    defaultMode: 420                    # 0644
    sources:
    - serviceAccountToken:              # ① 服务账号 token
        expirationSeconds: 3607
        path: token
    - configMap:                        # ② 集群 CA 证书
        name: kube-root-ca.crt
        items: [{key: ca.crt, path: ca.crt}]
    - downwardAPI:                      # ③ 元数据：命名空间
        items: [{fieldRef: {fieldPath: metadata.namespace}, path: namespace}]
```

挂载后容器内（实测文件列表）：

```bash
kubectl -n lab exec pvc-writer -- ls /var/run/secrets/kubernetes.io/serviceaccount/
# 输出:
# ca.crt   namespace   token
```

| 项 | 值 |
|----|----|
| 谁在用 | **每个 Pod 默认都有**（kube-api-access，全集群 32 个，占比第一） |
| 作用 | 让容器安全拿到"我是谁、集群 CA、访问 API 的 token"——SDK 连 apiserver 的凭证 |
| 为什么重要 | K8s 服务发现（第 19 章）＋认证靠它：容器里 `https://kubernetes.default.svc` 的调用就是用它鉴权 |

### 2.5 persistentVolumeClaim：真正的持久盘（数据能活过 Pod）

```yaml
volumes:
- name: data
  persistentVolumeClaim:
    claimName: nginx-data      # 引用一个 PVC
```

本集群 `lab/pvc-writer` Pod 实测：

```text
vol: data  type=persistentVolumeClaim  claim=nginx-data
mount: data → /data
```

**这是六类里唯一"数据独立于 Pod"的类型**——Pod 删了，PVC/PV 和盘上数据还在（§3 详讲）。

### 2.6 六类选型速查表

| 卷类型 | 生命周期 | 数据持久 | 跨节点 | 典型用途 | 生产建议 |
|--------|---------|---------|--------|---------|---------|
| emptyDir | 同 Pod | ❌ | ❌ | 缓存/中转 | ✅ 临时数据 |
| hostPath | 节点 | ✅（节点在就在） | ❌ | 系统组件读节点文件 | ⚠️ 少用 |
| ConfigMap/Secret | API 对象 | ✅（对象活着就活） | ✅ | 配置/证书注入 | ✅ 配置 |
| downwardAPI/projected | 同 Pod | ❌ | ❌ | 元数据/token | ✅ 身份注入 |
| **PVC（PV）** | **独立于 Pod** | **✅** | ❌（local-path）/✅（网络盘） | 数据库、文件、持久业务数据 | ✅ 生产数据 |

## 3. 持久化三件套原理：PVC / PV / StorageClass

### 3.1 三者的分工（"声明-供给-绑定"铁三角）

```text
PVC（用户声明）:  我要 1Gi、只能单节点写（RWO）—— 用 local-path 供给
PV（实际卷）:     pvc-6172...（1Gi RWO）+ 数据落在 server-1 的 /var/lib/rancher/k3s/storage/
StorageClass:   local-path —— 知道"怎么造 PV"的模板（provisioner: rancher.io/local-path）
```

### 3.2 静态供给 vs 动态供给

| 方式 | 谁造 PV | 流程 | 本集群 |
|------|--------|------|--------|
| **静态** | 管理员预先造好 PV | 创建 PVC → 控制面找匹配 PV 绑定 | 无 |
| **动态**（推荐） | **StorageClass 按需造** | PVC 指名 SC → 控制器动态 provision 新 PV → 绑定 | ✅ local-path（实测 `provisioned-by: rancher.io/local-path`） |

本集群 PV 实测证明动态供给 + 落点：

```bash
kubectl get pv pvc-61720575-6d78-4437-8d50-553a7b4c8fc8 \
  -o jsonpath='{.metadata.annotations.pv\.kubernetes\.io/provisioned-by} | {.spec.local.path}'
# 输出: rancher.io/local-path | /var/lib/rancher/k3s/storage/pvc-6172...
```

### 3.3 绑定流程（本集群实测状态机）

```text
创建 PVC（storageClassName: local-path）
   │
   ▼
Pending —— WaitingForFirstConsumer（SC 的 bindingMode 实测）
   │    ↑ 还没 Pod 用它，先不造卷（懒绑定）
   ▼
首次被 Pod 引用 → 调度器定节点 → 动态造 PV → 绑定
   │
   ▼
Bound（pvc-6172... ↔ lab/nginx-data，第 05 章实验的完整链路）
```

实测 SC：

```text
local-path (default)   rancher.io/local-path   Delete   WaitForFirstConsumer   false
```

### 3.4 访问模式（accessModes）

| 模式 | 含义 | 本集群 |
|------|------|--------|
| **RWO**（ReadWriteOnce） | 仅**单节点**可读写 | ✅ 实测（local-path 只能是 RWO） |
| ROX | 单节点只读 | — |
| **RWX** | **多节点**同时读写（NFS/CephFS 等共享存储） | —（local-path 不支持） |

local-path 与 RWO 的关联：数据在单节点磁盘上（第 17 章 nodeAffinity 实测）——所以**多副本 Pod 若共用同一块本地盘 PVC 会调度冲突**（一个节点能挂，另一个挂不上）。

### 3.5 回收策略（reclaimPolicy）

| 策略 | 删 PVC 时 PV 和数据 | 本集群 |
|------|-------------------|--------|
| **Delete** | **连 PV 带数据一起删**（local-path 把磁盘目录也清掉） | ✅ 实测 |
| Retain | PV 保留、数据保留，但变 Released 需人工处理 | — |
| Recycle | 已废弃 | — |

> **血的教训**：local-path 默认 Delete + 数据在节点磁盘——`kubectl delete pvc` 一按，**数据即销毁，且不经过回收站**。删前确认（或先用第 12 章快照/文件备份）。

### 3.6 其他字段

- `allowVolumeExpansion: false`（实测）：local-path 不允许在线扩容，改大容量需重建
- `volumeMode`：Filesystem（默认）/ Block（块设备）
- 多 PVC 一 Pod：`pvc-writer` 同时挂 PVC 和 projected（§2.4）就是实例

## 4. 挂载细节与最佳实践

### 4.1 一个卷挂多个容器（共享）

同 Pod 两个容器挂同一卷 → 双向可见：主容器写日志，sidecar 容器读日志转发。经典 sidecar 模式。

### 4.2 一个容器挂多个卷

`volumeMounts` 是数组；注意避免两个挂点互相嵌套覆盖。

### 4.3 subPath：只挂子目录/单文件

```yaml
volumeMounts:
- name: config-volume
  mountPath: /etc/nginx/nginx.conf
  subPath: nginx.conf        # 只把 CM 里的 nginx.conf 一个 key 挂成文件
```

| 用法 | 场景 | 坑 |
|------|------|----|
| 整卷挂目录 | 目录下所有 key 都是文件 | 覆盖目标目录原内容（§4.5） |
| subPath 单文件 | 只想覆盖一个配置文件 | **subPath 挂载不热更新**（改 CM 不会同步到文件！）|

### 4.4 readOnly

配置类卷（CM/Secret）一律 `readOnly: true`；数据类（PVC）按需。

### 4.5 覆盖陷阱（最常踩）

**挂载会"盖住"目标目录里原有的内容**。例：nginx 镜像默认 `/usr/share/nginx/html` 有 index.html；若把 PVC 整卷挂到该路径，原 index.html 被"藏"起来（卷为空则 404）。应对：挂到空子目录，或用 subPath 只覆盖单文件、或 `initContainer` 先拷贝。

### 4.6 热更新边界（CM/Secret）

- **整卷挂载**：改 CM → 控制面更新 → kubelet 同步 → 容器内文件自动更新（**秒级**，但**不重启进程**——应用得自己监听文件）
- **subPath 挂载、环境变量方式注入**：**不热更新**，需重建 Pod
- 口诀：**文件挂载会同步，子路径和环境变量不同步**

## 5. 应用场景串讲（本集群 + 生产）

| 场景 | 用什么卷 | 说明 |
|------|---------|------|
| Web 静态文件/上传目录 | PVC | 挂 `/usr/share/nginx/html`（注意覆盖陷阱） |
| 数据库数据 | PVC（RWO + 单副本或 StatefulSet） | 数据活过 Pod；升级前快照 |
| 应用日志 | emptyDir + sidecar | 日志跟随 Pod 生命周期，sidecar 转发出去 |
| 配置文件 | ConfigMap | 整卷挂载 + 热更新 |
| 证书/密钥 | Secret | TLS 证书、webhook 证书（ingress-nginx 实测） |
| 访问集群 API 的凭证 | projected（默认自带） | 每个 Pod 的 `/var/run/secrets/.../serviceaccount` |
| 多副本共享读写 | RWX 网络存储（NFS/CephFS） | local-path 做不到，需换 CSI |

## 6. 排障：挂载失败与数据安全（四层链路）

### 6.1 四层模型

```text
① YAML 层    : volumes/volumeMounts 名字对得上吗？mountPath 冲突？
② PVC 层     : Status 是 Bound 吗？为什么 Pending？
③ PV 层      : 绑定对了吗？accessModes/容量匹配吗？
④ 数据层     : 数据真落对节点了吗？容器里看得到吗？
```

### 6.2 现象 → 定位表

| 现象 | 最常见原因 | 第一命令 |
|------|-----------|---------|
| Pod 一直 ContainerCreating | 挂载等待/失败 | `kubectl describe pod` 的 Events：看 `MountVolume` / `FailedMount` |
| PVC 卡 Pending | SC 不存在 / 动态供给失败 | `kubectl describe pvc` 看 Events（`waiting for first consumer` 不算错，等 Pod 引用） |
| PVC Bound 但容器目录空 | 数据本来就没写入 / 落点在别的节点 | `kubectl exec <pod> -- ls <mountPath>`；查 selected-node（第 18 章） |
| 多副本挂同一 RWO PVC | **挑 node 冲突**：一个副本 Bound，另一个 Pending | 换 RWX 存储，或改为单副本/每个副本独立 PVC |
| 改 CM 容器内文件不变 | **subPath 挂载不热更新** | 换整卷挂载，或重建 Pod |
| 只读文件系统报错 | 卷 readOnly 或容器用户无权限 | `chmod/chown`（initContainer 做）；SC 层看 fsGroup |
| 删 PVC 后数据"不见了" | reclaimPolicy=Delete（local-path 默认） | 恢复靠节点目录备份（`/var/lib/rancher/k3s/storage/pvc-*`） |
| 节点故障数据取不回 | local-path 数据单节点（第 17 章） | 无备份则丢；生产用网络存储 + 快照 |

### 6.3 完整排查案例（只读不破坏）

```bash
# 症状：新部署的 pod 卡 ContainerCreating，describe 看到
# Events: FailedMount  MountVolume.SetUp failed for volume "data"

# ① YAML：卷和挂载名字是否一致
kubectl -n lab get deploy <应用> -o yaml | grep -A5 "volumes:\|volumeMounts:"

# ② PVC 状态
kubectl -n lab get pvc | grep <claim>          # Bound？Pending？
kubectl -n lab describe pvc <claim>            # Events: ProvisioningFailed?

# ③ SC 与绑定
kubectl get sc                                   # local-path 在吗？default 标了吗？
kubectl -n lab get pvc <claim> -o jsonpath='{.spec.volumeName}'   # 绑到哪个 PV

# ④ 数据层
kubectl -n lab get pvc <claim> -o jsonpath='{.metadata.annotations.volume\.kubernetes\.io/selected-node}'
# 数据在这台节点；exec 进去看目录内容
```

> **心法**：挂载问题九成在"名字对不上 / 该等没等（Pending）/ 选择器或模式不匹配（RWO 冲突）"三处，describe 的 Events 会把原因直接写出来——**先 describe，别猜**。

### 6.4 数据恢复常识

local-path 数据在节点 `/var/lib/rancher/k3s/storage/pvc-<uid>/`（实例路径前面实测过长路径可查）。**PV 还在时**重建 Pod 即可恢复；**PV/PVC 被删（Delete 策略）**则需在节点目录里找备份——这也是强烈建议生产环境换网络存储 + 定期快照（第 08/12 章）的原因。

## 7. Rancher 界面对照

- **工作负载 → 某 Pod → Volume**：列出所有挂载（来源类型 + 挂载点），对应 `volumes/volumeMounts` 的 UI 视图
- **存储 → PVCs**：状态/容量/绑定 PV/存储类一目了然；点开可看"数据落在哪个节点"（local-path 场景）
- **存储 → StorageClasses**：`local-path` 的 provisioner/回收策略/绑定模式
- **工作负载 → 编辑（YAML）**：加 `volumes` + `volumeMounts`，或 UI 表单直接选 PVC/CM/Secret——比手写 YAML 更不易错
- **Launch kubectl**：跑 §6 全部排障命令

## 8. 小结

- **为什么需要卷**：容器文件系统一次性；Volume 是 Pod 级目录，活过容器
- **三个生命周期**：容器层（随容器）< Pod 级卷（随 Pod）< 集群级 PV（独立于 Pod）
- **六类卷**：emptyDir（临时）/ hostPath（节点）/ CM-Secret（配置）/ downwardAPI-projected（元数据+token）/ PVC（持久）——本集群统计：projected 32 最多，PVC 仅 1
- **持久化三件套**：PVC 声明 → SC 动态供给（local-path/WaitForFirstConsumer 实测）→ PV 绑定（RWO/Delete 实测）；**local-path 数据单节点 + 默认 Delete，删 PVC = 删数据**
- **挂载细节**：两步语法、subPath 单文件（不热更新）、readOnly、覆盖陷阱、RWO 多副本冲突
- **排障四层**：YAML → PVC → PV → 数据层；**describe Events 直接给答案**
- 选型一句话：**数据要持久用 PVC（生产换网络盘），临时用 emptyDir，配置用 CM/Secret，身份用 projected**

4. 排障演练（只读）：把 `kubectl -n lab get pvc nginx-data -o jsonpath='{.spec.accessModes}'`、`{.spec.storageClassName}` 输出写下来，说明"若另一个 Pod 挂载同一 PVC 并调度到 agent-1 会发生什么"。
5. 深度题：emptyDir 存在哪个节点？Pod 被 drain 驱逐后 emptyDir 的数据还在吗？local-path PVC 同理吗？为什么两者结论不同？

<details>
<summary>参考答案</summary>

1. 统计应接近 §2.0（projected 最多）。projected 的三个 sources：serviceAccountToken / configMap(kube-root-ca.crt) / downwardAPI(namespace)。
2. `/data` 可看到 PVC 内容（可能为空目录）；serviceaccount 目录有 ca.crt、namespace、token 三文件。describe PVC 的 Used By 会列出 pvc-writer。
3. path 形如 `/var/lib/rancher/k3s/storage/pvc-6172...`，节点上存在该目录——本地盘 PV 的铁证。
4. RWO + local-path：同一 PVC 只能被"选中的那个节点"挂载；若 Pod 被调度到 agent-1 而数据在 server-1，会一直 Pending（调度器等待 PVC 可用时可能把 Pod 放 server-1，或卡住）。这正是"RWO 本地盘不能多副本共享"的体现。
5. emptyDir 在 Pod 所在节点的磁盘；drain 驱逐 → Pod 在新节点重建 → 新 emptyDir，**旧数据没带走**。local-path PVC 同理数据在原节点，但 PV 对象还在（Bound），新 Pod 若调度回原节点还能续用；若原节点挂了，数据不可达——都印证"本地存储数据单节点、不迁移"（第 17 章）。差别：emptyDir 无 PV 概念，删 Pod 即毁；PVC 卷的数据由 PV 承载、删 Pod 不毁。
</details>
