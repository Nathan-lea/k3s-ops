# 01 基础概念：容器 → K8s → k3s

## 本章目标

- 理解容器与 Kubernetes（K8s）要解决的问题
- 掌握 K8s 的核心思想：声明式、期望状态、控制循环
- 明确 k3s 与 K8s 的关系
- 会用 kubectl 完成第一次集群探索（看节点、看命名空间、看 Pod）

---

## 1. 为什么需要容器

传统部署：直接跑在物理机/虚拟机上，进程之间互相干扰、资源无法隔离。
容器化：把应用连同依赖打包成镜像，用 **命名空间（namespace）+ cgroup** 隔离进程，轻量、秒级启动。

```bash
# 单机运行一个 nginx 容器（示意，下列命令在 k3s 节点 VM 内）
docker run -d -p 8080:80 nginx
```

单机没问题，但当你需要：
- 很多台机器编排
- 自动扩缩容
- 故障自愈
- 服务发现与负载均衡

容器本身做不到 —— 需要**容器编排平台**，这就是 Kubernetes。

## 2. Kubernetes 是什么

Kubernetes（希腊语"舵手"，常写作 K8s）是 Google 开源的容器编排平台。它提供：

| 能力 | 说明 |
|------|------|
| 调度 | 把 Pod 放到合适的节点运行 |
| 自愈 | 容器挂了自动重启/重建 |
| 扩缩容 | 根据负载增减副本 |
| 服务发现与负载均衡 | Service 提供稳定访问入口 |
| 滚动更新/回滚 | 平滑升级应用 |
| 声明式管理 | 描述"期望状态"，集群持续向它收敛 |

### 核心思想：声明式 + 期望状态

你告诉集群**想要什么**（例如"运行 3 个 nginx 副本"），K8s 负责**怎么做到**。

```yaml
# 期望状态：3 个 nginx 副本，镜像 nginx:1.27
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-demo
spec:
  replicas: 3
  selector:
    matchLabels: { app: nginx-demo }
  template:
    metadata:
      labels: { app: nginx-demo }
    spec:
      containers:
        - name: nginx
          image: nginx:1.27
```

集群中的控制器持续对比 **期望状态（spec）** 与 **实际状态（status）**，有差距就补齐 —— 这个循环叫 **控制循环（Control Loop）**，是 K8s 一切自动化的核心。

## 3. k3s 与 K8s 的关系

k3s 是 Rancher（现 SUSE）发布的**轻量级 CNCF 认证 K8s 发行版**，目标是"适合边缘/资源受限场景"：

| 对比 | 标准 K8s | k3s |
|------|---------|-----|
| 安装 | 组件多、复杂 | 单二进制（约 60MB） |
| etcd | 独立部署 | 嵌入（也可用外部 etcd） |
| 网络 | 可插拔 CNI | 内置 flannel（也可换） |
| 负载均衡 | 需自装 | 内置 ServiceLB（本环境已禁用） |
| Ingress | 需自装 | 内置 Traefik（本环境换成了 nginx-ingress） |
| 证书 | 需单独管理 | 内置自签 CA 自动签发 |

**结论**：`kubectl` 命令、API、资源模型与标准 K8s **完全一致**。在本环境学到的一切 100% 可用于任何 K8s 集群。这也是本项目选 k3s 的原因 —— 一套资源跑标准集群。

## 4. 名词扫盲（先混个脸熟）

| 术语 | 一句话解释 |
|------|-----------|
| **Node 节点** | 一台运行 K8s 的机器（本环境是 VM） |
| **Cluster 集群** | 一组节点的集合（本环境：server-1 + agent-1） |
| **Namespace 命名空间** | 在集群内划分资源组（隔离/组织用的文件夹） |
| **Pod** | K8s 的最小调度单元，一个或多个容器的组合 |
| **Control Plane 控制面** | 集群的"大脑"（API Server、etcd、控制器、调度器） |
| **Worker 工作节点** | 真正跑业务容器的节点（kubelet + 容器运行时） |
| **kubectl** | 与集群交互的命令行工具（"遥控器"） |

## 5. 本集群实站对照

首先让 kubectl 能连上集群（项目根目录）：

```bash
cd ~/k3s-ops                  # 项目根目录
export KUBECONFIG=./kubeconfig
```

> 如果你用 `~/k3s-ops` 或自定义路径，替换为实际路径即可。
> 也可以不 export，每次命令写 `kubectl --kubeconfig ./kubeconfig`。

### 5.1 查看版本与集群信息

```bash
kubectl version
```

预期输出（节选，客户端 1.37 > 服务端 1.30，有 minor 版本差警告属正常）：

```
Client Version: v1.37.1
Kustomize Version: v5.8.1
Server Version: v1.30.2+k3s2
Warning: version difference between client (1.37) and server (1.30)
         exceeds the supported minor version skew of +/-1
```

### 5.2 查看节点

```bash
kubectl get nodes -o wide
```

预期输出（本环境真实）：

```
NAME                STATUS   ROLES                       AGE    VERSION        INTERNAL-IP     EXTERNAL-IP   OS-IMAGE             KERNEL-VERSION       CONTAINER-RUNTIME
k3s-demo-agent-1    Ready    <none>                      123d   v1.30.2+k3s2   192.168.56.20   <none>        Ubuntu 22.04.5 LTS   5.15.0-160-generic   containerd://1.7.17-k3s1
k3s-demo-server-1   Ready    control-plane,etcd,master   130d   v1.30.2+k3s2   192.168.56.10   <none>        Ubuntu 22.04.5 LTS   5.15.0-160-generic   containerd://1.7.17-k3s1
```

要点：
- `ROLES` 列：`control-plane,etcd,master` = 控制面节点；`<none>` = 纯工作节点（agent）
- `INTERNAL-IP`：节点在集群内网（192.168.56.x）的地址
- 两个节点都是 `Ready` —— 健康

### 5.3 查看节点详情（信息量很大的一条命令）

```bash
kubectl describe node k3s-demo-server-1
```

预期输出（节选）：

```
Name:               k3s-demo-server-1
Roles:              control-plane,etcd,master
Labels:             beta.kubernetes.io/arch=amd64
                    kubernetes.io/hostname=k3s-demo-server-1
                    node-role.kubernetes.io/control-plane=true
                    node-role.kubernetes.io/etcd=true
                    ...
Annotations:        alpha.kubernetes.io/provided-node-ip: 192.168.56.10
                    flannel.alpha.coreos.com/backend-type: vxlan
                    ...
```

`describe` 是 K8s 里最常用的"诊断"命令：看标签、注解（如 flannel 网段）、资源分配、节点上的 Pod、状态事件等。遇到"为什么这样"的问题，第一反应就是 `describe`。

### 5.4 查看命名空间

```bash
kubectl get namespaces        # 或 kubectl get ns
```

预期输出（节选，本环境装了 Rancher/Fleet/cert-manager，所以比空白集群多）：

```
NAME               STATUS   AGE
cattle-system      Active   130d      # Rancher 相关
cert-manager       Active   130d
default            Active   130d      # 业务默认命名空间
ingress-nginx      Active   130d      # nginx-ingress 控制器
kube-node-lease    Active   130d      # 系统：节点心跳
kube-public        Active   130d
kube-system        Active   130d      # 系统：控制面组件在此
```

要点：`kube-system` 是 K8s 系统组件所在的命名空间，第 02 章会深入。

### 5.5 查看所有 Pod

```bash
kubectl get pods -A -o wide    # -A = 所有命名空间
```

预期输出（节选）：

```
NAMESPACE        NAME                                        READY   STATUS         IP            NODE
cert-manager     cert-manager-webhook-7f8cc9d46b-94w2h       1/1     Running        10.42.0.212   k3s-demo-server-1

kube-system      coredns-576bfc4dc7-c5j4q                    1/1     Running        10.42.0.217   k3s-demo-server-1
kube-system      local-path-provisioner-86f46b7bf7-mdnxz     1/1     Running        10.42.0.208   k3s-demo-server-1
kube-system      metrics-server-557ff575fb-khjrx             1/1     Running        10.42.0.215   k3s-demo-server-1
```

要点：`IP` 列是 Pod 的集群内网地址（10.42.0.x 属于 flannel 分配的 Pod 网段，第 04 章详述）。注意此时它们都跑在 server-1 上（小集群 server 无污点，可运行业务负载）。

## 6. Rancher 界面对照

打开 `https://192.168.56.10:30443`，用 admin 登录：

1. **集群总览**：左上角选集群（local 或你的集群名）→ **Nodes** 页 = `kubectl get nodes`，能看到两个节点及健康状态
2. **工作负载**：左侧 **Workload → Pods** = `kubectl get pods -A`（记得切命名空间下拉框）
3. **命名空间**：左侧 **Namespaces** = `kubectl get ns`
4. 右上角可查看 **集群仪表盘**（CPU/内存用量）

> 💡 对应关系：Rancher 的列表页本质就是 kubectl 查询结果的可视化。边看 UI 边敲命令，能更快建立"命令 ↔ 对象"的映射。

## 7. 小结

- 容器解决"应用打包与隔离"，K8s 解决"大规模编排"
- K8s = 声明式期望状态 + 控制循环自动收敛
- k3s 是轻量 K8s，命令/API/资源模型与标准 K8s 完全一致
- 最常用探索命令：`get nodes` / `get ns` / `get pods -A` / `describe <资源>`
