# 05 存储与配置：ConfigMap / Secret / PV / PVC

## 本章目标

- 理解配置与存储分离的思想：ConfigMap 存配置、Secret 存敏感数据、PV/PVC 存持久化数据
- 掌握 ConfigMap / Secret 的创建、查看、注入 Pod 的方式
- 理解 PV/PVC/StorageClass 三者的关系
- 在本集群（local-path 存储）跑通「PVC → Pod 挂载 → 写数据」全链路

---

## 1. 为什么需要「配置管理」资源

生产运维的基本要求：**镜像不变，配置可变**。

- 同一个镜像（如 Nginx）在不同环境（测试/生产）用不同配置 → 不能用镜像里的写死配置
- 密码、Token 等敏感信息不能明文进镜像、进 Git 仓库 → 需要 Secret
- 容器文件系统是临时的，Pod 一删数据就没了 → 需要持久化存储

K8s 用三个资源分别解决：

| 资源 | 存什么 | 是否加密 | 注入方式 |
|------|--------|---------|---------|
| **ConfigMap** | 非敏感配置（开关、URL、参数） | 否（明文 base64） | 环境变量 / 卷挂载 |
| **Secret** | 敏感数据（密码、Token、证书） | 仅 base64（非真加密，别再往里存明文要求外泄的） | 环境变量 / 卷挂载 |
| **PV / PVC** | 持久化文件数据 | 取决于后端存储 | 卷挂载 |

## 2. 核心概念拆解

### 2.1 ConfigMap（配置映射）

键值对集合，`key: value`。大小限制 1MiB。

### 2.2 Secret（机密）

和 ConfigMap 结构一样，只是数据要求 base64 编码。**注意**：base64 不是加密，任何人拿到 Secret 对象都能解码。真正的加密靠 etcd 加密或外部 KMS（生产进阶）。

### 2.3 PV / PVC / StorageClass

```text
StorageClass (local-path, 默认)          ← 存储类型模板（"我想要什么类型的存储"）
      │ 动态供应（provision）
      ▼
PV（PersistentVolume）                   ← 实际的一块存储（"已经存在的存储资源"）
      │ 绑定（claimRef）
      ▼
PVC（PersistentVolumeClaim）             ← 用户的存储申请单（"我要 1Gi 可读写"）
      │ 挂载
      ▼
Pod 里的 volumeMounts                    ← 容器实际用起来
```

一句话记忆：**PVC 是申请，PV 是货，StorageClass 是供应商（自动备货）**。

两阶段绑定（本集群 local-path 是 `WaitForFirstConsumer`）：
1. 创建 PVC 后**先 Pending**（供应商还没备货）
2. Pod 第一次使用该 PVC 时，local-path-provisioner 在节点磁盘上真正创建目录 → PV 变成 Bound

## 3. 本集群实站对照

### 3.1 创建 ConfigMap 并查看

```bash
kubectl -n lab create configmap app-config \
  --from-literal=app.name=nginx-demo \
  --from-literal=app.env=test \
  --from-literal=app.port=80
```

预期输出：

```text
configmap/app-config created
```

```bash
kubectl -n lab get cm app-config
```

```text
NAME         DATA   AGE
app-config   3      1s      ← 3 个键值对
```

```bash
kubectl -n lab describe cm app-config
```

```text
Data
====
app.env:
----
test

app.name:
----
nginx-demo
```

### 3.2 创建 Secret 并查看（注意 base64）

```bash
kubectl -n lab create secret generic app-secret \
  --from-literal=username=admin \
  --from-literal=password=s3cret
```

预期输出：

```text
secret/app-secret created
```

```bash
kubectl -n lab get secret app-secret
```

```text
NAME         TYPE     DATA   AGE
app-secret   Opaque   2      0s
```

```bash
kubectl -n lab get secret app-secret -o jsonpath='{.data}'
```

预期输出（值都是 base64，`admin` → `YWRtaW4=`，`s3cret` → `czNjcmV0`）：

```text
{"password":"czNjcmV0","username":"YWRtaW4="}
```

解码验证（教学演示，生产别这么玩）：

```bash
echo "YWRtaW4=" | base64 -d    # 输出 admin
```

### 3.3 把 ConfigMap / Secret 注入 Pod

两种方式：环境变量（`envFrom`）或卷挂载（`volumes`）。数据更新时：环境变量方式**不会自动更新**（Pod 重启才生效），卷挂载方式**会自动同步**（文件更新）。生产推荐卷挂载。

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: config-demo
  namespace: lab
spec:
  nodeSelector:
    kubernetes.io/hostname: k3s-demo-server-1
  containers:
    - name: app
      image: nginx:latest
      imagePullPolicy: IfNotPresent
      envFrom:                            # 整个 ConfigMap/Secret 注入为环境变量
        - configMapRef: { name: app-config }
        - secretRef:    { name: app-secret }
      volumeMounts:
        - name: cfg
          mountPath: /etc/app/config
  volumes:
    - name: cfg
      configMap:
        name: app-config
```

进容器验证：

```bash
kubectl -n lab exec config-demo -- env | grep -E 'app_|username|password'
kubectl -n lab exec config-demo -- ls /etc/app/config && cat /etc/app/config/app.name
```

### 3.4 创建 PVC（体会 WaitForFirstConsumer）

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: nginx-data
  namespace: lab
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 1Gi
```

```bash
kubectl apply -f pvc.yaml
kubectl -n lab get pvc
```

**刚创建时（还没被 Pod 使用）——注意状态是 Pending，且全集群还没有 PV：**

```text
NAME         STATUS    VOLUME   CAPACITY   ACCESS MODES   STORAGECLASS   AGE
nginx-data   Pending                                      local-path     6s
```

```bash
kubectl get pv
```

```text
No resources found
```

查看 StorageClass 的绑定模式，解释为什么 Pending：

```bash
kubectl get storageclass
```

```text
NAME                   PROVISIONER             RECLAIMPOLICY   VOLUMEBINDINGMODE      ALLOWVOLUMEEXPANSION   AGE
local-path (default)   rancher.io/local-path   Delete          WaitForFirstConsumer   false                  130d
```

`WaitForFirstConsumer` = 等第一个消费者（Pod）出现才真正分配存储。

### 3.5 Pod 首次使用 PVC → 自动绑定

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: pvc-writer
  namespace: lab
spec:
  nodeSelector:
    kubernetes.io/hostname: k3s-demo-server-1
  containers:
    - name: writer
      image: nginx:latest
      imagePullPolicy: IfNotPresent
      command: ["/bin/sh", "-c", "echo 'hello pvc' > /data/test.txt && sleep 3600"]
      volumeMounts:
        - name: data
          mountPath: /data
  volumes:
    - name: data
      persistentVolumeClaim:
        claimName: nginx-data
```

```bash
kubectl apply -f pvc-pod.yaml
```

随后 PVC 变为 Bound，并自动出现对应 PV：

```bash
kubectl -n lab get pvc
```

```text
NAME         STATUS   VOLUME                                     CAPACITY   ACCESS MODES   STORAGECLASS   AGE
nginx-data   Bound    pvc-61720575-6d78-4437-8d50-553a7b4c8fc8   1Gi        RWO            local-path     78s
```

```bash
kubectl get pv
```

```text
NAME                                       CAPACITY   ACCESS MODES   RECLAIM POLICY   STATUS   CLAIM            STORAGECLASS   AGE
pvc-61720575-6d78-4437-8d50-553a7b4c8fc8   1Gi        RWO            Delete           Bound    lab/nginx-data   local-path     4s
```

PV 命名 = `pvc-<UUID>`，`CLAIM` 列指向 `lab/nginx-data`。`RECLAIM POLICY: Delete` = PVC 删除时 PV 和底层数据一并删除（这是 local-path 的默认行为，重要数据要注意备份！）。

验证数据真的写进去了：

```bash
kubectl -n lab exec pvc-writer -- cat /data/test.txt
```

预期输出：`hello pvc`

**数据持久化验证（重点实验）**：删掉 Pod 再重建，文件还在吗？

```bash
kubectl -n lab delete pod pvc-writer
kubectl apply -f pvc-pod.yaml     # 重建（内容改一下 command，比如 cat /data/test.txt）
kubectl -n lab logs pvc-writer    # 应能读到之前写入的 hello pvc
```

## 4. Rancher 界面对照

Rancher → 集群 → **Storage → ConfigMaps** / **Storage → Secrets**：图形化创建与查看。

- ConfigMap 页能看到所有 key/value（Secret 页默认显示「隐藏值」，有显示开关）
- **Storage → PersistentVolumeClaims**：能看到 PVC 状态（Pending/Bound），点进详情可看关联 PV
- **Storage → Storage Classes**：local-path

## 5. 小结

- 镜像不变、配置可变：ConfigMap（明文）/ Secret（base64）
- 数据要持久：PV 是存储资源、PVC 是申请单、StorageClass 按需自动备货
- `WaitForFirstConsumer`：PVC 直到被 Pod 使用才真正绑 PV
- local-path 的 PV 是节点本地目录，`Delete` 回收策略 = 删除即销毁
