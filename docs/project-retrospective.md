## 2. 项目全景

### 2.1 一句话定位

> 把"一台笔记本上的 k3s 集群"从**手工敲命令**变成**可复现、可交付、可自证**的工程产物，
> 并把它写成一套 45 章的教程。

这个定位里藏着一个关键判断：项目的**真正产品不是集群，而是"可复现性"**。
集群随时可以重建，可复现性一旦丢掉，所有工作都变成一次性表演。

### 2.2 四个交付层

项目不是一个东西，而是四层互相支撑的产物：

```
┌──────────────────────────────────────────────────────────────┐
│ 第 4 层  平台支撑                                             │
│   隐私检查门禁 · 测试桩 · 代码/安全审查 · 文档质量校验          │
├──────────────────────────────────────────────────────────────┤
│ 第 3 层  教程（45 章 / 20,730 行）                            │
│   概念 → 清单 → 实测输出 → 练习 → 参考答案                     │
├──────────────────────────────────────────────────────────────┤
│ 第 2 层  production/（69 文件）                               │
│   裸机 → 一键 k3s：预检/初始化/安装/附加组件/扩缩容/升级/备份   │
├──────────────────────────────────────────────────────────────┤
│ 第 1 层  本地开发集群（Vagrant + Ansible + k3s）               │
│   k3s-ops.sh 15 个子命令 · 4 个 Ansible 角色 · 11 个 playbook  │
└──────────────────────────────────────────────────────────────┘
```

| 层 | 产物 | 受众 | 完成度 |
|---|---|---|---|
| 1 本地集群 | `k3s-ops.sh` + `vagrant/nodes.yml` + `ansible/` | 自己、学习者 | 可用，日常在用 |
| 2 生产方案 | `production/` 自带 `roles/` `lib/` `playbooks/` | 公司测试 / 生产 | 静态校验通过，**未真机验证**（已明示） |
| 3 教程 | `docs/k8s-tutorial/` 00–45 | 学员 | 45 章齐全，含实测输出 |
| 4 平台支撑 | `scripts/privacy-check.sh`、`tests/`、审查报告 | 维护者 | 每次 push 自动生效 |

**为什么分层很重要**：分层的直接好处是"第 2 层可以整体搬走"。
`production/` 最终做到了**物理独立**（自带 roles、lib、playbooks，对父仓库引用清零，
提交 `80588be`），因此它可以被单独复制到一台没有本项目历史的机器上使用。
如果四层搅在一起，这件事做不到。

## 3. 演进史：六个阶段

### 3.1 P0 打地基（W36，5 提交）

**目标**：让 `./k3s-ops.sh up && ./k3s-ops.sh install` 能跑通。

**关键动作**：

1. Vagrant 读取 `vagrant/nodes.yml` 动态建 VM，Ansible 用 4 个角色分层
   （`k3s-common` / `k3s-server` / `k3s-agent` / `k3s-manage`）；
2. **第二个提交就是隐私钩子**（`5c95d0d`）。这个顺序很关键：门禁在第一天装上，
   而不是等出了事再补；
3. 引入 MIT 许可证，删掉本地中间备份文档（`1944c73`）——
   从一开始就明确"仓库只放该放的东西"。

**产出**：可用的本地集群 CLI（`init/up/down/install/add-node/remove-node/upgrade/backup/restore/status/destroy/ssh/kubeconfig`）。

**转折**：项目从"我的脚本"变成"有门禁的仓库"。

### 3.2 P1 教程起步（W40，4 提交）

**目标**：把踩过的坑沉淀成教程。

**关键动作**：一次写 11 章（第 11–17 章），随后立刻修隐私检查的**中文文件名漏检**。

> 那个 bug 很典型：`git ls-files` 默认对非 ASCII 文件名输出八进制转义，
> 导致 `[ -f "$f" ]` 判断失败、整个文件被**静默跳过**。
> 修法是一行 `core.quotepath=false`，但发现它需要"怀疑门禁本身"的意识——
> **门禁自己也要被审计**（详见第 9 章）。

**产出**：教程从 10 章扩到 17 章。

### 3.3 P2 教程主体（W41，21 提交）

**目标**：把"能用"讲成"能懂"。

**关键动作**：

1. 第 18–29 章：Annotation、服务发现、存储卷、四/七层转发、eBPF、CNI、
   Helm、Kustomize、GitOps（ArgoCD/Fleet）与私有仓库认证；
2. `c6886c1`：新增 `down` 子命令**并修复 7 个既有缺陷**——
   把"加功能"和"还技术债"放在同一个提交里，因为它们同源（都是 CLI 参数解析问题）；
3. `3232e0c`：架构文档新增 2.5 节"宿主机与 VM 网络路径"（NAT / Host-only）——
   这是给"为什么 VM 里连不上宿主机 Gitea"这个高频问题写的**永久答案**。

**方法论收获**：**同一个根因的改动要合并提交，不同根因的改动要分开提交**。
按"根因"而不是按"文件"组织提交，历史才可读。

### 3.4 P3 重流程试点（W42，39 提交）

**目标**：证明"重流程"值得。

**关键动作**：第 42 章（CRD 与 Operator）与第 43 章（Kyverno）走完整 SDD 流程：
设计 → 计划 → 11 个任务 brief → 逐任务门禁 → 独立评审 → 逐条裁决。
台账留在 `.superpowers/sdd/2026-10-14-k8s-tutorial-ch42-ch43/`。

**为什么这两章要重流程**（对照 AGENTS.md 的 5 条触发条件）：

| 条件 | 是否命中 | 说明 |
|---|---|---|
| 1. 手写并跑通代码/构建产物 | ✅ | 自研 Go Operator + scratch 镜像 |
| 2. 引入可能"拦死集群"的准入组件 | ✅ | Kyverno `failurePolicy=Fail` |
| 3. 破坏性 / 集群级 / 不可逆 | ✅ | 准入 webhook，配错即全集群写入失败 |
| 4. 输出强非确定且需多处一致 | 🔶 | 实测输出会随版本变，需标注 |
| 5. 用户显式要求独立评审 | ✅ | 用户要求 |

**收益是真实的**：评审抓出了 5 个 I 级问题，其中 2 个是"文档说反了"级别：

- **I4**：原文以为 `kinds: [Pod]` 的策略不会影响 Deployment，实测经 autogen 会拦。
- **I5**：原文建议 `nginx:1.27` + `runAsUser: 101` 兜底，实测直接
  `mkdir() "/var/cache/nginx/client_temp" failed (13: Permission denied)` 退出。
  **这条建议如果留着，学员会照着做然后卡死。**

这正是重流程的价值：**不是让流程好看，是让错误在发布前死掉**。

### 3.5 P4 生产化（W43，21 提交）

**目标**：从"演示"走向"能交付给公司"。

**关键动作**：

1. `docs/k3s-tutorial/44`：Service 暴露与 LoadBalancer，明确 **k3s ServiceLB 必须关闭**，

## 4. 方法论：八条主线

### 4.1 分层交付：先能跑，再能复现，再能交付，最后能自证

四级台阶，每一级都有明确的"毕业标准"：

| 级别 | 毕业标准 | 本项目对应 |
|---|---|---|
| 能跑 | 一条命令起集群 | `k3s-ops.sh up && install` |
| 能复现 | 换台机器照文档做，结果一致 | 教程每章含实测输出与清单文件 |
| 能交付 | 别人敢拿去用在非演示环境 | `production/` 一键 bootstrap + 约束清单 |
| 能自证 | 不需要人盯着，机器自己证明 | 隐私门禁 + 测试桩 + selftest |

**绝大多数项目死在"能跑"就停手**。判断自己在哪一级的方法很简单：
问"如果明天换一台干净机器，需要几个人、多少口头知识才能重建？"
答案里"口头知识"越多，级别越低。

### 4.2 约束编号法

`production/design.md` §2 把用户说的话逐条编号成 **21 条约束**，后续每一节都标注
"本条实现对应约束 8/11/12"。例：

```
## 11. k3s 安装（20-k3s-cluster.yml，约束 8/11/12）
```

**为什么有效**：

1. **防丢失**：用户随口一句"防火墙用 ufw"，不编号就会在实现时蒸发；
2. **防曲解**：编号后可以逐条对照"我是这么理解的，对吗"；
3. **防范围蔓延**：不在编号里的需求，默认不做；要做就新增编号并说明来源；
4. **可审计**：实现完成时，用脚本核对"21 条约束是否都有落点"。

**操作要点**：

- 编号只增不改。约束变了，新增一条并注明"取代第 N 条"，保留历史；
- 每条约束必须**可验证**（能写出一条检查命令或一段断言）；
- 约束原文**照录**，包括错别字（见 `design-history.md` §1）——
  改写原文等于篡改需求证据。

### 4.3 契约先行 / 单一事实源

项目里所有"两边都要知道"的东西，都收敛到一个文件、一个函数：

| 契约 | 唯一来源 | 被谁消费 |
|---|---|---|
| 节点拓扑（名字/角色/IP/规格） | `vagrant/nodes.yml`；production 用 `config/ipam.yml` | Vagrant、Ansible、CLI、inventory 生成器 |
| 集群参数（版本、存储、Ingress） | `production/config/cluster.env` | 全部 playbook |
| 节点名解析规则 | `lib/nodes.sh` 的 `resolve_host` | 所有接受节点名的命令 |
| 集群名前缀 | `nodes.yml` 的 `cluster_name` | 主机名、kubeconfig、日志 |

**硬规则**：新增一个接受节点名的命令，**必须复用** `resolve_host`，
不许自己拼 `"k3s-demo-" + name`。这条规则写进了 AGENTS.md，
因为违反它的代价是"某个命令在改名后静默失效"。

### 4.4 证据驱动

三种证据，各有用途：

| 证据类型 | 用途 | 本项目的做法 |
|---|---|---|
| **真实输出** | 证明"确实跑过" | 教程每段命令后贴真实 `kubectl` 输出 |
| **静态校验** | 证明"结构正确" | `bash -n` / `shellcheck` / `python -m py_compile` / 清单 `kubectl apply --dry-run=client` |
| **诚实标注** | 证明"我知道边界" | "未真机验证"、"会变"、"截断说明" |

**"会变"标注法**：非确定性输出（Pod 名、IP、时间戳）给**一次真实样例**，
并明确写"你自己的环境会不同"。这比伪造一个稳定输出诚实得多，也比含糊其辞有用得多。

**诚实边界的写法**（来自 `production/design.md` §15）：

> 本轮**不做真机验证**。已完成的是：设计、实现、静态校验、自测脚本。
> 未完成的是：在真实裸机上的端到端运行。

这段话的价值在于：**它让读者能正确评估风险**。如果省略它，读者会以为这是"已验证方案"，
出事时的信任损失远大于当初承认的尴尬。

### 4.5 流程分级：轻量是默认，重流程要"中签"

这是本项目最重要的**元规则**，写在 AGENTS.md 里：

**默认轻量**：不做 brainstorming / 设计文档 / writing-plans / 子代理评审；
直接写、小步提交（一章一个提交）；采集一次到位；提交信息用 Conventional Commits；不主动 push。

**只有命中以下任一条才升级为重流程**：

1. 需要**手写并跑通代码/构建产物**；
2. 引入**有副作用、可能"拦死集群"的新准入/控制面组件**；
3. 涉及**破坏性 / 集群级 / 不可逆操作**；
4. 输出**强非确定且必须多处一致**；
5. 用户**显式要求**独立评审。

**为什么这条规则值钱**：没有它，要么每章都走重流程（45 章会做到明年），
要么永远不走（42/43 章的 5 个 I 级错误就会进正文）。
**流程的成本必须和风险匹配**，而不是和"仪式感"匹配。

### 4.6 小步提交与语义化提交

- **一章一个提交**：教程章节粒度天然清晰，回滚成本低；
- **同一根因合并、不同根因分开**：`down` 子命令 + 7 个缺陷修复放一起，因为同源；
- **revert 是荣誉而非耻辱**：`9d484fc` 撤销越界改动，是流程生效的证据；
- **提交信息写"为什么"**：`fix(registry): registry.k8s.io/quay.io 加速换 DaoCloud（1panel 不代理非 docker.io）`
  ——括号里那句话，半年后能省一次排查。

### 4.7 先复用，再新建，最后物理剥离

`production/` 的演进是三段式的：

```
① 复用        直接用父仓库的 roles/lib          → 快，但耦合
② 参数化      给父仓库角色加开关（use_ufw / registry auth）
                                                 → 灵活，但污染公共资产
③ 物理剥离    自带 roles/lib/playbooks，引用清零 → 独立，但成本高
```

**关键判断**：第 ② 步产生的 5 处父仓库改动，最终**全部 revert**（`9d484fc`）。
理由：父仓库服务的是"本地演示集群"，production 服务的是"客户裸机"，
两者的默认值会持续分叉。**共用一套角色，最终会变成两套都不好用**。

**教训**：复用是**起点**不是**终点**。当两个消费者的默认值开始打架时，
剥离比参数化便宜——参数化只是把分叉藏进了 `if`。

### 4.8 自我审计

项目做了两轮系统性自审：

| 审计 | 范围 | 产出 |
|---|---|---|
| 可复现性审计 | 全教程 45 章 | 补齐 10 个缺失清单文件；统一"清单 + 内联头"格式 |
| 文档-实现对照 | `production/design.md` vs 实际文件 | 发现并修正设计文档与实现的偏差 |
| 门禁自审 | `privacy-check.sh` | 修复中文文件名漏检、路径误报、go.sum 手机号误报 |

**审计的触发条件**（值得抄）：

- 文档超过 30 章 / 实现超过 5 个 playbook；
- 有"照着做但失败"的反馈；
- 有人问"这个值到底以哪个文件为准"——**这个问题一出现，说明有契约分叉**。

## 5. 工程原则：十二条

每条按"原则 → 为什么 → 怎么落地 → 反例"四段写。

### 5.1 单一事实源

**原则**：同一个事实只允许有一个权威位置。

**为什么**：重复的事实必然分叉，分叉必然导致"改了 A 没改 B"。

**落地**：`nodes.yml` / `cluster.env` / `ipam.yml` / `resolve_host` / `cluster_name`。

**反例**：曾经有命令自己拼主机名前缀，集群改名后该命令静默指向不存在的节点。
现在这类代码一律拒绝合并。

### 5.2 幂等优先

**原则**：同一个操作跑两遍，结果和跑一遍相同。

**为什么**：运维脚本一定会被重复执行（重试、补跑、出错重来）。

**落地**：Ansible 任务用 `creates:` / `state:` 而不是裸 `command`；
`bootstrap.sh` 分阶段可重入；`scale.sh add` 对已存在节点报错而不是重复加。

**反例**：用 `shell: k3s server ...` 直接启动，第二次执行会因端口占用失败，
且留下半启动状态。

### 5.3 失败要显式（fail fast）

**原则**：能提前 5 秒发现的错误，不要等到 5 分钟后。

**为什么**：分布式/集群类操作，越晚失败，残留状态越多，清理成本越高。

**落地**：`bootstrap.sh` 开跑前校验"ipam 里至少一台 `role: server`"；
`scale.sh remove` 拒绝删除最后一台 server；`K3S_VERSION` 格式不合法直接退出。

**反例**：先装 10 台机器，最后发现配置少了一个字段，全部重来。

### 5.4 只读优先

**原则**：能不写就不写；必须写时，先想"写坏了怎么恢复"。

**为什么**：这是数据事故的第一道防线（见第 10 章）。

**落地**：`--dry-run` 模式覆盖所有破坏性命令；`privacy-check.sh` 只读；
诊断脚本只读；`status` 不修改集群。

**反例**：出问题时第一反应是 `fsck -y` 或 `kubectl delete --all`。

### 5.5 不静默降级

**原则**：降级必须留痕。

**为什么**：静默降级会把"功能失效"伪装成"功能正常"，是最贵的 bug。

**落地**：`health-check.sh` 在 `/var/log` 不可写时降级到 `$TMPDIR`，**并在输出里说明**；
`install` 匹配不到主机时的问题（见 12.2）之所以危险，正是因为它是**空跑**。

**反例**：`|| true` 吞掉所有错误，脚本"成功退出"，实际什么都没做。

### 5.6 诚实边界

**原则**：没验证的就写"没验证"，不确定的就写"不确定"。

**为什么**：项目的可信度 = 说对的比例 × 敢承认不知道的比例。

**落地**：`production/design.md` §15 明示"未真机验证"；
教程标注"会变"；评审台账记录"存疑，待联网核实"。

**反例**：把估算值（"镜像约 20–30 MB"）写进文档，实测 39.8 MB。
台账里如实记为"计划估算偏乐观"，并统一改用实测值。

### 5.7 白名单只做精确豁免

**原则**：白名单是"我知道这个值是安全的"，不是"别管这类问题"。

**为什么**：一个 `grep -v` 式的粗白名单会让整类泄漏合法化。

**落地**：`ALLOW_IPS` 逐值列出；`ALLOW_PATH_PATTERNS` 限定具体路径；
新增用例时**同时**维护白名单与注释说明理由。

**反例**：为了让检查通过而写 `--exclude-dir=docs`，
等于宣布"docs 目录里的泄漏不算泄漏"。

### 5.8 文档即产品

**原则**：文档不是代码的副产品，它本身就是交付物。

**为什么**：66% 的提交是 `docs`，这不是浪费——**用户买的就是文档**。

**落地**：每章含"概念 → 清单 → 实测输出 → 练习 → 答案"；
文档变更与代码变更同批提交；`docs/architecture.md` 在架构改动时同步更新。

**反例**：README 写"支持扩容"，但脚本参数已经改名三个月。

### 5.9 破坏性操作必须有逃生路径

**原则**：任何可能"拦死系统"的组件，必须预先写好两步能拆掉它。

**为什么**：准入 webhook 配错 = 全集群写入失败，包括"删掉 webhook"这个操作本身。

**落地**（Kyverno 实例，顺序不可反）：

1. `kubectl -n kyverno scale deploy --all --replicas=0`（先让控制器停手）
2. `kubectl delete validatingwebhookconfiguration,mutatingwebhookconfiguration -l webhook.kyverno.io/managed-by=kyverno`

**反例**：直接删 webhook 配置，控制器还活着会立刻重建，形成拉锯。

### 5.10 演示环境与生产环境不混

**原则**：两套环境的默认值必须能独立演进。

**为什么**：演示要"开箱即用"，生产要"默认安全"，两者的默认值天然冲突。

**落地**：`production/` 物理独立；演示用 `admin` 密码进白名单，
生产用 `cluster.env.local`（gitignore）承载真实凭据。

**反例**：为了让演示方便，把 `disable_servicelb: false` 写进公共默认值，
结果生产环境的 `svclb` 抢了 `30080`。

### 5.11 先复用再剥离

见 4.7。

### 5.12 恢复能力比预防便宜？不，反过来

**原则**：**预防比恢复便宜一百倍**，恢复能力是兜底不是方案。

**为什么**：这次事故里唯一救不回来的风险最大的那份文档，正是**从未 `git add` 过**的。

**落地**：重要文件进 git（哪怕本地仓库）；`rm` 用 `trash-cli`；
关键目录定时快照；3-2-1 备份。

**反例**：相信"我记性好，不会删错"。删除命令不区分"重要"和"临时"。

## 6. 标准作业流程（SOP）

### 6.1 新功能 SOP（重流程，7 步）

```
① 需求原文照录       不改写、不改错别字
        ↓
② 约束编号           每条可验证，只增不改
        ↓
③ 设计文档           目标/非目标/反目标 + 约束映射
        ↓
④ 独立评审           设计评审，列出 Critical/Major/Minor
        ↓
⑤ 计划拆任务         每任务有 Produces/Consumes/验收命令
        ↓
⑥ 实现 + 逐任务门禁  每任务收口跑一次可用门禁
        ↓
⑦ 对照 + 归档        设计 vs 实现偏差写进文档
```

**第 ⑤ 步的关键细节**：每个任务必须写清"我产出什么、下一个任务消费什么"。
SDD 台账的 Pre-flight scan 就是干这个的，例如：

```
Task2 consumes Task1 `api/v1`（GroupVersion/AddToScheme/WebApp/WebAppStatus）⊂ Task1 Produces。一致。
Task3 produces 镜像 tag `webapp-operator:v0.1.0`；Task2 的 deployment.yaml 消费同一 tag。一致。
```

这一步能在写代码前发现"任务 2 等的东西任务 1 根本没做"。

### 6.2 教程章节 SOP（轻量，5 步）

默认节奏，**不做**设计文档与独立评审：

1. **一次采集**：把这一章要用的命令**一次性**在真集群跑完，
   输出重定向到文件（不用 `/tmp`，避免重启丢失）；
2. **一次成文**：概念 → 清单 → 命令 → 实测输出 → 坑 → 练习 → 答案；
3. **自查**：围栏偶数、表格列数一致、锚点有效、首末行完整；
4. **补导航**：`00-README.md` 三处（目录、学习路径图、统计）同步；
5. **一个提交**，不 push。

**"采集一次到位"的含义**：不要边写边跑边补——
那会产生"命令和输出对不上"的经典错误（`2b38028` 修的就是这个）。

### 6.3 重流程章节 SOP（以 42/43 章为例）

11 个任务，台账结构：

```
.superpowers/sdd/2026-10-14-k8s-tutorial-ch42-ch43/
├── plan-path                 指向计划文件
├── progress.md               台账：Setup / Pre-flight / 每任务完成记录 / Rulings
├── task-1-brief.md … task-11-brief.md    任务说明书
└── task-N-tests.log          每个任务的门禁日志
```

`progress.md` 里最有价值的是 **Rulings**（裁决）：
每一处"计划与现实不符"都记录"现象 / 处置 / cost if wrong"。

三个真实裁决，示范了三种类型：

| 类型 | 实例 | 处置 |
|---|---|---|
| 计划估算偏差 | 镜像"预计 20–30 MB"，实测 58.7 MB，裁剪后 39.8 MB | 改文档用实测值，不引用估算 |
| 计划遗漏 | 规格没写 `USER`，但 Deployment 设了 `runAsNonRoot: true` | Dockerfile 补 `USER 65532:65532` |
| 环境事实 | 在 `vagrant/` 下执行 `vagrant status` 显示 VM 未创建，但 `VBoxManage` 显示在跑 | 记录"必须在仓库根执行"，不改代码 |

**"cost if wrong" 这个字段值得单独学**：它强迫你在决策时估算错误代价。
代价低的决策可以快，代价高的必须验证。

### 6.4 环境重建 SOP

```bash
./k3s-ops.sh destroy          # 彻底销毁
./k3s-ops.sh init             # 检查依赖
./k3s-ops.sh up               # 起 VM（Vagrant 会自动跑 provision）
./k3s-ops.sh install          # 装 k3s
./k3s-ops.sh deploy-ingress   # 可选
./k3s-ops.sh deploy-rancher   # 可选
./k3s-ops.sh kubeconfig       # 拉 kubeconfig 到仓库根
./k3s-ops.sh status           # 健康检查
```

**注意**：`install` 走 `ansible/inventory.yml`（占位空清单），
真正把 `nodes.yml` 下发到节点的是 **Vagrant 的 ansible provisioner**。
所以改完 `nodes.yml` 必须 `vagrant up` / `vagrant provision`，光跑 `install` 是空跑。
（这个坑已记入 12.2。）

### 6.5 发布前门禁 SOP

```bash
# 1. 结构校验
bash -n scripts/*.sh && shellcheck scripts/*.sh
python3 -m py_compile scripts/gen-inventory.py

# 2. 测试桩
bash tests/run-all.sh

# 3. 隐私检查（推送前钩子会自动跑，也可手动）
bash scripts/privacy-check.sh

# 4. production 自测
bash production/scripts/selftest.sh

# 5. 文档校验（围栏/表格/锚点）
#    见 8.4 的检查脚本
```

### 6.6 事故响应 SOP

```
① 停止写入（remount,ro / 停服务）
② lsof +L1                    找"还被打开的"免费午餐
③ 记录现场（lsblk -f / df -hT / blockdev --getsize64）
④ 只读试一次元数据路线         extundelete / debugfs lsdel
⑤ 裸盘 carve                  carve-scan → 聚类 → 挖窗口 → 定边界 → 解码 → 校验
⑥ 先写到别处，校验通过再写回    绝不覆盖唯一副本
```

完整技术细节见仓库根目录的《数据恢复实战手册》（本地文档，不入 git）。

### 7.2 四个关键技能的作用机制

**（1）brainstorming —— 把"我想做"变成"要做什么"**

42/43 章开工前先出 spec，而不是直接写。收获：

- "Kyverno 控制器全在唯一 agent 上"这个**单点风险**，是设计阶段被问出来的；
- 由此才有"两步逃生"（scale 到 0 → 删 webhook）写进章节。

**如果跳过这一步**，章节会写成"如何安装 Kyverno"，而漏掉"装完之后你怎么活下来"。

**（2）writing-plans —— 任务边界与依赖检查**

计划里每个任务写 `Produces` / `Consumes`。
Pre-flight scan 逐条核对"消费的东西是否真的被生产"，在**写代码前**发现缺口。

**（3）subagent-driven-development —— 隔离与可追溯**

每个任务一个 brief、一份门禁日志。好处：

- 上下文隔离：任务 3 不需要知道任务 1 的全部细节；
- 可追溯：出问题能定位到"哪份 brief 说错了"；
- 可恢复：会话中断后，看台账就知道做到哪了。

**（4）requesting / receiving code review —— 双向纪律**

- 请求评审时给**可验证的断言**（命令 + 期望输出），而不是"帮我看看"；
- 接收评审时逐条裁决，**包括拒绝**。

台账里的处置很有代表性：

> **Minor（M7–M16）：不改**，整理成清单交用户决定（避免范围蔓延）。

**"不改"也需要理由**。否则评审会变成需求扩容器。

### 7.3 子代理与角色分工

| 角色 | 职责 | 产出物 |
|---|---|---|
| `design-agent` | 出设计文档 | spec / design |
| `design-reviewer` | 设计评审 | Critical/Major/Minor 清单 |
| `task-planner` | 拆任务 | 带 Produces/Consumes 的计划 |
| `code-reviewer-agent` | 代码/文档评审 | 分级问题清单 |
| `explore` | 快速定位代码 | 文件/符号位置 |
| `pr-manager` | 提交推送建 PR | 提交 + PR（本项目未用，推送为手工） |

**经验**：子代理适合"边界清晰、可独立验收"的任务；
不适合"需要全局上下文才能判断"的任务（比如"这段措辞是否准确"）。

| 虚拟化 | VirtualBox ≥ 7.0 + Vagrant | VM 生命周期 |
| 配置管理 | Ansible ≥ 2.15 | 幂等配置下发 |
| 集群 | k3s（嵌入式 etcd） | 轻量 K8s |
| 包管理 | Helm 3 | 附加组件 |
| 客户端 | kubectl | 验证与断言 |
| 代码 | Go（Operator 示例） | 第 42 章产物 |
| 脚本 | bash / Python 3 | CLI、inventory、carve |
| 质量 | shellcheck / `py_compile` / `bash -n` | 静态校验 |
| 私有仓库 | Gitea | 推送目标（`localhost`） |
| 镜像加速 | 1panel（仅 docker.io）/ DaoCloud（k8s、quay） | 受限网络拉取 |
| 恢复 | `dd` / `grep -abo` / Python | 裸盘 carve（第 10 章） |

### 7.5 技能使用的经验

**什么时候不该用技能**：

1. **任务比技能便宜时**。改一个错别字走 brainstorming 是浪费。
2. **技能会引入不存在的严格性时**。文档项目的"测试"不是单测，
   强行套 TDD 会产出一堆测 Markdown 字符串的无用测试。
   ——正确做法是**改造**（把"真实输出 vs Expected"当测试）并在台账里写明裁决理由。
3. **顺序依赖强的任务**。并行子代理在这里只会制造合并冲突。

**判断标准**：技能应该**降低**总成本。如果它让你花更多时间解释"为什么没用它"，
那就是用错了。

## 8. 质量保障体系

### 8.1 三层门禁

```
提交时    ┌─ 人工：一个章节一个提交，信息写"为什么"
          └─ 自动：无（有意为之，避免提交变慢）

推送时    ┌─ pre-push 钩子 → scripts/privacy-check.sh（8 条规则，222 文件，约 2 秒）
          └─ 失败即阻断，输出逐条问题

变更后    ┌─ tests/run-all.sh（stub，不依赖真集群）
          ├─ production/scripts/selftest.sh（正反例）
          ├─ 静态校验（shellcheck / py_compile / bash -n）
          └─ 文档校验（围栏 / 表格 / 锚点 / U+FFFD）
```

**为什么提交时不跑全套**：提交要快。**门禁的位置应该匹配"错误的代价"**——
隐私泄漏一旦推送就来不及，所以卡在 push；语法错误本地就能改，没必要卡。

### 8.2 测试策略

**stub-based harness**（`tests/`）：

```
tests/
├── run-all.sh              跑全部
├── lib/harness.sh          断言库（199 行）
├── stubs/ansible-playbook  记录调用参数，不真执行
├── stubs/kubectl
├── stubs/vagrant
├── test-gen-inventory.sh   inventory 生成正确性
├── test-node-names.sh      短名 ↔ 完整主机名
└── test-vbox-archive.sh    VM 日志归档与保留 20 个
```

**核心思想**：把"外部命令"换成记录器，就能在不启动任何 VM 的情况下
验证"脚本有没有按预期调用工具"。这让回归测试从"半小时"变成"两秒"。

**真机断言**（教程用）：

```bash
kubectl --kubeconfig ./kubeconfig wait --for=condition=Established \
  crd/webapps.demo.example.com --timeout=30s
```

**两类测试的分工**：stub 测"逻辑对不对"，真机测"事实对不对"。
只有前者会漏掉"命令写对了但 API 已改"；只有后者会慢到没人跑。

### 8.3 评审机制

`docs/code-review.md` 与 `docs/security-review.md` 采用统一分级：

| 级别 | 含义 | 处置 |
|---|---|---|
| Critical | 会导致数据损坏/安全问题 | 必须修，不修不合并 |
| Major | 功能错误或明显风险 | 应修 |
| Minor | 措辞、可维护性 | 可选，汇总交用户 |
| Positive | 值得肯定的设计 | 保留，避免"只挑刺" |
| Questions | 向作者确认 | 澄清后转成问题或约束 |

**"Positive" 这一节很重要**：它防止评审变成"找茬游戏"，
也让"哪些做法应该保留"变成显式知识。

**评审后的裁决纪律**（来自台账）：

- 属实 → 修；
- 属实但危险 → 修，并把**实测报错**写进正文（教训比结论值钱）；
- 存疑 → 标记"待核实"，联网验证后再定，**不猜**；
- 范围外 → 不改，列清单交用户。

### 8.4 文档质量校验

Markdown 的坑比代码多，因为"看起来对"不等于"渲染对"。固定检查项：

| 检查 | 判据 | 本次发现 |
|---|---|---|
| 代码围栏配对 | 三个反引号出现次数为**偶数** | 发现 1 处奇数（表格里写了围栏） |
| 表格列数 | 每张表所有行的竖线数量一致 | 发现 2 处（行内代码含竖线） |
| 内部锚点 | 所有以 `#锚点` 结尾的链接都能对上标题 slug | 全部有效 |
| 标题层级 | 不跳级（H2 → H4） | 必须先剔除代码块内的井号 |
| 编码 | `U+FFFD` 计数为 0 | 仅术语表故意留 1 个示例 |
| 行尾空格 | 0 | 通过 |
| 首末行 | 是完整句子 | 通过 |

**一个容易踩的坑**：统计围栏时，表格里若出现三个反引号（哪怕在行内代码里），
也会被算成围栏。**检查脚本必须先剔除行内代码**，否则会误报。

### 8.5 可复现性审计

**审计问题清单**（可直接复用）：

1. 文档里出现的每个清单文件，仓库里是否存在？
2. 每条命令是否能在当前版本跑通？
3. 输出里的版本号/CRD 数量是否与实测一致？
4. 章节之间的引用（"见第 N 章"）是否有效？
5. `00-README.md` 的目录/学习路径/统计三处是否与正文一致？
6. 术语是否统一（NodePort vs nodePort vs 节点端口）？

**本轮结果**：补齐 10 个缺失清单；修正 3 处版本口径；统一标题格式。
**成本**：10 个提交。**收益**：教程从"能读"变成"能照着做"。

## 9. 隐私与安全工程

### 9.1 八条规则

`scripts/privacy-check.sh` 扫描所有 git 跟踪/待跟踪文件：

| # | 规则 | 检测内容 | 豁免机制 |
|---|---|---|---|
| 1 | 本地绝对路径 | home / Users / data / mnt / root 等本机目录前缀 | `ALLOW_PATH_PATTERNS` 精确前缀 |
| 2 | 私钥 | PEM 私钥文件头（BEGIN … PRIVATE KEY） | 无（永不豁免） |
| 3 | kubeconfig 私钥数据 | 内嵌的私钥与证书 base64 字段 | 无 |
| 4 | 云/平台密钥 | AWS、GCP、GitHub、Slack、OpenAI 的密钥前缀及证书 | 无 |
| 5 | 明文密码 | 密码类字段的直接赋值 | 变量引用 / 模板占位 / 演示值白名单 |
| 6 | 内网 IP | 192.168 / 10.x / 172.16-31 网段 | `ALLOW_IPS` 逐值 |
| 7 | 邮箱 / 手机号 | 正则 | `go.mod`/`go.sum` 只查邮箱（伪版本号误报） |
| 8 | 敏感文件名 | kubeconfig、pem、key、env、id_rsa 等 | `ALLOW_SENSITIVE_FILES` 精确文件名 |

### 9.2 白名单设计三原则

1. **精确到值，不精确到类**：`ALLOW_IPS` 写 `"192.168.56.10"`，不写 `"192.168.*"`。
2. **每条豁免必须能说清理由**：注释写明"这是项目设计内的拓扑"还是"演示占位密码"。
3. **删代码时同步删豁免**：`deployment-recommendations.md` 删除后，
   立即移除只为它存在的那个 IP 白名单条目。**豁免的生命周期 = 它保护的内容的生命周期。**

### 9.3 真实拦截案例

**案例 A：文档里的本机路径**

合并归档文档时，`privacy-check` 报：

```
[绝对路径] production/design-history.md
```

原因是正文里有 4 处本机绝对路径（形如 `/data/<项目目录>`）。

处置：**改成 `<repo-root>` 后 `git commit --amend`**，
而不是"先提交、再补一个修复提交"。

> 理由：泄漏一旦进历史，就永久留在 `git log` 里。
> "leak-then-fix" 只是让工作区干净，历史仍然脏。

**案例 B：中文文件名漏检（门禁自身的 bug）**

`git ls-files` 默认把非 ASCII 文件名输出成 `"docs/01-\346\226\207.md"`，
`[ -f "$f" ]` 判断失败 → **整个文件被跳过，且不报错**。

修法：`git -c core.quotepath=false ls-files`。

**教训**：门禁的失效模式是"静默放行"，比"误报"危险得多。
所以门禁本身要有**自测正反例**（`production/scripts/selftest.sh`）。

**案例 C：白名单不能因为麻烦而放宽**

`go.sum` 里的 Go 伪版本号（形如 `v0.0.0-<14 位时间戳>-<hash>`）含连续 11 位数字，
必然命中手机号正则。

**错误修法**：对 `go.sum` 整体豁免。
**正确修法**：只对 `*/go.mod|go.sum` 关闭手机号分支，邮箱分支照查。

### 9.4 安全审查要点

`docs/security-review.md` 的结论落在三件事上：

1. **凭据不进仓库**：真实值放 `cluster.env.local`（gitignore），仓库只放 `*.example`；
2. **权限最小化**：kubeconfig 保存后 `chmod 600`；`ops` 账号 NOPASSWD 是**初始化期**策略，
   后续可改为需密码；
3. **日志脱敏**：日志库对敏感字段做过滤，避免 token 落盘。

**一个诚实的判断**：Vagrant 生成的 VM 使用已知的私有 key，
在"本地演示"场景下风险可控——**写清楚适用边界，比假装它安全更有用**。

## 10. 事故与恢复

### 10.1 发生了什么

- 目标：`/dev/sda3`（375 GiB，ext4，挂载在 `/data`）；
- 事故：误删 3 份 Markdown 文档，其中 1 份**从未提交过 git**；
- 时间：删除后约 1 小时开始抢救，期间目标分区只有零星写入（数 MB）。

### 10.2 处置链

```
lsof +L1        → 无进程持有（没有免费午餐）
extundelete     → 0 descriptors / checksum mismatch / Operation not permitted
                   ⇒ 元数据路线彻底断
photorec 类     → Markdown 无文件签名，不适用
裸盘 carve      → 唯一可行：用记得的一句话去盘上找正文
```

### 10.3 关键数字

| 项 | 值 |
|---|---|
| 扫描耗时 | 约 10 分钟（375 GiB / 4 线程） |
| 命中数 | 9 处 |
| 实际文档数 | **3 份** |
| 最大命中聚类 | 7 处命中落在同一份 17.8 KB 文档内 |
| 最终恢复 | 3 份全部找回（第 4 份判定无价值，主动丢弃） |

### 10.4 三条教训

**教训 1：命中数 ≠ 文件数。**
`grep` 统计的是"关键字出现次数"。同一份文档里出现 7 次，就是 7 行命中。
**先把命中按位置聚类，再挖窗口。**

**教训 2：恢复工具会"看见"不属于你的东西。**
同一个窗口里扫到一份无关项目的交接文档，**没有去抠**。
克制是恢复者的基本素养。

**教训 3：唯一救不回来的风险最大的那份，正是从未 `git add` 过的。**
这条比所有技术都值钱：
**恢复是应急，备份才是方案。**

## 结语

这个项目做对的核心只有一件事：**把"不可复现的经验"变成了"可复现的资产"**。

具体表现为三句话：

1. **约束有编号**，所以需求不会蒸发；
2. **证据有落盘**，所以"跑过"是可验证的；
3. **边界有声明**，所以"没做"不会被误读成"做了"。

技术选型（Vagrant、Ansible、k3s、Helm）都可以换，
这三条换不掉——它们是**方法**，不是工具。

> 最后留一句给自己：**恢复是应急，备份才是方案；
> 重流程是保险，轻流程才是日常。**
